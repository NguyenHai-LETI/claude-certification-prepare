1. Lab Ex1: agent hỗ trợ khách hàng có escalation

CCAR-F D1 CCAR-F D2 CCAR-F D5

Hình dung đời thường
Một nhân viên quầy được giao bốn việc: tra khách, tra đơn, hoàn tiền, chuyển cấp trên. Quầy có một quy định cứng: hoàn tiền trên $500 phải có quản lý ký. Quy định đó không nằm trong lời dặn miệng, mà nằm ở máy tính tiền: máy không cho in phiếu hoàn trên $500.

Mục tiêu: tự dựng một vòng lặp agent có tool, lỗi có cấu trúc, cổng chặn bằng code và escalation. Không cần gọi API thật; viết code và tự kiểm theo tiêu chí ở cuối mục. Domain: D1, D2, D5. Lý thuyết ở bài 07, bài 05, bài 09.

Bước 1: bốn tool, hai tool dễ nhầm

tools = [
  {"name": "get_customer",
   "description": "Look up a customer by email or phone and return a verified customer_id. "
                  "Use FIRST, before any order or refund action. Does not return orders.",
   "input_schema": {"type": "object", "properties": {
       "email": {"type": "string"}, "phone": {"type": "string"}}}},
  {"name": "lookup_order",
   "description": "Return one order's status and amount. Requires a verified customer_id "
                  "from get_customer and an order_id. Use for 'where is my order' questions.",
   "input_schema": {"type": "object", "properties": {
       "customer_id": {"type": "string"}, "order_id": {"type": "string"}},
       "required": ["customer_id", "order_id"]}},
  {"name": "process_refund", "description": "...", "input_schema": {...}},
  {"name": "escalate_to_human", "description": "...", "input_schema": {...}}
]

get_customer và lookup_order là cặp dễ nhầm. Mô tả nói rõ mỗi tool trả gì, dùng khi nào, cần gì đầu vào, và ranh giới "không trả đơn hàng".

Bước 2: vòng lặp dựa trên stop_reason

messages = [{"role": "user", "content": user_text}]
while True:
    resp = client.messages.create(model=MODEL, max_tokens=4096,
                                  system=SYSTEM, tools=tools, messages=messages)
    messages.append({"role": "assistant", "content": resp.content})
    if resp.stop_reason != "tool_use":          # end_turn: trả lời xong
        break
    results = [run_tool_with_gate(b) for b in resp.content if b.type == "tool_use"]
    messages.append({"role": "user", "content": results})   # mọi tool_result trong MỘT message

Bước 3: lỗi có cấu trúc

{"type": "tool_result", "tool_use_id": block.id, "is_error": true,
 "content": json.dumps({"errorCategory": "business",        # transient | validation | business | permission
                        "isRetryable": false,

Bước 4: cổng chặn bằng code

def run_tool_with_gate(block):
    if block.name in ("lookup_order", "process_refund") and not session.verified_customer_id:
        return error(block, "validation", False, "Call get_customer first to verify the customer.")
    if block.name == "process_refund" and block.input["amount"] > 500:
        ticket = escalate_to_human(summary_for_human(block))       # chuyển luồng
        return error(block, "business", False, f"Escalated to a manager: ticket {ticket}.")
    return execute(block)

Trong Agent SDK, cùng logic này đặt ở hook PreToolUse (chặn hoặc chuyển hướng trước khi tool chạy). Hook là cơ chế tất định; dặn trong system prompt chỉ là xác suất.

Bước 5: tin nhắn nhiều vấn đề

Thử: "Đơn #123 chưa tới, đơn #456 bị trừ tiền hai lần, và tôi muốn đổi email." Agent nên tách ba việc, xử lý từng việc (tra đơn, kiểm tra trùng tiền, đổi thông tin), rồi trả một câu trả lời tổng hợp.

2.1 Hai câu hỏi để đặt mỗi thứ vào đúng chỗ

Với mỗi mảnh cấu hình, hỏi hai câu. Ai cần nó? Cả đội thì đặt trong repo và commit; chỉ mình bạn thì đặt ở thư mục nhà hoặc file settings.local.json. Khi nào cần nạp? Luôn luôn thì vào CLAUDE.md; chỉ khi sửa file khớp một mẫu thì vào rule có paths; chỉ khi có người gọi thì vào command hay skill.

2.2 Skill chạy trong context riêng

Mặc định, mọi thứ một skill đọc và in ra đều chảy vào hội thoại chính. Khi skill có context: fork, nó chạy trong một subagent với context riêng; phiên chính chỉ nhận bản tóm tắt cuối. Trường allowed-tools giới hạn tool trong lúc skill chạy, ví dụ chỉ Read, Grep, Glob để skill phân tích không thể sửa file. Trường argument-hint nhắc người dùng nhập đối số khi gọi skill mà chưa truyền.

Ví dụ chạy từng bước. Đội muốn kiểm tra phụ thuộc lỗi thời của một monorepo có 200 file package.json.

  1. Không fork: Claude đọc 200 file ngay trong hội thoại chính; context đầy, các chỉ dẫn đầu phiên bị đẩy xa.
  2. Có context: fork và allowed-tools: Read, Grep, Glob: skill đọc 200 file trong context riêng, không có tool ghi.
  3. Skill trả về một bản tóm tắt ngắn: gói lỗi thời, gói rủi ro, đề xuất.
  4. Phiên chính vẫn gọn, người dùng hỏi tiếp về kết quả mà không mất bối cảnh trước đó.
Sai
Dồn mọi quy ước (API, test, tài liệu) vào một CLAUDE.md 600 dòng ở gốc repo; quy ước test cũng được nạp khi chỉ đang sửa tài liệu, và loãng chú ý.
Đúng
Giữ trong CLAUDE.md chỉ thứ cần mọi lúc; quy ước theo loại file chuyển thành rule có paths, chỉ nạp khi Claude đụng file khớp.
Bẫy. Ghi giá trị token thật vào .mcp.json rồi commit. File này nằm trong repo nên lộ cho mọi người và lưu vào lịch sử git. Viết ${GITHUB_TOKEN} để mỗi người dùng token của chính mình.
Thuật ngữ
Scope
Phạm vi áp dụng của một cấu hình: project (commit vào repo, cả đội dùng) hay user (thư mục nhà, riêng bạn).
Glob
Mẫu tên file có ký tự đại diện, ví dụ **/*.test.* khớp mọi file test ở mọi thư mục.
context: fork
Thiết lập cho skill chạy trong subagent riêng, chỉ trả tóm tắt về phiên chính.
Cốt lõi. "Cả đội", "khi clone repo" thì đặt ở project và commit. "Cá nhân", "thử nghiệm" thì đặt ở thư mục nhà. Quy ước theo loại file rải khắp repo thì dùng rule có paths.

3. Lab Ex3: pipeline trích xuất có cấu trúc

CCAR-F D4 CCAR-F D5

Hình dung đời thường
Nhập hoá đơn vào phần mềm kế toán: ô nào hoá đơn không có thì để trống, không tự bịa. Nhập sai định dạng ngày thì phần mềm báo lỗi và bạn sửa đúng ô đó. Hoá đơn nào mờ thì để riêng cho kế toán trưởng xem.

Mục tiêu: trích xuất bằng tool_use với JSON schema, validate và retry, xử lý theo lô, chuyển ca khó cho người. Domain: D4, D5. Lý thuyết ở bài 04, bài 09 §6.

{"name": "extract_invoice", "input_schema": {"type": "object",
  "properties": {
    "invoice_number": {"type": "string"},
    "due_date":       {"type": ["string", "null"]},       # có thể không có: nullable
    "category":       {"enum": ["goods", "services", "other", "unclear"]},
    "category_detail":{"type": ["string", "null"]},       # mô tả khi category = other
    "stated_total":   {"type": "number"},
    "calculated_total": {"type": "number"},
    "conflict_detected": {"type": "boolean"},
    "field_confidence": {"type": "object"}},
  "required": ["invoice_number", "category", "stated_total"]}}

Theo lô và SLA

100 tài liệu qua Message Batches, mỗi request có custom_id. Kết quả về không theo thứ tự: ghép bằng custom_id. Mục lỗi: chỉ gửi lại mục đó, có điều chỉnh (chia nhỏ tài liệu quá dài). Tính thời gian: chờ tới lần gửi lô + tối đa 24 giờ xử lý phải nằm trong SLA. Ví dụ SLA 30 giờ thì gửi lô ít nhất mỗi 6 giờ.

Tiêu chí tự kiểmĐạt khi
Trường không có trong tài liệuTrả null, không bịa
Loại ngoài danh sáchother kèm category_detail
RetryGhi lại lỗi nào sửa được qua retry, lỗi nào không
Few-shot2–4 ví dụ cho tài liệu cấu trúc khác nhau (trích dẫn nội dòng và thư mục, bảng và văn xuôi)
Người duyệtĐộ chính xác đo theo loại tài liệu và theo trường, lấy mẫu phân tầng, trước khi giảm duyệt tay
Cốt lõi. Schema loại lỗi cú pháp, không loại lỗi ngữ nghĩa. Nullable chống bịa. Retry chỉ có ích khi thông tin có trong tài liệu.

4. Lab Ex4: hệ nghiên cứu nhiều agent

CCAR-F D1 CCAR-F D5

Hình dung đời thường
Trưởng nhóm nghiên cứu giao hai trợ lý cùng lúc: một người tìm tài liệu trên mạng, một người đọc báo cáo nội bộ. Mỗi người nộp phiếu ghi chép có cột "nhận định, trích đoạn, nguồn, ngày". Ai không truy cập được nguồn thì ghi rõ đã thử gì và còn thiếu gì.

Mục tiêu: coordinator giao việc song song, truyền context rõ, giữ nguồn gốc, lan truyền lỗi có cấu trúc. Domain: D1, D2, D5. Lý thuyết ở bài 07, bài 09 §7.

4.1 Subagent không thừa hưởng hội thoại

Subagent bắt đầu với context trống. Nó chỉ biết những gì coordinator viết trong prompt giao việc. Vì vậy prompt phải tự đủ: câu hỏi cần trả lời, phạm vi (nguồn nào, giai đoạn nào), ranh giới với subagent khác, định dạng kết quả. Subagent làm đúng yêu cầu mà báo cáo vẫn thiếu thì lỗi nằm ở người giao việc.

Sai
Giao "nghiên cứu về năng lượng tái tạo" cho hai subagent; cả hai cùng tìm tin về điện mặt trời, không ai đụng tới điện gió. Báo cáo cuối phủ hẹp.
Đúng
Coordinator chia chủ đề thành các hướng không chồng nhau (điện mặt trời, điện gió, lưu trữ), mỗi prompt ghi rõ hướng, nguồn ưu tiên và định dạng kết quả.

4.2 Ba cách xử lý lỗi của subagent

Cách làmHậu quảĐánh giá

Trả lỗi có cấu trúc: loại lỗi, truy vấn đã thử, kết quả một phần, hướng thay thếCoordinator đi tiếp với phần có sẵn, thử hướng khác hoặc ghi rõ chỗ thiếu trong báo cáoĐúng

Ví dụ chạy từng bước. Subagent phân tích tài liệu nội bộ bị timeout ở báo cáo thứ ba trong năm báo cáo.

  1. Subagent trả status: partial, errorType: timeout, hai kết quả đã trích, và gợi ý thử lại báo cáo thứ ba.
  2. Coordinator thử một lần với phạm vi nhỏ hơn; vẫn lỗi.
  3. Coordinator đi tiếp: tổng hợp từ bốn báo cáo, ghi chú "báo cáo thứ ba chưa phân tích được do timeout".
  4. Người đọc báo cáo biết phạm vi phủ thật, không nhầm thiếu dữ liệu với không có phát hiện.
Bẫy. Khi hai nguồn uy tín đưa số liệu khác nhau, đừng chọn một số "có vẻ đúng" và bỏ số kia. Giữ cả hai kèm nguồn và ngày, ghi rõ chỗ mâu thuẫn. Chọn một bên mà không có căn cứ là làm mất thông tin người đọc cần.

5. Phạm vi đề CCAR-F

CCAR-F D5 CCAR-F

Exam guide liệt kê rõ chủ đề có ra và không ra. Dùng danh sách "không ra" để không học thừa và để loại nhanh phương án nói về các chủ đề đó.

Có ra
  • Vòng lặp agent theo stop_reason; điều kiện dừng
  • Coordinator, subagent, phân rã, chạy song song, lặp tinh chỉnh
  • Truyền context cho subagent, lưu trạng thái, khôi phục bằng manifest
  • Thiết kế tool, tách hay gộp, đặt tên; resource và tool của MCP
  • Cấu hình MCP project và user, biến môi trường
  • Lỗi có cấu trúc, phục hồi tại chỗ trước khi đẩy lên
  • Escalation theo tiêu chí, tôn trọng yêu cầu khách, chính sách có khoảng trống
  • CLAUDE.md, @import, rules có glob, command, skill
  • Plan mode hay làm trực tiếp; tinh chỉnh lặp
  • Output qua tool_use, nullable, tool_choice; few-shot
  • Batches; tối ưu context; human review; nguồn gốc thông tin
Không ra
  • Fine-tuning, huấn luyện model riêng
  • Xác thực API, billing, quản lý tài khoản
  • Chi tiết ngôn ngữ lập trình, framework
  • Triển khai, host MCP server
  • Kiến trúc nội bộ, quá trình huấn luyện, Constitutional AI, RLHF
  • Embedding, vector database
  • Computer use, vision
  • Streaming, SSE
  • Rate limit, quota, tính giá
  • OAuth, xoay vòng key
  • Cấu hình AWS, GCP, Azure; benchmark
  • Chi tiết prompt caching (chỉ cần biết có); thuật toán tokenization
Bẫy. Phương án "dùng vector database", "chuyển sang streaming", "tăng rate limit" trong một câu CCAR-F hiếm khi là đáp án, vì chủ đề nằm ngoài phạm vi. Nhiều mục trong cột phải lại có trong CCDV-F (streaming, caching, rate limit): đừng mang suy luận CCAR-F sang CCDV-F.

6.1 Cách đọc bảng khi gặp một phương án "mới hơn"

Đề CCAR-F viết theo exam guide v1.0. Nếu một phương án dùng tính năng của tài liệu hiện hành mà exam guide không nhắc, đừng chọn chỉ vì nó mới. Làm ba bước:

  1. Xác định câu hỏi đang kiểm khái niệm nào (ví dụ: ép Claude trả đầu ra có cấu trúc).
  2. Tìm trong bảng hàng tương ứng. Cột exam guide là cách đề coi là đúng.
  3. Chọn phương án khớp cột exam guide. Nếu hai phương án cùng đúng theo exam guide, quay về nguyên tắc: nguyên nhân gốc, cách nhẹ và tương xứng, cơ chế tất định cho hậu quả lớn.
Sai
Câu hỏi về cách đảm bảo mọi lần trả lời đều có đầu ra có cấu trúc. Loại phương án tool_choice: "any" vì "model mới trả 400", chọn phương án nói về một tính năng ngoài exam guide.
Đúng
Chọn tool_choice "any" hoặc tool cụ thể, đúng theo exam guide. Khác biệt của tài liệu hiện hành ghi vào ghi chú ôn tập, không đổi đáp án.
Bẫy. Làm ngược lại cũng sai khi làm sản phẩm thật. Bảng này chỉ cho cách trả lời đề; khi viết code chạy trên API hiện hành, đọc tài liệu hiện hành, vì model mới có thể từ chối tham số cũ.

7.1 Ba kiểu nguyên nhân gốc lặp lại

Mười hai bài học trên quy về ba kiểu. Nhận ra kiểu nào thì chọn nhanh được hướng sửa.

Ví dụ chạy từng bước. Một câu hỏi mô tả: agent hỗ trợ đôi lúc gọi process_refund trước khi xác minh khách. Bốn phương án: viết lại system prompt nhấn mạnh "luôn xác minh trước"; thêm ví dụ few-shot; chặn bằng code; thêm một agent giám sát.

Bẫy. Đừng áp một công thức cho mọi câu. Khi lỗi chỉ do mô tả tool sơ sài, thêm cổng chặn là làm quá tay; cách nhẹ nhất giải quyết đúng nguyên nhân mới là đáp án. Cơ chế tất định dành cho trường hợp hậu quả nặng.
Cốt lõi. Tìm nguyên nhân gốc; chọn cách nhẹ và tương xứng; ngoại lệ là khi có hậu quả tài chính, bảo mật, tuân thủ thì chọn cơ chế tất định. Chiến thuật đầy đủ ở trang tổng quan §6.
