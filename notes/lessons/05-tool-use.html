1. Thiết kế giao diện tool

CCAR-F D2 CCDV-F D8

Hình dung đời thường
Bạn mở danh bạ và thấy hai số cùng ghi “Dịch vụ khách hàng”. Bạn không biết gọi số nào cho việc của mình. Model cũng ở tình huống đó: nó không nhìn thấy code bên trong tool, chỉ đọc tên và mô tả để đoán tool nào hợp với câu hỏi. Mô tả càng rõ, nó càng chọn đúng.

Một tool definition (khai báo tool) gồm ba phần bắt buộc: name, description, input_schema. Có thể thêm input_examples. Mục này nói từng phần dùng để làm gì; mục 2 đi qua một khai báo đầy đủ và cách gộp tool trùng; mục 3 nói code của bạn gửi tool, nhận lời gọi và trả kết quả ra sao.

Cốt lõi. Mô tả tool là cơ chế chính để model chọn tool. Mô tả tốt nêu: tool làm gì, định dạng đầu vào, ví dụ câu hỏi, trường hợp biên, và ranh giới “khi nào dùng tool này thay vì tool kia”.
{
  "name": "lookup_order",
  "description": "Tra một đơn hàng theo mã đơn (dạng ORD-123456). Dùng khi khách nhắc mã đơn
    hoặc hỏi trạng thái giao hàng. KHÔNG dùng để tìm khách hàng; khi chỉ có tên hoặc email,
    dùng get_customer trước. Trả về null nếu không có đơn.",
  "input_schema": {"type": "object",
    "properties": {"order_id": {"type": "string", "pattern": "^ORD-\\d{6}$"}},
    "required": ["order_id"]}
}

Đoạn mô tả trên trả lời đủ bốn câu: làm gì, dùng khi nào, không dùng khi nào (và dùng tool nào thay thế), kết quả khi không có dữ liệu.

Khi hai tool trông giống nhau

Dễ nhầm
  • analyze_content: “Phân tích nội dung”
  • analyze_document: “Phân tích tài liệu”
  • Hai mô tả gần như giống hệt, model chọn ngẫu nhiên
Rõ ràng
  • Đổi tên: analyze_content thành extract_web_results, mô tả riêng cho kết quả web
  • Hoặc tách tool chung thành các tool có hợp đồng vào/ra rõ: extract_data_points, summarize_content, verify_claim_against_source
  • Rà system prompt: một câu như “luôn kiểm tra tài khoản trước” có thể vô tình kéo model về get_customer cả khi khách chỉ hỏi đơn hàng, lấn át mô tả tool tốt.
Bẫy. Bước đầu tiên khi model chọn sai tool là sửa mô tả (và tên), không phải thêm few-shot, dựng router riêng hay gộp tool.
Thực tế 11/2026 Tài liệu hiện hành có thêm input_examples: danh sách ví dụ đầu vào hợp lệ theo input_schema (ví dụ sai schema trả lỗi 400). Mỗi ví dụ tốn thêm khoảng 20 đến 200 token, và không dùng được cho server tool như web search. Exam guide chỉ nhấn mạnh mô tả, ví dụ câu hỏi và ranh giới.

1.1 Ví dụ từng bước: sửa mô tả, không thêm router

Agent hỗ trợ khách có hai tool với mô tả ngắn: get_customer (“Retrieves customer information”) và lookup_order (“Retrieves order details”). Khách gõ: “Kiểm tra đơn #4521 của tôi”.

  1. Quan sát: nhật ký cho thấy Claude gọi get_customer trước, dù khách chỉ hỏi đơn hàng. Hai mô tả đều nói “retrieves … information”, và chữ “của tôi” kéo model về tool khách hàng.
  2. Sửa mô tả của get_customer: “Look up a customer by email or customer ID. Use when you need account status. Do NOT use for order status: use lookup_order.”
  3. Sửa mô tả của lookup_order: “Look up an order by order number such as #4521. Use for shipping and payment status. Returns an empty list if the order does not exist.”
  4. Chạy lại eval với các câu hỏi về đơn. Đúng tool thì dừng; vẫn sai thì rà system prompt xem có câu nào kéo về get_customer.

Thứ tự ưu tiên sửa khi chọn sai tool: mô tả và tên trước, system prompt tiếp theo, rồi mới tới few-shot hay gộp tool. Dựng một router riêng là bước cuối.

Thuật ngữ
Tool definition
Phần khai báo một tool gửi kèm request: tên, mô tả, schema đầu vào.
JSON Schema
Cách mô tả hình dạng dữ liệu JSON: kiểu từng trường, trường nào bắt buộc, mẫu chuỗi hợp lệ.
Few-shot
Đưa vài ví dụ mẫu vào prompt để model bắt chước.
Router
Thành phần riêng quyết định gọi tool nào. Đắt và chậm hơn việc sửa mô tả.

2. Một khai báo đầy đủ và gộp tool trùng

CCDV-F D8 CCAR-F D2

Mục 1 đã nêu bốn phần của tool definition. Ví dụ dưới là một khai báo đủ cả bốn phần, với description viết nhiều dòng theo khoá Tool Use with the Messages API của Academy. Tên tool nên là động từ + đối tượng, viết snake_case; input_schema là JSON Schema.

tools = [{
    "name": "search_products",
    "description": """Search the product catalog by keyword and optional filters.

    Use this tool when:
    - Customer asks about available products
    - You need to find products matching specific criteria
    - Customer wants to compare products

    Do NOT use this tool for:
    - Checking inventory levels (use check_inventory instead)
    - Processing orders (use create_order instead)

    Returns a list of matching products with name, price, and availability.""",
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {
                "type": "string",
                "description": "Search keywords, e.g. 'wireless headphones under $100'"
            },
            "category": {
                "type": "string",
                "enum": ["electronics", "clothing", "home", "sports"],
                "description": "Optional category filter"
            },
            "max_price": {
                "type": "number",
                "description": "Maximum price in USD. Omit to search all prices."
            }
        },
        "required": ["query"]
    },
    "input_examples": [
        {"query": "bluetooth speaker", "max_price": 50},
        {"query": "running shoes", "category": "sports"}
    ]
}]

Đọc code trên từng phần:

Đoạn codeÝ nghĩa
tools = [{ ... }]Danh sách tool gửi kèm request. Ở đây chỉ có một tool.
"name": "search_products"Tên theo kiểu động từ + đối tượng, viết thường, nối bằng gạch dưới.
"description": """..."""Chuỗi nhiều dòng. Có đủ: tool làm gì, Use this tool when, Do NOT use this tool for (kèm tool thay thế), và Returns (dạng đầu ra).
"type": "object"Đầu vào của tool là một đối tượng JSON có các trường bên dưới.
"query": {"type": "string", ...}Trường chuỗi, kèm mô tả và ví dụ để Claude biết điền gì.
"enum": [...]Chỉ cho chọn trong danh sách đóng: Claude không được tự nghĩ ra danh mục khác.
"max_price": {"type": "number"}Trường số. Mô tả nói rõ “Omit to search all prices” để Claude biết có thể bỏ trống.
"required": ["query"]Chỉ query bắt buộc. category và max_price là tùy chọn.
"input_examples": [...]Hai ví dụ đầu vào hợp lệ để Claude thấy cách dùng thực tế.
Cốt lõi. Description tốt có ba đến bốn câu, mỗi câu trả lời một ý: tool làm gì; khi nào dùng; khi nào không dùng và dùng tool nào thay; kết quả trả về có dạng gì. Đây cũng là bốn câu mà ví dụ lookup_order ở mục 1 trả lời.
Thuật ngữ
snake_case
Kiểu đặt tên viết thường, các từ nối bằng gạch dưới, ví dụ search_products.
enum
Danh sách giá trị cho phép. Giá trị ngoài danh sách là không hợp lệ.
Optional parameter
Tham số tùy chọn: không nằm trong required, có thể bỏ trống.

2.1 Gộp tool trùng chức năng

Khi nhiều tool cùng làm một việc và chỉ khác nhau ở bộ lọc, gộp chúng thành một tool có tham số tuỳ chọn:

# BAD — Claude không biết khi nào dùng cái nào
tools_bad = [
    {"name": "search_by_name", ...},
    {"name": "search_by_category", ...},
    {"name": "search_by_price", ...}
]

# GOOD — một tool với optional parameters
tools_good = [{
    "name": "search_products",
    "description": "Search products by any combination of name, category, or price range.",
    "input_schema": {
        "type": "object",
        "properties": {
            "name": {"type": "string"},
            "category": {"type": "string"},
            "min_price": {"type": "number"},
            "max_price": {"type": "number"}
        }
        # required: [] — tất cả optional
    }
}]
  • tools_bad: ba tool với ba tên gần giống, ... là phần còn lại bị lược. Câu hỏi “tìm tai nghe rẻ hơn 100 đô” cần cả tên lẫn giá, nhưng Claude chỉ được chọn một tool.
  • tools_good: một tool với bốn trường, không có trường nào bắt buộc (required bỏ trống). Claude điền trường nào cần dùng và bỏ qua trường còn lại.
Sai
  • Ba tool search_by_* mô tả mơ hồ như nhau
  • Thêm few-shot để “dạy” Claude chọn giữa ba tool đó
Đúng
  • Một tool search_products với tham số tùy chọn
  • Hoặc giữ tool riêng nhưng viết description khác biệt rõ
Gộp hay tách. Mục 1 khuyên tách analyze_content thành các tool hẹp; mục này khuyên gộp ba tool search_by_*. Hai lời khuyên không mâu thuẫn, vì mục tiêu chung là mỗi tool có ranh giới dễ phân biệt: gộp khi các tool chỉ khác nhau ở bộ lọc, tách khi chúng khác nhau ở mục đích hay ở hợp đồng vào/ra. Trước khi gộp hay tách, thử sửa tên và mô tả trước.

3. Vòng lặp tool use từ đầu đến cuối

CCDV-F D8

Hình dung đời thường
Claude như một nhân viên giỏi nhưng ngồi trong phòng kín, không có mạng. Bạn đưa cho họ một danh sách điện thoại nội bộ (tool schema). Khi cần biết giờ hiện tại, họ viết giấy nhờ: “Hãy gọi số get_current_datetime” (tool_use). Bạn gọi giúp, ghi kết quả ra giấy (tool_result) và đưa lại. Họ đọc rồi trả lời. Claude không tự bấm máy, code của bạn mới chạy tool.

Mục này đi theo khoá Building with the Claude API (module 4) của Academy: viết hàm, khai báo schema, rồi chạy vòng gửi và nhận cho tới khi Claude trả lời xong. Cách viết description đã nói ở mục 1 và 2; cách xử lý nhiều lời gọi cùng lúc ở mục 7.

Thuật ngữ
Tool schema
Tên khoá học dùng cho tool definition (mục 1).
tool_use block
Khối Claude trả về để xin gọi tool: có id, name, input.
tool_result block
Khối bạn gửi lại kết quả: có tool_use_id (khớp với id trên), content, is_error.
Server tool
Tool do Anthropic chạy hộ (web search, code execution). Bạn không viết phần thực thi.

3.1 Bốn bước

Tool use cho Claude lấy dữ liệu thời gian thực và gọi hệ thống bên ngoài. Luồng có bốn bước: (1) gửi message kèm danh sách tool; (2) Claude trả tool_use block; (3) code của bạn chạy tool; (4) gửi tool_result và nhận câu trả lời cuối của Claude.

3.2 Hàm và schema

Hàm của tool là một hàm Python bình thường. Schema là khai báo mô tả hàm đó cho Claude:

def get_current_datetime(format: str = "%Y-%m-%d %H:%M:%S") -> str:
    """Get current date and time."""
    if not format: raise ValueError("format required")
    return datetime.now().strftime(format)

get_current_datetime_schema = {
    "name": "get_current_datetime",
    "description": "Returns current date/time. Use when user asks about today's date, current time, or needs to calculate relative dates. Returns formatted datetime string.",
    "input_schema": {
        "type": "object",
        "properties": {
            "format": {"type": "string",
                       "description": "strftime format string, e.g. '%Y-%m-%d' for date only, '%H:%M:%S' for time only"}
        },
        "required": ["format"]
    }
}

Description ở đây trả lời đủ các câu của mục 2: làm gì, khi nào dùng, trả về gì; tham số có mô tả và ví dụ.

3.3 Content block và tool result

Khi Claude dùng tool, response có nhiều content block: text block (giải thích) và tool_use block (hành động). Phải thêm toàn bộ assistant message vào lịch sử, không chỉ phần text:

messages = [{"role": "user", "content": "What time is it?"}]
response = client.messages.create(
    model=model, max_tokens=1000, messages=messages,
    tools=[get_current_datetime_schema]
)

# response.content có thể gồm text block + tool_use block
messages.append({"role": "assistant", "content": response.content})

# Execute tool
tool_block = next(b for b in response.content if b.type == "tool_use")
result = get_current_datetime(**tool_block.input)

# Trả tool result
messages.append({"role": "user", "content": [{
    "type": "tool_result",
    "tool_use_id": tool_block.id,     # phải khớp với id của tool_use block
    "content": str(result),
    "is_error": False
}]})

# Final call — vẫn phải gửi tools
final = client.messages.create(
    model=model, max_tokens=1000, messages=messages,
    tools=[get_current_datetime_schema]
)

3.4 Vòng lặp nhiều lượt

Vòng lặp xử lý nhiều lời gọi tool liên tiếp, dừng khi stop_reason là end_turn:

def run_conversation(messages, tools):
    while True:
        response = client.messages.create(
            model=model, max_tokens=1000, messages=messages, tools=tools)
        messages.append({"role": "assistant", "content": response.content})

        if response.stop_reason == "end_turn":
            return response  # Claude xong, không cần tool nữa

        # Có tool_use blocks → execute và trả results
        tool_results = []
        for block in response.content:
            if block.type == "tool_use":
                result = run_tool(block.name, block.input)
                tool_results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": str(result)
                })
        messages.append({"role": "user", "content": tool_results})
Sai
  • Chỉ thêm phần text của response vào lịch sử, bỏ mất tool_use block
  • tool_use_id không khớp, hoặc quên gửi tools ở lần gọi cuối
Đúng
  • Append nguyên response.content vào history
  • Mỗi tool_use có một tool_result cùng id, lỗi thì is_error: true

3.5 Nhiều tool, fine-grained, text edit, web search

Nhiều tool: thêm một tool gồm bốn việc: viết hàm, khai báo schema, thêm vào danh sách tools, thêm nhánh trong run_tool. Claude có thể gọi nhiều tool trong một response (mục 7).

Fine-grained tool calling (eager_input_streaming: True): nhận từng mảnh JSON ngay khi Claude sinh ra, dùng khi cần hiện tiến độ theo thời gian thực. Đánh đổi: không có kiểm tra phía server, code của bạn phải xử lý JSON hỏng.

Text edit tool: tool có sẵn của Claude để xem và sửa file. Claude biết schema, còn bạn viết phần thực thi.

web_search_schema = {
    "type": "web_search_20250305",
    "name": "web_search",
    "max_uses": 5,
    "allowed_domains": ["docs.anthropic.com"]  # restrict tới trusted sources
}
# Claude tự quyết định khi nào search, không cần implement execution
Web search tool: phải bật trong cài đặt Console trước khi dùng. Response có ServerToolUseBlock, WebSearchToolResultBlock và các citation block.

3.6 Đọc stop_reason trong vòng lặp

Vòng lặp tool không chỉ kiểm tra end_turn. Mỗi giá trị stop_reason cần một hành động khác:

stop_reasonNghĩaViệc code làm
tool_useClaude đang gọi toolChạy tool, gửi tool_result, lặp
end_turnClaude xong tự nhiênDùng câu trả lời, thoát vòng lặp
max_tokensChạm trần max_tokensTăng max_tokens hoặc cho Claude viết tiếp; câu trả lời đã bị cắt
pause_turnVòng lặp server tool đạt giới hạn lượtGửi lại nội dung assistant để viết tiếp (mục 8)
refusalClaude từ chối trả lờiĐọc stop_details, cân nhắc model dự phòng
Bẫy. Thêm một khối text ngay sau tool_result trong user message. Docs hiện hành cảnh báo Claude có thể coi lượt là đã xong và trả response rỗng với end_turn. Chỉ gửi các tool_result. Nếu vẫn rỗng, thêm một user message mới kiểu “Please continue” thay vì gửi lại response rỗng.

4. Lỗi có cấu trúc

CCAR-F D2 CCDV-F D8

Hình dung đời thường
Bạn gọi tổng đài và nghe “Máy bận, vui lòng gọi lại sau” (nên thử lại). Lần khác nghe “Số này không tồn tại” (thử lại cũng vô ích). Lần khác nữa: “Bạn không có quyền xem thông tin này”. Ba câu khác hẳn nhau nên bạn biết phải làm gì tiếp. Nếu tổng đài chỉ nói “Có lỗi xảy ra”, bạn sẽ đoán mò. Tool cũng cần báo lỗi đủ rõ để agent quyết định đúng.

Khi tool lỗi, hãy trả về một kết quả đánh dấu lỗi kèm thông tin có cấu trúc. Với MCP, tool dùng cờ isError. Với client tool trên Messages API, tool_result có is_error: true.

{ "isError": true,
  "errorCategory": "business",
  "isRetryable": false,
  "message": "Đơn quá 30 ngày nên không được đổi trả. Hãy giải thích chính sách cho khách." }

Ví dụ minh hoạ cách đặt tên trường; điều quan trọng là có loại lỗi, cờ có thể thử lại, và lời giải thích dễ hiểu.

  • Lỗi business nên kèm lời giải thích thân thiện để agent nói lại với khách, và đánh dấu không thử lại. Nếu để agent thử lại, nó chỉ tốn lượt.
  • Không bao giờ bỏ qua một khối tool_use: mỗi lời gọi đều cần có tool_result tương ứng, kể cả khi lỗi.
  • Subagent tự xử lý lỗi transient tại chỗ. Chỉ đẩy lên coordinator lỗi không tự giải quyết được, kèm kết quả một phần và những gì đã thử.
Truy cập thất bại
  • Không lấy được dữ liệu (timeout, mất kết nối)
  • Chưa biết khách có đơn hay không
  • Cần quyết định thử lại
Truy vấn thành công nhưng rỗng
  • Truy vấn chạy tốt, trả về danh sách rỗng
  • Câu trả lời hợp lệ: khách chưa có đơn nào
  • Không phải lỗi, đừng thử lại
Bẫy. Thông báo chung chung “Operation failed” (agent không biết có nên thử lại). Trả danh sách rỗng khi thực ra lỗi truy cập, làm agent kết luận “khách không có đơn”. Trộn lẫn hai tình huống ở bảng trên.
Bẫy. Hiểu isRetryable: false là “bỏ việc”. Cờ này chỉ trả lời câu hỏi: gửi lại y hệt lời gọi này có thể thành công không. Lỗi validate là false vì đầu vào phải đổi trước; agent tự sửa đầu vào rồi gọi lại, và errorCategory cho nó biết điều đó. Lỗi nghiệp vụ và lỗi quyền cũng là false nhưng việc vẫn tiếp tục theo đường khác: giải thích cho khách, chuyển người, hoặc người có quyền. Exam guide chỉ nêu false cho lỗi nghiệp vụ; giá trị cho lỗi validate là quy ước chung của các hệ thống gọi dịch vụ.
Thực tế 11/2026 Đặc tả MCP bản 2026-07-28 chia lỗi làm hai loại. Protocol error là lỗi JSON-RPC chuẩn cho sự cố ở cấp yêu cầu mà model khó tự sửa: tool không tồn tại, yêu cầu sai cấu trúc, lỗi server. Tool execution error nằm trong kết quả tool với isError: true, gồm lỗi gọi API, lỗi validate đầu vào (ví dụ ngày sai định dạng, giá trị ngoài khoảng) và lỗi nghiệp vụ. Client nên đưa loại thứ hai cho model để model tự sửa tham số rồi gọi lại. Vì vậy một lỗi validate nên được trả bằng isError: true kèm thông báo cụ thể, không phải lỗi giao thức. Bản 2025-06-18 còn xếp “invalid arguments” vào protocol error; bản 2026-07-28 mới ghi rõ lỗi validate đầu vào là tool execution error, còn request không khớp schema CallToolRequest mới là protocol error. Đề thi chia lỗi theo bốn nhóm transient, validation, business, permission; hai cách chia này bổ sung nhau. Nguồn: MCP specification 2026-07-28, Tools: Error Handling, bản 2025-06-18.

6. tool_choice

7. Gọi tool song song

CCDV-F D8

Hình dung đời thường
Bạn cần ba việc: hỏi thời tiết, xem giá cổ phiếu, đọc tin công nghệ. Làm lần lượt thì mất 3 lượt chờ. Nhờ ba người cùng làm thì chỉ chờ lâu bằng người chậm nhất. Parallel tool calling là Claude giao ba việc cùng lúc, code của bạn cho ba luồng chạy cùng lúc.

Claude có thể gọi nhiều tools cùng lúc trong một turn — chạy song song để giảm latency:

from concurrent.futures import ThreadPoolExecutor
import anthropic

client = anthropic.Anthropic()

def run_tool(tool_name: str, tool_input: dict) -> str:
    """Execute a tool and return result as string."""
    if tool_name == "get_weather":
        return get_weather(**tool_input)
    elif tool_name == "get_stock_price":
        return get_stock_price(**tool_input)
    elif tool_name == "get_news":
        return get_news(**tool_input)
    else:
        raise ValueError(f"Unknown tool: {tool_name}")

messages = [{"role": "user", "content": "Get weather, AAPL stock price, and tech news."}]

while True:
    response = client.messages.create(
        model="claude-sonnet-5", max_tokens=2048,
        tools=tools, messages=messages
    )

    if response.stop_reason == "end_turn":
        break

    if response.stop_reason == "tool_use":
        # Collect ALL tool_use blocks trước khi chạy
        tool_use_blocks = [b for b in response.content if b.type == "tool_use"]

        # Chạy song song với ThreadPoolExecutor
        with ThreadPoolExecutor(max_workers=len(tool_use_blocks)) as executor:
            futures = {
                executor.submit(run_tool, block.name, block.input): block
                for block in tool_use_blocks
            }

            tool_results = []
            for future, block in futures.items():
                try:
                    result = future.result(timeout=30)
                    tool_results.append({
                        "type": "tool_result",
                        "tool_use_id": block.id,
                        "content": result
                    })
                except Exception as e:
                    tool_results.append({
                        "type": "tool_result",
                        "tool_use_id": block.id,
                        "is_error": True,  # Quan trọng: báo lỗi cho Claude
                        "content": f"Error: {str(e)}"
                    })

        # Thêm cả response của Claude VÀ tất cả tool results vào messages
        messages.append({"role": "assistant", "content": response.content})
        messages.append({"role": "user", "content": tool_results})  # Một user message, nhiều results

Chú giải từng đoạn:

  • ThreadPoolExecutor: công cụ của Python để chạy nhiều hàm cùng lúc trên nhiều luồng (thread). Phù hợp khi tool chủ yếu chờ mạng.
  • run_tool(tool_name, tool_input): một hàm điều phối. Nhận tên tool, gọi đúng hàm; tên lạ thì raise ValueError để lỗi lộ ra thay vì im lặng.
  • while True: vòng lặp chạy đến khi Claude trả end_turn.
  • tool_use_blocks = [b for b in response.content if b.type == "tool_use"]: lọc ra mọi khối tool_use trong câu trả lời. Có thể là 1 hoặc nhiều khối.
  • ThreadPoolExecutor(max_workers=len(tool_use_blocks)): số luồng bằng số tool cần chạy, nên tất cả chạy cùng lúc.
  • executor.submit(run_tool, block.name, block.input): giao một việc cho luồng. Trả về future (hứa hẹn kết quả sẽ có).
  • future.result(timeout=30): chờ kết quả tối đa 30 giây. Quá hạn thì ném lỗi, chuyển xuống except.
  • "tool_use_id": block.id: ghép kết quả với đúng lời gọi.
  • "is_error": True: báo cho Claude biết tool lỗi. Claude đọc nội dung lỗi và quyết định thử lại, hỏi người dùng hay đổi cách. Không ném ngoại lệ làm chết cả vòng lặp.
  • Hai dòng cuối: thêm response.content của Claude vào messages trước, rồi thêm một tin nhắn user chứa danh sách mọi kết quả.
Sai
  • Gửi mỗi tool_result một tin nhắn user riêng
  • Chạy tool_use đầu tiên ngay khi thấy, rồi mới đọc các khối còn lại
  • Ném ngoại lệ khi tool lỗi, làm sập vòng lặp
Đúng
  • Một tin nhắn user chứa mảng mọi tool_result, đứng sau tin nhắn assistant tương ứng
  • Gom hết các tool_use rồi mới chạy song song
  • Trả is_error: true kèm nội dung lỗi cho Claude
Quy tắc gọi tool song song: (1) gom TẤT CẢ tool_use block trước khi chạy bất kỳ cái nào; (2) chạy song song, ví dụ bằng ThreadPoolExecutor; (3) tool lỗi thì trả is_error: true, không ném exception; (4) gửi TẤT CẢ kết quả trong một user message duy nhất.
Thực tế 11/2026 Tài liệu hiện hành xác nhận cùng quy tắc: tách mỗi kết quả thành một tin nhắn user riêng là lỗi định dạng phổ biến nhất, và còn “dạy” Claude gọi song song ít hơn. Trong tin nhắn user đó, các khối tool_result phải đứng trước mọi nội dung văn bản. Claude 4 trở lên mặc định gọi song song khi hợp lý; disable_parallel_tool_use: true trong tool_choice tắt hành vi này. Nguồn: Parallel tool use.

7.1 Ví dụ có số: vì sao song song nhanh hơn

Ba tool chạy 2 giây, 3 giây và 1 giây. Chạy tuần tự mất 2 + 3 + 1 = 6 giây. Chạy song song mất bằng tool chậm nhất, khoảng 3 giây. Nhưng song song chỉ hợp khi ba lời gọi độc lập: tool 2 cần kết quả của tool 1 thì phải chạy sau.

Hình dạng messages sau lượt này, theo đúng thứ tự:

  1. Một message assistant chứa ba khối tool_use (id t1, t2, t3).
  2. Một message user chứa ba khối tool_result (tool_use_id lần lượt t1, t2, t3). Không thêm text trước chúng.

Nếu t2 lỗi, khối tool_result của t2 mang is_error: true. Hai khối còn lại vẫn thành công. Đủ ba khối là điều kiện để API chấp nhận request tiếp theo.

8. Client tool và server tool

CCDV-F D8 CCDV-F D2

Hình dung đời thường
Gọi món ở quán. Có món bạn tự làm ở nhà theo yêu cầu của đầu bếp rồi mang lại (client tool). Có món quán làm sẵn trong bếp và bưng ra luôn (server tool). Khác biệt là ai đứng bếp.
Client tool
  • Bạn định nghĩa, bạn chạy
  • Gửi tool_result (kèm tool_use_id) về
  • Nhiều tool_use song song: trả mọi tool_result trong một user message
Server tool
  • Web search, web fetch, code execution
  • Anthropic chạy, kết quả có sẵn trong response
  • Chạy lâu thì có thể gặp pause_turn

Bẫy. bash và text_editor có schema do Anthropic định nghĩa, nhưng vẫn là client tool: code của bạn chạy lệnh và gửi kết quả về. Chữ “Anthropic-defined” nói ai viết schema, không nói ai chạy.

8.2 Ví dụ: một lượt trộn cả hai loại

  1. Bạn gửi request có tool web_search (server) và get_customer (client). Khách hỏi một câu cần cả hai.
  2. Response chứa khối server_tool_use cho web_search (chưa có kết quả) và khối tool_use cho get_customer, với stop_reason: "tool_use".
  3. Bạn chỉ chạy get_customer và gửi một tool_result cho nó. Không gửi gì cho web_search.
  4. API chạy web_search khi nhận request kế tiếp, rồi Claude tiếp tục.

8.3 pause_turn: server tool chạy lâu

Server tool chạy trong vòng lặp phía server. Khi vòng lặp đạt giới hạn lượt, response có stop_reason: "pause_turn". Bạn không viết thêm câu của người dùng. Bạn gửi lại request với nội dung assistant vừa nhận được nối vào messages, để Claude chạy tiếp từ chỗ dừng.

Sai
  • Gặp pause_turn thì coi là xong và hiển thị câu trả lời dở dang
  • Tự chạy lại web_search bằng code của mình
Đúng
  • Nối response.content vào messages dưới role assistant, gửi request tiếp
  • Để API chạy server tool; bạn chỉ xử lý client tool
Cốt lõi. Hỏi “ai chạy code?” để phân loại. Client tool cần bạn trả tool_result. Server tool thì không, và có thể kèm pause_turn. Nguồn: Server tools.

Đúng
  • Edit lỗi vì không có đoạn text duy nhất: Read cả file rồi Write bản đã sửa

Bẫy. Nhầm Grep và Glob: Grep tìm trong nội dung, Glob tìm theo đường dẫn.
Thực tế 11/2026 Theo tài liệu tools của Claude Code, Edit làm thay thế chuỗi chính xác (không regex, không so khớp mờ). old_string phải khớp từng ký tự, kể cả khoảng trắng, và phải xuất hiện đúng một lần. Khi nó xuất hiện nhiều lần, Claude có hai cách rẻ trước khi đổi sang Read + Write: cung cấp chuỗi dài hơn kèm đủ ngữ cảnh xung quanh để chỉ khớp một chỗ, hoặc đặt replace_all: true để thay mọi chỗ. Claude thường cần đã đọc file trong hội thoại trước khi sửa (model mới hơn có thể sửa file chưa đọc khi việc đọc không cần hỏi quyền), và có thể sửa ngay sau khi xem file bằng Bash như cat hoặc grep trên một file. Đáp án đề khi Edit không tìm thấy mốc duy nhất vẫn là Read + Write; hai cách trên là bước thực tế cần thử trước.
Thực tế 11/2026 Exam guide v1.0 liệt kê Grep và Glob trong nhóm built-in tool, và đó vẫn là đáp án đề thi. Tài liệu tools reference hiện ghi Glob và Grep không có sẵn mặc định trên macOS, Linux và WSL: Claude tìm file và nội dung bằng find, grep qua tool Bash. Subagent vẫn có thể nhận Glob và Grep khi hội thoại chính không có. Nguồn: code.claude.com/docs/en/tools-reference, sub-agents.

10. Chọn cách mở rộng

CCDV-F D8 CCAR-P D3

Hình dung đời thường
Cần sửa nhà: việc nhỏ dùng dụng cụ có sẵn trong nhà (built-in). Cần một dụng cụ riêng cho nhà bạn thì tự chế (custom tool). Có quy trình hay lặp lại thì viết thành sổ tay (skill). Cần dùng dịch vụ bên ngoài thì gọi qua ổ cắm chuẩn (MCP). Muốn tặng cả bộ cho nhiều nhà thì đóng thành hộp (plugin).
CáchKhi nào
Built-in toolĐọc, ghi, tìm file, chạy lệnh: dùng trước tiên
Custom toolHàm riêng trong ứng dụng của bạn
SkillĐóng gói quy trình hoặc kiến thức lặp lại (deploy, checklist review); chỉ nạp khi cần
MCP serverNối hệ thống ngoài, dùng lại cho nhiều ứng dụng, bảo trì độc lập
PluginGói nhiều skill, hook, MCP để cài cho nhiều dự án

Về cách nối: GitHub, Notion, Slack, Figma, Postgres, Playwright thường qua MCP; git, docker, aws, psql qua shell; Obsidian, Jupyter qua đọc ghi file (ghi chú 15 tổ hợp Claude Code).

Mỗi skill, plugin, MCP server chạy với quyền của bạn và chiếm chỗ trong context. Chỉ cài thứ giải quyết vấn đề thật; kiểm tra tác giả và mã nguồn, số sao không phải bảo chứng an toàn (ghi chú 30 thứ nên cài).
Bẫy. Viết MCP server cho một hàm chỉ ứng dụng của bạn dùng (chỉ cần custom tool), hoặc nhồi quy trình dài vào CLAUDE.md thay vì skill nạp khi cần.
Thực tế 11/2026 Skill cung cấp kiến thức và quy trình, không tự cung cấp đường truy cập. Trên Claude API, skill chạy trong container của code execution tool, không có mạng và không cài thêm package được. Viết skill mô tả kỹ một hệ thống nội bộ không giúp Claude gọi được hệ thống đó; cần custom tool hoặc MCP server chạy ở nơi với tới được hệ thống. Trong Claude Code thì skill có quyền mạng như mọi chương trình trên máy. Skill cũng không tự đồng bộ giữa claude.ai, API và Claude Code. Nguồn: platform.claude.com/docs/en/agents-and-tools/agent-skills/overview.
