2. Introduction to Evals — 4 bài

CCDV-F D2 CCDV-F D4 CCAR-P D4

Hình dung đời thường
Giáo viên ra một bộ đề kiểm tra có đáp án chuẩn. Mỗi lần đổi cách dạy (prompt), thầy cho học sinh làm lại cùng bộ đề rồi chấm điểm. Nếu điểm tăng thì cách dạy mới tốt hơn. Nếu không có bộ đề cố định, thầy chỉ “cảm thấy” lớp giỏi lên, và có thể sai.

2.1 Why Evals Matter (Bài 1)

Eval = cơ chế đo lường chất lượng response của Claude một cách có hệ thống. Không có evals, bạn không biết liệu prompt thay đổi có cải thiện hay làm xấu đi kết quả. Quy tắc: iterate prompt trước, upgrade model sau — thường cải thiện prompt hiệu quả hơn và rẻ hơn nhiều so với chuyển sang model mạnh hơn.

Quy trình 5 bước chọn model và tối ưu:

  1. Xác định tiêu chí chất lượng (accuracy floor)
  2. Viết test cases vào golden dataset
  3. Chọn grader phù hợp (code/LLM/human)
  4. Iterate prompt cho đến khi vượt accuracy floor
  5. Chỉ khi đó mới xem xét upgrade model
Thuật ngữ
Golden dataset
Bộ test case chuẩn: mỗi dòng có input, đáp án mong đợi và rubric.
Accuracy floor
Ngưỡng accuracy thấp nhất chấp nhận được.
Grader
Thứ chấm điểm một câu trả lời: code, LLM hoặc người.
Rubric
Tiêu chí chấm viết thành lời, ví dụ “câu trả lời phải nêu mã đơn”.
Sai
  • Thấy kết quả chưa ổn thì đổi ngay sang model mạnh nhất
  • Sửa prompt rồi “thấy tốt hơn” mà không đo
Đúng
  • Đặt ngưỡng, đo bằng golden dataset, sửa prompt đến khi vượt ngưỡng
  • Chỉ nâng model khi prompt đã tối ưu mà vẫn không đạt

2.2 Building Your First Eval (Bài 2)

Cấu trúc eval đơn giản: golden dataset + grader + run loop.

import anthropic
import json

client = anthropic.Anthropic()

# Golden dataset — input + expected output + rubric
with open("golden.json") as f:
    test_cases = json.load(f)
# Format: [{"input": "...", "expected": "...", "rubric": "..."}]

def run_eval(test_cases: list, grader_model="claude-haiku-4-5") -> dict:
    results = []
    for case in test_cases:
        # Chạy model cần test
        response = client.messages.create(
            model="claude-sonnet-5",
            max_tokens=1024,
            system=SYSTEM_PROMPT,
            messages=[{"role": "user", "content": case["input"]}]
        )
        actual = response.content[0].text

        # LLM grader với rubric
        grade = client.messages.create(
            model=grader_model,
            max_tokens=100,
            system="You are an evaluator. Answer only PASS or FAIL.",
            messages=[{"role": "user", "content": f"""
Rubric: {case['rubric']}
Expected: {case['expected']}
Actual: {actual}
Does the actual response satisfy the rubric? Answer PASS or FAIL."""}]
        )
        passed = "PASS" in grade.content[0].text.upper()
        results.append({"input": case["input"], "passed": passed, "actual": actual})

    total = len(results)
    passing = sum(1 for r in results if r["passed"])
    return {"accuracy": passing / total, "results": results}

report = run_eval(test_cases)
print(f"Accuracy: {report['accuracy']:.1%}")  # target: > 80%

Đọc code theo thứ tự: nạp golden.json; với mỗi case, gọi model cần test, rồi gọi grader (grader_model, mặc định claude-haiku-4-5) với rubric; "PASS" in …upper() đổi chữ trả về thành true hoặc false; cuối cùng chia số case đạt cho tổng số.

Bẫy. Để grader nói tự do. Hãy ép grader chỉ trả PASS hoặc FAIL (system prompt và max_tokens nhỏ như trong ví dụ), vì câu trả lời dài khó chuyển thành số.

2.3 Grader Types và CI Evals (Bài 3–4)

Hình dung đời thường
Chấm bài thi: câu trắc nghiệm thì máy quét chấm tức thì (code grader). Bài luận thì cần giáo viên đọc (LLM hoặc người). Bài quan trọng cuối kỳ thì thầy chủ nhiệm xem lại (human). Rẻ và nhanh để kiểm tra mỗi ngày, đắt và chậm để kiểm tra kỹ.
GraderKhi nào dùngChi phí
Code graderOutput có cấu trúc (JSON, SQL, code)Rất thấp
LLM graderOpen-ended text, cần đánh giá chất lượngTrung bình
Human graderValidation cuối, edge cases, calibrationCao nhất

CI smoke eval — chạy trong GitHub Actions, chỉ dùng 10–20 test cases đại diện. Smoke test là phép thử nhanh để báo sớm có gì hỏng, không cần chạy hết bộ dữ liệu:

# .github/workflows/eval.yml
name: Smoke Eval
on: [push, pull_request]
jobs:
  eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run smoke eval
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: python scripts/smoke_eval.py --threshold 0.80

Chú giải: on: [push, pull_request] chạy mỗi khi có commit hoặc PR. Khóa API lấy từ secrets của GitHub, không ghi vào file. --threshold 0.80 là accuracy floor: dưới 80% thì script thoát lỗi và job đỏ.

Batch API cho nightly eval đầy đủ — rẻ hơn 50% so với gọi thẳng:

batch = client.messages.batches.create(requests=[
    {"custom_id": f"case-{i}", "params": {
        "model": "claude-sonnet-5", "max_tokens": 1024,
        "messages": [{"role": "user", "content": case["input"]}]
    }}
    for i, case in enumerate(full_test_cases)
])
# Poll cho đến khi xong, rồi đọc kết quả
while batch.processing_status != "ended":
    batch = client.messages.batches.retrieve(batch.id)

for result in client.messages.batches.results(batch.id):
    if result.result.type == "succeeded":
        process(result.custom_id, result.result.message)
    else:
        log_error(result.custom_id, result.result.error)

Mỗi request trong batch có một custom_id riêng (ở đây case-0, case-1…) để ghép kết quả về đúng case, vì kết quả có thể trả về không theo thứ tự.

Thực tế 11/2026 Trang Batch hiện hành ghi bốn loại kết quả cho mỗi request: succeeded, errored, canceled, expired (batch hết hạn sau 24 giờ), và request_counts đếm số request đang xử lý cùng từng loại kết quả. Chỉ errored có thông tin lỗi, nên nhánh else trong ví dụ chỉ đúng khi bạn kiểm tra thêm loại. Vòng while ở trên nên có sleep giữa hai lần hỏi. Nguồn: Batch processing.
Nightly drift sampling: Run 100 random real requests mỗi đêm qua batch eval để detect khi model update làm thay đổi behavior mà không có thay đổi prompt.

Drift
Hành vi đổi dần theo thời gian dù bạn không sửa gì, ví dụ do model được cập nhật.
Baseline
Mức điểm chuẩn để so sánh các lần chạy sau.
Sai

  • Chỉ dùng LLM grader cho output JSON
Đúng

  • Output có cấu trúc thì dùng code grader: rẻ và chắc

3. Claude Code in Action — 9 bài

CCAR-F D3 CCDV-F D2 CCDV-F D3

Hình dung đời thường
Một thợ phụ mới vào xưởng. Bạn bảo anh ta: “Vẽ phương án trước, chưa được đụng dụng cụ” (plan mode). Bạn dán nội quy lên tường (CLAUDE.md). Có một bảo vệ ở cửa kho kiểm tra phiếu trước khi cho lấy đồ (hooks). Và bạn quy định mức độ anh được tự quyết (permission modes). Nếu anh làm sai, bạn bấm “quay lại” (rewind).

3.1 Plan Mode, Compact, Rewind (Bài 1–2)

Plan mode: Nhấn Shift+Tab (hoặc gõ /plan) để bật — Claude đọc/phân tích nhưng không viết code. Dùng để review kế hoạch trước khi thực thi. Nhấn lại để tắt.

Compact conversation: Dùng /compact khi context đầy — Claude tóm tắt lịch sử hội thoại, giải phóng context window. Có thể truyền custom summary prompt: /compact Focus on the database schema changes.

Rewind: Nếu Claude đi sai hướng, nhấn Escape để dừng, sau đó dùng /rewind để quay về checkpoint trước. Checkpoint tạo tự động trước mỗi bước quan trọng.

Thực tế 11/2026 Tài liệu hiện hành mô tả Shift+Tab là phím xoay vòng các permission mode (default, acceptEdits, plan, rồi auto nếu có), và khởi động thẳng vào plan bằng claude --permission-mode plan. Checkpoint được tạo trước mỗi prompt bắt đầu một lượt; /rewind (bí danh /undo) hoặc nhấn Esc hai lần mở menu gồm: khôi phục code và hội thoại, chỉ hội thoại, chỉ code, hoặc “Summarize”. File chỉ bị đổi bởi lệnh Bash không được theo dõi, vì vậy checkpoint không thay thế git. Chưa tìm thấy lệnh /plan trong trang tài liệu đã tra; vẫn giữ theo bài giảng. Nguồn: Permission modes, Checkpointing.

3.2 CLAUDE.md Hierarchy (Bài 3)

Hình dung đời thường
Nội quy có nhiều tầng: nội quy tập đoàn, nội quy chi nhánh, nội quy riêng của phòng ban, và ghi chú cá nhân của bạn. Khi làm việc ở phòng nào, bạn đọc các tầng liên quan. CLAUDE.md cũng vậy: Claude đọc nhiều file nội quy theo vị trí.

CLAUDE.md được load từ bốn vị trí, theo thứ tự ưu tiên:

  1. ~/.claude/CLAUDE.md — global, áp dụng mọi project
  2. {project-root}/CLAUDE.md — project-level (committed vào git)
  3. {subdirectory}/CLAUDE.md — subdirectory scope (chỉ áp dụng khi làm việc trong thư mục đó)
  4. .claude/CLAUDE.md — không committed, settings cá nhân trong project

Dùng /init để tạo CLAUDE.md từ codebase analysis tự động. Two-strikes rule: sửa một lỗi lần đầu tay; nếu xảy ra lần thứ hai, thêm vào CLAUDE.md ngay.

Thực tế 11/2026 Tài liệu hiện hành chia khác bài giảng. Có thêm bản managed policy cho cả tổ chức (macOS /Library/Application Support/ClaudeCode/CLAUDE.md, Linux /etc/claude-code/CLAUDE.md). Chỗ ghi cá nhân, không commit là ./CLAUDE.local.md (nên thêm vào .gitignore), còn ./.claude/CLAUDE.md được tính là vị trí project, dùng chung qua git như ./CLAUDE.md. Các file được nối vào context (không ghi đè nhau), và file gần thư mục làm việc được đọc sau cùng. File trong thư mục con chỉ nạp khi Claude đọc hoặc sửa file ở đó. Nên giữ mỗi file dưới khoảng 200 dòng. CLAUDE.md là chỉ dẫn, không phải cơ chế ép buộc; muốn chặn chắc chắn thì dùng hook PreToolUse. Đề thi vẫn theo bốn vị trí như bài. Nguồn: Memory.
Sai
  • Lỗi lặp lại lần hai mà vẫn nhắc bằng lời mỗi phiên
  • Nhồi quy trình dài, ít dùng vào CLAUDE.md
Đúng
  • Lần hai gặp lỗi thì thêm một dòng cụ thể vào CLAUDE.md

3.3 Hooks và Permissions (Bài 4–5)

Hình dung đời thường
Cổng kiểm soát ở kho hàng. Bảo vệ nhận phiếu lấy hàng, xem xét, rồi làm một trong ba việc: vẫy tay cho qua (exit 0), nhắc nhở nhưng vẫn cho qua (exit 1), hoặc chặn lại và nói lý do (exit 2). Chỉ có “chặn lại” mới thật sự giữ hàng ở trong kho.

Hooks = shell script chạy trước/sau khi Claude dùng tool. Cấu hình trong .claude/settings.json:

{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{
        "type": "command",
        "command": "node scripts/safety-check.js"
      }]
    }]
  }
}

Hook nhận tool input qua stdin (JSON), có thể:

  • Allow: thoát với exit code 0, không output gì
  • Block: thoát với exit code 2 + output lý do — exit 1 KHÔNG block, chỉ exit 2 mới block
  • Ask: output JSON {"permissionDecision": "ask", "message": "..."}
#!/bin/bash
# hooks/redact-secrets.sh — hook PreToolUse để redact PII trước khi log
INPUT=$(cat)
TOOL=$(echo "$INPUT" | jq -r '.name')
if [ "$TOOL" = "Bash" ]; then
    COMMAND=$(echo "$INPUT" | jq -r '.input.command')
    # Check for secret patterns
    if echo "$COMMAND" | grep -qE "(password|secret|token|key)="; then
        echo '{"permissionDecision":"ask","message":"Command contains potential secrets. Review before proceeding."}'
        exit 0
    fi
fi
exit 0

Script này đọc JSON từ stdin, lấy tên tool và lệnh. Nếu lệnh Bash chứa mẫu như password= hoặc token=, nó in JSON “ask” rồi exit 0: Claude Code sẽ hỏi bạn trước khi chạy. Ngược lại nó thoát 0 và không in gì, tức cho qua.

Permission modes: default (hỏi mọi thứ), auto-approve (approve mọi thứ), bypassPermissions (developer mode — không hỏi gì cả, chỉ dùng trong CI với môi trường sandboxed).

Bẫy. Viết hook chặn nhưng dùng exit 1. Hook báo lỗi, nhưng lệnh vẫn chạy. Muốn chặn phải exit 2.
Thực tế 11/2026 Tài liệu hooks hiện hành xác nhận: exit 2 là cách chặn; mọi mã khác (kể cả 1) là “non-blocking error”, hành động vẫn đi tiếp. Muốn trả quyết định bằng JSON thì phải thoát exit 0; nếu thoát 2 thì JSON allow cũng không mở được cổng. JSON đầu vào của hook dùng khóa tool_name và tool_input (ví dụ tool_input.command), khác với .name và .input.command trong ví dụ trên. Về permission mode, tài liệu liệt kê: default, acceptEdits, plan, auto, dontAsk, bypassPermissions; bypassPermissions chỉ nên dùng trong container hoặc VM cô lập. Đề thi theo ba mode như bài. Nguồn: Hooks reference, Permission modes.

Bộ lọc chọn hook áp dụng cho tool nào, ví dụ Bash hoặc Edit.

Kênh vào chuẩn và kênh lỗi chuẩn của một chương trình.

3.4 Scheduled Tasks và Headless Mode (Bài 6–7)

Hình dung đời thường
Máy giặt hẹn giờ: bạn bỏ đồ vào, bấm nút, máy tự chạy lúc 6 giờ sáng mà không cần bạn đứng cạnh. Headless mode là Claude Code chạy “không màn hình”, không hỏi gì giữa chừng. Scheduled task là hẹn giờ cho nó.

Headless mode: chạy Claude Code không tương tác — dùng trong scripts, CI, cron jobs.

# -p: prompt text
# --bare: output chỉ content (không có markdown formatting)
# --output-format json: machine-readable output
claude -p "Review these test failures and suggest fixes" \
       --input-file test-results.txt \
       --bare \
       --output-format json > review.json

# Chạy từ Agent SDK (Python)
result = subprocess.run(
    ["claude", "-p", task_description, "--bare"],
    capture_output=True, text=True, cwd=project_dir
)

Scheduled tasks: Dùng /schedule command trong Claude Code (hoặc claude schedule create) để tạo cloud-hosted cron job. Cũng có thể dùng GitHub Actions với schedule trigger.

Cron là cách viết lịch lặp bằng năm trường: phút, giờ, ngày trong tháng, tháng, thứ. Ví dụ 0 9 * * 1-5 là 9 giờ sáng các ngày trong tuần.

Thực tế 11/2026 Trang tài liệu hiện hành mô tả --bare theo nghĩa khác bài: nó bỏ qua việc tự nạp hook, skill, subagent, plugin, MCP server, auto memory và CLAUDE.md để chạy giống nhau trên mọi máy; không phải “chỉ in nội dung”. Dạng gọi là claude --bare -p "…", và bare mode không dùng đăng nhập subscription nên cần ANTHROPIC_API_KEY. Đưa dữ liệu vào bằng pipe stdin (cat file | claude -p "…"), tôi chưa thấy cờ --input-file trong trang đã tra. Về lịch chạy, tài liệu liệt kê cloud scheduled tasks (routines), Desktop scheduled tasks, /loop trong phiên, và GitHub Actions; tôi chưa kiểm chứng được lệnh /schedule hay claude schedule create. Nguồn: Headless, Scheduled tasks.
Sai
  • Chạy claude tương tác trong cron job rồi chờ nó hỏi quyền
  • Dùng bypassPermissions trên máy làm việc thật
Đúng
  • Dùng -p và --output-format json để script đọc được kết quả
  • bypassPermissions chỉ trong CI sandboxed

3.5 GitHub Actions Integration (Bài 8–9)

Hình dung đời thường
Mỗi khi ai đó nộp bài (mở pull request), một người chấm tự động được gọi tới, đọc bài, rồi ghi nhận xét lên chính tờ bài. Bạn không phải nhắc. GitHub Actions là chuông báo, Claude là người chấm. 
# .github/workflows/claude-review.yml
name: Claude Code Review
on:
  pull_request:
    types: [opened, synchronize]

jobs:
  review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Claude Code Review
        uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          github_token: ${{ secrets.GITHUB_TOKEN }}
          review_type: "security,performance,correctness"
          post_as_comment: true

Claude Code Review service: Anthropic-hosted service có thể trigger qua GitHub App — không cần tự host. Cấu hình qua CLAUDE.md trong repo hoặc review-specific settings.

Thực tế 11/2026 Trang GitHub Actions hiện hành dùng các input anthropic_api_key (hoặc claude_code_oauth_token), prompt và claude_args; chưa thấy review_type và post_as_comment trong tài liệu đã tra. Workflow mẫu hiện dùng actions/checkout@v6 và id-token: write cho xác thực GitHub App mặc định. Khi workflow có prompt, Claude chạy ở chế độ automation; không có prompt thì chờ nhắc @claude. Trang này cũng tách “Code Review” (review tự động, không viết workflow) thành sản phẩm riêng. Ví dụ ở trên vẫn giữ theo bài giảng. Nguồn: Claude Code GitHub Actions.
Bẫy. Dán API key thẳng vào file workflow. Luôn dùng ${{ secrets.… }}, và cấp permissions vừa đủ.

4. AI-Native SDLC Playbook — 14 bài

CCDV-F D2 CCAR-F D3 CCAR-P D7 Phần lớn playbook (intent.md, worktree song song) là nâng cao; đề chỉ hỏi vòng đời và review.

Hình dung đời thường
Xây một căn nhà. Có kiến trúc sư, thợ xây, người kiểm tra chất lượng, và chủ nhà ký nhận. Máy móc làm phần nặng và lặp lại, nhưng chủ nhà vẫn giữ quyền quyết định ở những điểm quan trọng: bản vẽ cuối, nghiệm thu, bàn giao. AI-native SDLC chia việc kiểu đó giữa AI và người.

4.1 AI-Native SDLC: 6 Giai đoạn (Bài 1–2)

Giai đoạnAI roleHuman role
1. Intent clarificationHỏi làm rõ, tóm tắt requirementsViết intent.md, review tóm tắt
2. Architecture planningĐề xuất kiến trúc, tradeoff analysisQuyết định, sign-off
3. ImplementationViết code, test, debugReview PR, check edge cases

4.2 Intent.md và CLAUDE.md /init (Bài 3–4)

Hình dung đời thường
Trước khi thuê thợ, bạn viết một tờ giấy: muốn gì, không được làm gì, thế nào là xong. Thợ đọc tờ giấy đó thay vì đoán ý bạn mỗi lần hỏi lại. intent.md là tờ giấy ấy.

intent.md: Viết trước khi bắt đầu task phức tạp — mô tả mục tiêu, constraints, success criteria. Đặt trong project root hoặc task-specific folder. Claude sẽ tham chiếu khi cần clarification.

# Intent: Migrate auth system to JWT

## Goal
Replace session-based auth with stateless JWT tokens.

## Constraints
- Must maintain backward compatibility during rollout
- Zero downtime migration
- Keep existing user sessions valid for 24h after cutover

## Success Criteria
- All existing tests pass
- Login time < 200ms p99
- No auth-related errors in first 24h post-deploy

Ba phần: Goal (việc cần đạt), Constraints (điều không được vi phạm), Success Criteria (đo được để biết đã xong). Ví dụ p99 < 200ms nghĩa là 99% lượt đăng nhập phải dưới 200 mili giây.

/init workflow: Chạy /init trong project mới → Claude đọc codebase → tạo CLAUDE.md với stack summary, commands, và conventions. Two-strikes rule: lần đầu sửa tay, lần thứ hai thêm vào CLAUDE.md.

Sai
  • “Chuyển auth sang JWT” và để Claude tự đoán ràng buộc
  • Success criteria mơ hồ: “chạy tốt”
Đúng
  • Viết goal, constraints (zero downtime, tương thích ngược) và success criteria đo được
  • Đặt intent.md ở project root để Claude tham chiếu

4.3 Parallel Worktrees và Verifier Subagent (Bài 5–7)

Hình dung đời thường
Hai thợ cùng sửa một căn nhà. Nếu cùng đứng trong một phòng, họ vướng nhau. Cho mỗi người một phòng riêng (worktree) thì không đụng nhau. Sau khi thợ xong, một người kiểm tra mới đến (verifier) soi lại, vì người chưa từng thấy lúc thi công sẽ ít bị thiên vị hơn.

Parallel worktrees: Dùng git worktree add để nhiều instance Claude Code làm việc song song trên cùng repo mà không conflict:

git worktree add ../feature-auth feature/auth-migration
git worktree add ../feature-tests feature/test-improvements
# Mỗi worktree có thư mục riêng, branch riêng

Verifier subagent pattern: Sau khi implementation subagent xong, spawn verifier subagent để review độc lập — có fresh context, không bị bias bởi implementation decisions.

---
name: code-verifier
description: Verify implementation correctness after changes. Use when implementation is complete and needs independent review.
tools: Bash, Glob, Grep, Read
model: sonnet
---
Review the implementation for:
1. All acceptance criteria from intent.md are met
2. No security vulnerabilities introduced
3. Tests cover happy path and error cases
4. Performance implications considered

Report: APPROVED or NEEDS_REVISION with specific issues.

Chú giải phần đầu file: name là tên subagent; description cho Claude biết khi nào nên gọi nó; tools giới hạn tool được dùng (không có Edit, nên verifier không tự sửa code); model: sonnet chọn model. Phần sau dấu --- là chỉ dẫn gửi cho subagent.

Thực tế 11/2026 Claude Code hiện có cờ claude --worktree <tên> (hoặc -w) tạo worktree trong .claude/worktrees/<tên>/ trên branch worktree-<tên>, và subagent có thể chạy trong worktree riêng bằng isolation: worktree trong frontmatter. Worktree mới là bản checkout sạch nên cần cài dependency lại. Nguồn: Worktrees.
Thuật ngữ
Git worktree
Một thư mục làm việc thêm của cùng repo, có branch riêng.
Subagent
Một Claude phụ chạy việc riêng với context riêng.
Fresh context
Context trống, chưa thấy quá trình làm việc trước, nên đánh giá độc lập.
Bias
Thiên lệch: người làm ra thường khó thấy lỗi của chính mình.

4.4 Hooks như Approval Gates (Bài 8–10)

Hình dung đời thường
Cửa kiểm soát có khóa từ: dù nhân viên quên hay muốn bỏ qua, cửa không mở nếu chưa quét thẻ. Quy tắc viết trong tài liệu có thể bị quên. Quy tắc nằm trong hook thì máy tự ép thực hiện.

Dùng hooks để enforce workflow steps — không thể skip, không thể bypass:

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{
          "type": "command",
          "command": "scripts/check-test-pass.sh"
        }]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Edit",
        "hooks": [{
          "type": "command",
          "command": "scripts/auto-lint.sh"
        }]
      }
    ]
  }
}
#!/bin/bash
# check-test-pass.sh — block deploy nếu tests chưa pass
INPUT=$(cat)
COMMAND=$(echo "$INPUT" | jq -r '.input.command')
if echo "$COMMAND" | grep -q "deploy\|push"; then
    if ! npm test --silent 2>/dev/null; then
        echo "Tests must pass before deploying" >&2
        exit 2  # exit 2 = block action
    fi
fi
exit 0

Đọc từng bước: hook PreToolUse với matcher Bash chạy check-test-pass.sh trước mọi lệnh Bash. Nếu lệnh chứa deploy hoặc push và npm test thất bại, script ghi lý do ra stderr rồi exit 2, nên lệnh bị chặn (xem lại Hình 6). Hook PostToolUse với matcher Edit chạy auto-lint.sh sau mỗi lần sửa file.

Exit codes quan trọng: exit 0 = allow, exit 1 = warning (KHÔNG block), exit 2 = block. Nhiều người nhầm exit 1 với block — nó không block!
Sai
  • Viết “luôn chạy test trước khi deploy” trong CLAUDE.md và tin là đủ
  • exit 1 trong hook chặn
Đúng
  • Dùng hook PreToolUse để ép bước test, vì hook chạy chắc chắn
  • exit 2 kèm lý do ở stderr

4.5 Managed Settings cho Regulated Enterprises (Bài 11–14)

Hình dung đời thường
Một ngân hàng có quy định bảo mật chung do trụ sở đặt. Chi nhánh và từng nhân viên có thể chỉnh vài thứ nhỏ, nhưng các quy định an ninh thì không ai sửa được. Managed settings là bộ quy định từ trụ sở cho Claude Code.

Enterprise quản lý Claude Code settings tập trung qua managed settings files:

  • macOS: /Library/Application Support/ClaudeCode/managed-settings.json
  • Linux: /etc/claude-code/managed-settings.json
  • Windows: C:\ProgramData\ClaudeCode\managed-settings.json

Managed settings override user settings cho security-sensitive fields. Dùng MDM (Jamf, Intune) để deploy. Có thể pre-load skills và CLAUDE.md trên toàn tổ chức.

Thực tế 11/2026 Trang managed settings hiện hành ghi đường dẫn Windows là C:\Program Files\ClaudeCode\managed-settings.json và nói rõ Claude Code không còn đọc đường dẫn cũ C:\ProgramData\ClaudeCode\managed-settings.json. macOS và Linux giữ nguyên như bài. Ngoài file còn có server-managed settings (từ admin console claude.ai) và MDM, có thể kèm thư mục managed-settings.d/ để chia policy cho nhiều đội. Đề thi theo bài giảng. Nguồn: Managed settings.
Thuật ngữ
MDM
Mobile Device Management: công cụ quản trị đẩy cấu hình xuống nhiều máy (Jamf, Intune).
Regulated enterprise
Tổ chức chịu quy định chặt như tài chính, y tế, nên cần kiểm soát tập trung.

5. Lưu ý ôn thi

Hình dung đời thường
Trước giờ thi, bạn ghi ra một tờ nhớ nhanh những chỗ dễ nhầm nhất. Ở bài này, chỗ nhầm nổi tiếng nhất là cái “bảo vệ” (exit code): chỉ một mã duy nhất thật sự chặn cổng.
CCAR-F D3 (20%) – hooks: Nhớ: exit 2 block, exit 1 không block. PreToolUse cho enforcement. permissionDecision: allow/deny/ask. Phân biệt permission modes. CLAUDE.md hierarchy (4 vị trí). Two-strikes rule.
CCDV-F D4 (2,6%) – evals: 5 bước chọn model, 3 loại grader, batch API (custom_id, request_counts), nightly drift sampling. Iterate prompt trước upgrade model.
SDLC key patterns: intent.md trước task phức tạp, parallel worktrees cho parallel work, verifier subagent cho independent review, hooks như approval gates.
