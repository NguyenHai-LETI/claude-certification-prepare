1. Gọi API: REST thô và SDK

CCDV-F D5 CCDV-F D2

Hình dung đời thường
Gửi bưu kiện có hai cách. Tự ra bưu điện: tự điền phiếu, tự dán tem, tự hỏi lại khi thất lạc. Hoặc thuê dịch vụ chuyển phát: họ điền phiếu đúng mẫu, tự gửi lại khi xe hỏng, báo bạn biết đang ở đâu. Gọi REST thô là tự ra bưu điện. Dùng SDK là thuê dịch vụ. Hàng vẫn đi cùng một con đường.

Mọi tính năng của Claude API đi qua một endpoint (địa chỉ nhận request) chính: POST https://api.anthropic.com/v1/messages. Body là JSON. Request cần ba header (dòng thông tin đi kèm request):

HeaderÝ nghĩaLỗi khi thiếu hoặc sai
x-api-keyAPI key của workspace401 authentication_error
anthropic-versionPhiên bản API, dạng ngày. Đổi phiên bản là cách Anthropic đưa ra thay đổi phá vỡ tương thích400
content-typeapplication/json400
anthropic-betaTuỳ chọn: bật tính năng beta, nhiều giá trị cách nhau bằng dấu phẩyTính năng beta không chạy

Response có header request-id (body lỗi có request_id). Ghi log mã này để báo hỗ trợ khi cần. Trên Bedrock và Vertex AI, phiên bản API nằm trong body (anthropic_version) và xác thực bằng IAM của cloud, không dùng x-api-key.

Sai
Dự án Python gọi API bằng requests cho "nhẹ", tự viết retry. Quên retry 529 và đọc retry-after, nên giờ cao điểm lỗi hàng loạt.
Đúng
Dùng SDK chính thức của ngôn ngữ đó. Chỉ gọi REST thô khi ngôn ngữ không có SDK, hoặc là script shell, cURL.

Streaming là SSE, không phải WebSocket

SSE (server-sent events) là kết nối HTTP một chiều: server đẩy từng sự kiện xuống client. WebSocket là kết nối hai chiều, giữ lâu, hai bên cùng gửi được. Streaming của Messages API dùng SSE (xem bài 01 mục Streaming). Nếu trình duyệt cần nhận chữ dần, server của bạn đọc SSE từ API rồi chuyển tiếp xuống trình duyệt bằng SSE hoặc WebSocket tuỳ kiến trúc. API key luôn ở server.

Cốt lõi. SDK bọc REST API và lo retry, timeout, kiểu dữ liệu, streaming. Dùng SDK mặc định. API key không bao giờ nằm trong code chạy ở trình duyệt hay app di động.
Bẫy. "Mở WebSocket tới api.anthropic.com để stream" là tính năng không tồn tại. "Gọi API thẳng từ frontend cho nhanh" làm lộ key.
Thực tế 11/2026 Phiên bản API mới nhất là 2026-10-21; ở phiên bản này request gửi temperature, top_p, top_k bị trả 400. SDK đời mới tự gửi phiên bản tương ứng. Nguồn: platform.claude.com/docs/en/api/versioning.
Thuật ngữ
Endpoint
Một địa chỉ URL của API nhận một loại request.
Header
Các dòng tên–giá trị đi kèm request hoặc response HTTP, ngoài phần body.
SSE
Server-sent events: server đẩy chuỗi sự kiện xuống client qua một kết nối HTTP.
WebSocket
Kết nối hai chiều giữ lâu giữa client và server.

2. Đếm token trước khi gửi

CCDV-F D5 CCDV-F D2

Hình dung đời thường
Trước khi gửi hàng, bạn cân bưu kiện để biết cước và biết nó có vượt cân không. Bạn không đoán bằng mắt, cũng không mượn cân của hãng khác vì mỗi hãng tính khác nhau.

Token counting là endpoint POST /v1/messages/count_tokens. Bạn gửi đúng những gì sẽ gửi cho Messages API (model, system, messages, tools, ảnh, PDF), API trả về input_tokens. Không gọi model, không sinh output.

  • Số token phụ thuộc model: mỗi đời model có thể dùng tokenizer khác. Đếm bằng đúng model sẽ chạy.
  • Không dùng tokenizer của hãng khác (ví dụ tiktoken): đếm thiếu, nhất là với code và tiếng Việt.
  • Dùng để: kiểm tra input có vừa context window không, ước tính chi phí trước khi chạy lô lớn, quyết định có cần chia nhỏ tài liệu, chặn request quá lớn từ người dùng.

Sau khi gọi, trường usage của response là số liệu thật. Có cache thì input_tokens chỉ là phần sau điểm cache cuối:

tổng input = cache_read_input_tokens + cache_creation_input_tokens + input_tokens
Sai
Ước lượng "1 token ≈ 4 ký tự" rồi cắt tài liệu theo số ký tự. Văn bản tiếng Việt và code lệch nhiều, request vẫn vượt giới hạn.
Đúng
Gọi count_tokens với đúng model và đúng nội dung; quá ngưỡng thì chia nhỏ hoặc tóm tắt trước.
Cốt lõi. Muốn biết chính xác trước khi gửi thì count_tokens; muốn biết sau khi gửi thì đọc usage. Cả hai đều theo tokenizer của model cụ thể.
Bẫy. Đọc input_tokens rồi kết luận "prompt chỉ có 50 token" khi đang dùng cache: phần lớn input nằm ở cache_read_input_tokens.
Thuật ngữ
Tokenizer
Bộ quy tắc cắt văn bản thành token. Mỗi họ model có thể khác nhau.
Context window
Tổng số token tối đa model đọc được trong một lần gọi, gồm cả input và output.

3. Rate limit và spend limit

CCDV-F D2 CCDV-F D5 CCDV-F D7

Hình dung đời thường
Một xô nước có vòi chảy vào đều đặn. Mỗi lần bạn múc là lấy bớt nước. Múc chậm thì xô luôn đầy. Múc dồn dập thì xô cạn và phải chờ vòi chảy thêm. Rate limit của Claude API hoạt động như cái xô này, gọi là token bucket.

Giới hạn đặt ở cấp tổ chức (organization), theo usage tier (bậc sử dụng, tự tăng theo lịch sử dùng và thanh toán), và tính riêng cho từng nhóm model. Có ba thước đo:

Thước đoĐếm gìLưu ý
RPMSố request mỗi phút60 RPM có thể bị áp như 1 request mỗi giây; dồn burst vẫn dính 429
ITPMInput token mỗi phútChỉ đếm input chưa cache và token ghi cache; token đọc từ cache không tính
OTPMOutput token mỗi phútĐếm token thật sinh ra; đặt max_tokens cao không bị trừ thêm

Header cho biết còn bao nhiêu

Mỗi response có các header anthropic-ratelimit-requests-*, anthropic-ratelimit-input-tokens-*, anthropic-ratelimit-output-tokens-* (đuôi -limit, -remaining, -reset). Đọc chúng để tự giảm tốc trước khi dính 429.

Ba loại "hết hạn mức" cần phân biệt

Tình huốngMãXử lý
Vượt RPM, ITPM, OTPM429, có retry-afterChờ rồi gửi lại; giảm đồng thời; cache
Ramp limit: tải tăng đột ngột dù chưa chạm hạn mức429, ramp_limit_exceededTăng tải từ từ; job hằng đêm khởi động chậm rồi tăng dần
Chạm spend cap của tier trong tháng429, không có retry-afterRetry vô ích; xin lên tier hoặc chờ tháng sau
Chạm spend limit tự đặt (tổ chức hoặc workspace)400 invalid_request_errorNâng hoặc bỏ giới hạn tự đặt

Workspace có thể đặt hạn mức thấp hơn tổ chức, để môi trường dev không ăn hết hạn mức của production. Message Batches API có hạn mức riêng (số request trong hàng đợi), không bị ramp limit.

Cốt lõi. 429 thì đọc retry-after và backoff; muốn chạy nhiều hơn thì cache, giới hạn đồng thời, rải tải, dùng Batches, rồi mới xin tier cao hơn.
Bẫy. "Giảm max_tokens để tránh vượt OTPM": OTPM đếm token thật sinh ra, không đếm max_tokens. "Retry ngay lập tức nhiều lần": làm tình trạng tệ hơn.
Thực tế 11/2026 Bảng hạn mức theo tier (Start, Build, Scale, Custom) và con số cụ thể đổi theo thời gian. Nguồn: platform.claude.com/docs/en/api/rate-limits.
Thuật ngữ
Token bucket
Thuật toán giới hạn tốc độ: hạn mức được nạp lại liên tục tới mức tối đa, thay vì đặt lại theo mốc giờ.
Usage tier
Bậc của tổ chức, quyết định hạn mức và trần chi tiêu tháng.
Spend cap
Trần chi tiêu mỗi tháng của tier.
Workspace
Nhóm con trong tổ chức, có key, hạn mức và chi tiêu riêng.

4. Thinking trong vòng lặp tool

CCDV-F D5 CCDV-F D2

Hình dung đời thường
Một thám tử ghi sổ tay trước khi đi hỏi nhân chứng. Quay về, anh ta mở lại đúng trang đó để nối suy luận cũ với lời khai mới. Nếu ai xé hoặc sửa trang sổ, anh ta mất mạch suy luận.

Khi bật thinking và có tool, response có thể gồm khối thinking rồi khối tool_use. Bạn chạy tool và gửi lại. Quy tắc quan trọng nhất: gửi lại nguyên vẹn toàn bộ content của assistant message, gồm cả khối thinking, rồi mới tới user message chứa tool_result. Khối thinking có chữ ký (signature) để API kiểm tra nó không bị sửa.

Quy tắcVì sao
Không sửa, không cắt khối thinking (và redacted_thinking ở model cũ) trong lượt tool đang chạyClaude cần mạch suy luận cũ; API kiểm tra chữ ký, khối bị sửa có thể bị bỏ hoặc gây lỗi
Thinking chỉ đi với tool_choice auto hoặc noneÉp gọi tool (any, tool) không cho model nghĩ trước khi gọi
Kiểu cũ budget_tokens phải nhỏ hơn max_tokensPhần nghĩ nằm trong output; không chừa chỗ thì không còn chỗ cho câu trả lời
Không bật hoặc tắt thinking giữa một lượt tool đang dởLượt assistant phải nhất quán từ đầu tới khi xong vòng tool
Token thinking tính như outputKể cả khi chỉ nhận bản tóm tắt hoặc phần thinking để trống

Interleaved thinking: model nghĩ xen giữa các lần gọi tool, không chỉ nghĩ một lần ở đầu. Adaptive thinking tự bật chế độ này. Phần chọn khi nào bật thinking, effort, chi phí xem bài 02 mục Thinking.

Sai
Để tiết kiệm token, ứng dụng chỉ giữ khối text và tool_use của assistant, bỏ khối thinking trước khi gửi tool_result.
Đúng
Nối nguyên response.content vào lịch sử. Muốn giảm token thì dùng context editing để xoá thinking cũ của các lượt đã xong.
Cốt lõi. Thinking cộng tool: giữ nguyên content của assistant, tool_choice chỉ auto hoặc none, thinking tính như output.
Bẫy. "Ép tool_choice về một tool cụ thể trong khi vẫn bật extended thinking" để vừa chắc chắn gọi tool vừa suy luận kỹ: hai thứ này không đi cùng nhau.
Thực tế 11/2026 Model mới (Opus 5.5, Sonnet 5.5, Fable 5.2) dùng thinking: {type: "adaptive"}, bỏ budget_tokens, và trả 400 với tool_choice any/tool dù có bật thinking hay không. Mặc định phần thinking trả về để trống (display: "omitted"); đặt "summarized" để xem bản tóm tắt. Khối thinking gắn với model và hội thoại đã sinh ra nó: sửa lịch sử phía trước làm khối đó mất hiệu lực. Nguồn: platform.claude.com/docs/en/build-with-claude/extended-thinking.
Thuật ngữ
Signature
Chuỗi mã hoá đi kèm khối thinking để API xác minh khối không bị sửa.
redacted_thinking
Khối thinking đã mã hoá (ở model cũ), không đọc được nhưng vẫn phải gửi lại nguyên vẹn.
Interleaved thinking
Model nghĩ xen giữa các lần gọi tool trong cùng một lượt.

5. Context dài: context editing, compaction, memory

CCDV-F D6

Hình dung đời thường
Bàn làm việc có ba cách giữ gọn. Dọn bỏ giấy nháp đã dùng xong (xoá). Gom chồng tài liệu cũ thành một trang tóm tắt (nén). Cất hồ sơ quan trọng vào tủ để tuần sau còn dùng (lưu trữ). Ba cách giải ba vấn đề khác nhau.

Model hiện hành có context window tới 1M token. Context lớn hơn không làm mất các vấn đề cũ: chi phí tăng theo số token gửi lại mỗi lượt, độ trễ tăng, và thông tin cũ, thừa vẫn kéo chất lượng xuống (context drift, lost in the middle; xem bài 07). API có ba công cụ:

Công cụCách bậtĐiểm phải nhớ
Context editingcontext_management.edits, betaXoá chứ không tóm tắt. Thường xoá tool result cũ nhất, giữ vài lượt gần nhất
CompactionBật phía server, betaNối cả response.content vào lịch sử, không chỉ phần chữ, vì compaction block thay cho phần đã nén ở request sau
Memory toolTool memory do Anthropic định nghĩaLà client tool: lệnh tạo, đọc, sửa, xoá file do ứng dụng của bạn thực thi; phải chặn đường dẫn ra ngoài thư mục memory
Sai
Bật compaction nhưng mỗi lượt chỉ lưu response.content[0].text vào lịch sử. Phần đã nén biến mất, Claude quên hết đầu hội thoại.
Đúng
Lưu nguyên mảng response.content, gồm cả compaction block, rồi gửi lại ở lượt sau.
Cốt lõi. Context editing và compaction làm gọn trong một hội thoại; memory giữ thông tin giữa các phiên. Context 1M không thay được việc giữ context gọn.
Bẫy. "Chuyển sang model có context lớn hơn" để chữa việc agent trả lời sai sau nhiều lượt: vấn đề là thông tin cũ gây nhiễu, không phải thiếu chỗ.
Thực tế 11/2026 Context editing dùng beta context-management-2025-06-27 với chiến lược clear_tool_uses_20250919, clear_thinking_20251015; compaction dùng beta compact-2026-01-12, ngưỡng mặc định 150K token; memory tool có type memory_20250818. Haiku 4.5 vẫn là 200K. Nguồn: docs về context editing, compaction, memory tool trên platform.claude.com.
Thuật ngữ
Compaction block
Khối nội dung chứa bản tóm tắt API tạo ra, thay cho phần đầu hội thoại đã nén.
Context drift
Chất lượng trả lời trượt dần khi hội thoại dài và nhiều thông tin cũ.

6. Citations và search_result

CCDV-F D2

Hình dung đời thường
Báo cáo nghiêm túc có chú thích chân trang: câu này lấy từ trang mấy của tài liệu nào. Người đọc lật lại kiểm được ngay. Citations làm việc đó tự động cho câu trả lời của Claude.

Gửi tài liệu trong khối document (PDF, văn bản, nội dung tự tạo) và đặt citations: {enabled: true} trên mọi khối tài liệu. Câu trả lời được tách thành nhiều khối text; khối nào dựa vào tài liệu thì có mảng citations:

TrườngNghĩa
cited_textĐoạn trích nguyên văn từ tài liệu
document_index, document_titleTài liệu nào
char_location / page_location / content_block_locationVị trí: theo ký tự (văn bản), theo trang (PDF), theo khối (nội dung tự tạo)

search_result là loại content block để đưa kết quả tìm kiếm của chính bạn (hệ RAG, tìm trong kho nội bộ) cho Claude, có source, title, nội dung, và bật được citations. Tool tìm kiếm của bạn trả về các khối search_result trong tool_result; câu trả lời có trích nguồn giống như web search của Anthropic.

Sai
Dặn trong prompt "hãy trích nguyên văn và ghi số trang", rồi tự viết regex tách trích dẫn. Model có thể trích sai hoặc bịa số trang.
Đúng
Bật citations: API trả vị trí trích dẫn có cấu trúc, ứng dụng hiển thị và kiểm tra được.
Cốt lõi. Cần câu trả lời kiểm chứng được theo nguồn thì bật citations trên khối document, hoặc trả search_result từ tool tìm kiếm của mình.
Bẫy. Citations không dùng chung với structured output (output_config.format): bật cả hai bị 400. Cần cả JSON lẫn trích dẫn thì tách hai bước.
Thực tế 11/2026 Từ phiên bản API 2026-10-21, không được gửi khối text có mảng citations khác rỗng trong user message (kể cả khi lồng trong search_result hay tool_result); bỏ trường citations, giữ chữ. Nguồn: platform.claude.com/docs/en/build-with-claude/citations.
Thuật ngữ
RAG
Retrieval-augmented generation: tìm tài liệu liên quan rồi đưa vào prompt để model trả lời dựa trên đó.
Content block
Một phần tử trong mảng content của message: text, image, document, tool_use, tool_result…

7. Dữ liệu, vùng xử lý, mức dịch vụ, quản trị tổ chức

CCDV-F D7

Hình dung đời thường
Thuê kho cho doanh nghiệp: bạn hỏi hàng để ở nước nào, kho giữ hàng bao lâu, có làn ưu tiên khi cao điểm không, và ai giữ chìa khoá tổng. Dùng Claude API cho doanh nghiệp cũng phải trả lời đúng mấy câu đó.
Nhu cầuCông cụGhi nhớ

Sai
Một API key dùng chung cho dev, staging, prod. Đặt Admin key trong biến môi trường của ứng dụng để "tiện quản lý".
Đúng
Mỗi môi trường một workspace, một key; spend limit cho dev. Admin key chỉ ở công cụ quản trị, quyền tối thiểu, xoay vòng định kỳ.
Cốt lõi. Yêu cầu về lưu trữ dữ liệu, vùng xử lý, độ sẵn sàng và tách môi trường đều có công cụ riêng ở cấp tổ chức; trả lời bằng công cụ đó, không bằng lời dặn trong prompt.
Bẫy. "Thêm vào system prompt: không lưu dữ liệu này" không phải biện pháp kiểm soát dữ liệu. Chính sách lưu trữ được đặt bằng thoả thuận và cấu hình tổ chức.
Thực tế 11/2026 Một số model (Fable 5.x) yêu cầu lưu trữ 30 ngày; tổ chức đặt ZDR gọi tới các model này bị 400. Priority Tier không hỗ trợ một số model mới nhất. Admin API (beta) có thêm nhóm RBAC và spend limit. Nguồn: docs về data retention, service tiers, Admin API trên platform.claude.com.
Thuật ngữ
ZDR
Zero Data Retention: thoả thuận Anthropic không lưu nội dung request và response sau khi xử lý.
Data residency
Yêu cầu dữ liệu được xử lý hoặc lưu trong một vùng địa lý nhất định.
Service tier
Mức dịch vụ của request: standard, priority, batch.

8. MCP connector trong Messages API

CCDV-F D8

Hình dung đời thường
Bạn cần một tài liệu ở thư viện. Cách một: tự đi lấy rồi đưa cho trợ lý. Cách hai: đưa thẻ thư viện cho trợ lý để họ tự đi. Cách hai ít việc hơn, nhưng chỉ làm được khi thư viện mở cửa công khai và bạn tin cách trợ lý dùng thẻ.

Có hai cách dùng MCP server với Claude API:

MCP connector cần hai nửa trong cùng request: danh sách mcp_servers (type: "url", url, name, tuỳ chọn authorization_token) và một mục {"type": "mcp_toolset", "mcp_server_name": …} trong tools, kèm beta header mcp-client-….

Duyệt từng lời gọi tool trước khi chạyỨng dụng tự chặnHạn chế

Xác thựcỨng dụng tự loOAuth access token bạn lấy trước, gửi qua authorization_token
Cốt lõi. Server từ xa công khai, chỉ cần tool, muốn ít code: MCP connector. Server local, mạng nội bộ, cần resource hoặc cần duyệt từng lời gọi: MCP phía client.
Bẫy. Khai báo mcp_servers mà quên mục mcp_toolset trong tools (bị lỗi validate). Token của server đặt quyền rộng hơn cần: dữ liệu trả về từ tool vẫn là input không tin cậy.
Thực tế 11/2026 Connector chưa có trên mọi nền tảng bên thứ ba. Tên beta header đã đổi theo thời gian; tra tài liệu MCP connector trên platform.claude.com. Phần viết MCP server và MCP client xem bài 12.
Thuật ngữ
OAuth access token

9. Agent framework bên ngoài

CCDV-F D1

Hình dung đời thường
Nấu ăn bằng bộ nồi đa năng thì nhanh với món nó hỗ trợ sẵn. Món lạ thì bạn phải hiểu bên trong nó nấu thế nào, và khi cháy thì khó biết cháy ở đâu.

Ngoài Claude Agent SDK, nhiều đội dùng framework của bên thứ ba. Exam guide nêu tên ba cái:

FrameworkÝ tưởng chínhHợp khi
Strands Agents (AWS, mã nguồn mở)Model-driven: khai báo model, prompt, tool; model tự lập kế hoạchĐội đã ở trên AWS, Bedrock
LangGraphLuồng là đồ thị trạng thái: node, cạnh, checkpointWorkflow nhiều nhánh, cần lưu và khôi phục trạng thái, có bước người duyệt
PydanticAIKiểu dữ liệu chặt: input, output validate bằng PydanticỨng dụng Python cần output có cấu trúc đáng tin

Gọi API trực tiếpTự viết vòng lặp toolLuồng đơn giản, cần kiểm soát hết, ít phụ thuộc

Đánh đổi chung: framework cho sẵn trạng thái, retry, đồ thị, đổi nhà cung cấp model. Đổi lại thêm phụ thuộc, thêm prompt ẩn, và khó gỡ lỗi hơn vì phải đọc qua lớp trừu tượng. Dùng framework nào thì vẫn cần hiểu vòng lặp gốc (stop_reason, tool_use, tool_result) để đọc trace.

Cốt lõi. Bắt đầu bằng cách đơn giản nhất. Chọn framework vì nó giải được một nhu cầu cụ thể (trạng thái bền, đồ thị nhiều nhánh, validate kiểu), không vì nó phổ biến.
Bẫy. "Chuyển sang framework X" để chữa một lỗi nằm ở mô tả tool hay prompt: lỗi vẫn đi theo sang framework mới.
Thuật ngữ
Harness
Phần mềm bao quanh model: vòng lặp, tool, quản lý context, quyền.
Checkpoint
Bản lưu trạng thái giữa chừng để chạy tiếp sau khi dừng hoặc lỗi.
