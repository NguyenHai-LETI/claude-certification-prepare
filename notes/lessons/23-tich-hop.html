1. Phình năng lực: quá nhiều tool, quá nhiều quyền

CCAR-P D3

Hình dung đời thường
Nhân viên thu ngân được phát chìa khoá kho, két sắt và phòng giám đốc "cho tiện". Họ không cần, nhưng nếu bị lừa hoặc nhầm thì thiệt hại lớn hơn nhiều. Cách an toàn là thu lại chìa không dùng, không phải lắp thêm camera.

Capability bloat là khi agent có nhiều tool, quyền hoặc subagent hơn việc cần. Hậu quả: chọn tool kém chính xác hơn (nhiều tool mô tả gần giống nhau), tốn context cho định nghĩa tool, và bề mặt tấn công rộng hơn.

Biện phápLoạiKhi nào là đáp án
Bỏ tool, quyền không cần cho vai trò đóPhòng ngừa: loại bỏ rủi roVai trò không bao giờ cần thao tác đó (quyền tối thiểu)
Xác nhận trước khi chạyGiảm thiểuThao tác cần cho vai trò nhưng rủi ro cao
Log, kiểm toánPhát hiện sauLuôn cần, nhưng không ngăn được sự cố
Tool hẹp thay tool chungPhòng ngừaload_document có kiểm URL thay vì fetch_url tự do
Chia tool theo subagentPhòng ngừaMỗi agent chỉ có tool đúng chuyên môn

Ví dụ chạy từng bước: agent hỗ trợ có bốn tool. Agent có read_ticket, draft_reply, issue_refund, delete_account. Nhân viên hỗ trợ chỉ đọc ticket và soạn trả lời.

  1. Liệt kê việc vai trò này thật sự làm: đọc ticket, soạn trả lời.
  2. Bỏ delete_account khỏi agent này: vai trò không bao giờ cần, nên loại bỏ chứ không thêm xác nhận.
  3. issue_refund chuyển sang một agent khác dành cho đội tài chính, có cổng duyệt.
  4. Đo lại: tỷ lệ chọn đúng tool tăng, định nghĩa tool chiếm ít context hơn, bề mặt tấn công nhỏ hơn.
Thuật ngữ
Capability bloat
Agent có nhiều tool, quyền hay subagent hơn việc cần.
Bề mặt tấn công
Tập các cách mà kẻ xấu có thể lợi dụng hệ thống; càng nhiều quyền thì càng rộng.

Thư viện tool lớn: tải dần thay vì nạp hết

Khi cần hàng trăm tool (nhiều MCP server), có hai kỹ thuật của Anthropic:

  • Tool search: đánh dấu tool defer_loading, Claude chỉ thấy công cụ tìm tool và vài tool hay dùng, rồi tìm và nạp tool khi cần. Bài viết của Anthropic ghi nhận giảm khoảng 85% token định nghĩa tool trong ví dụ của họ.
  • Code execution với MCP: trình bày tool như file code để agent chỉ đọc định nghĩa cần dùng và xử lý dữ liệu trung gian trong sandbox; ví dụ của Anthropic giảm từ 150.000 xuống 2.000 token.
Sai
Agent hỗ trợ có tool xoá tài khoản dù nhân viên hỗ trợ không bao giờ xoá tài khoản; "bù lại" bằng log và hộp thoại xác nhận.
Đúng
Gỡ hẳn tool xoá tài khoản khỏi cấu hình agent đó. Log và xác nhận dành cho thao tác vai trò thật sự cần.
Cốt lõi. Câu hỏi "giảm rủi ro tốt nhất theo quyền tối thiểu" thì chọn loại bỏ năng lực không cần, không chọn biện pháp phát hiện hay bù trừ.

2. Xác thực, phân quyền và lỗ hổng

CCAR-P D3 CCDV-F D7

Hình dung đời thường
Lễ tân khách sạn cầm thẻ tổng mở mọi phòng. Khách nào nói "mở phòng 305 giúp tôi" là lễ tân mở. Lễ tân bị lợi dụng làm "người được uỷ quyền nhầm": hệ thống tin lễ tân, lễ tân tin bất kỳ ai.
Lỗ hổngMô tảCách chặn
Tài khoản dịch vụ dùng chungAgent dùng một tài khoản quyền rộng cho mọi người dùngHành động theo danh tính và quyền của từng người dùng (như connector thừa hưởng quyền)
Confused deputyProxy MCP tới API bên thứ ba bị lợi dụng để lấy quyền mà người dùng chưa đồng ýXin đồng ý theo từng client, kiểm tra redirect, không dùng lại sự đồng ý cũ
Token passthroughMCP server nhận token từ client rồi chuyển thẳng cho API phía sauServer không được chuyển tiếp token; chỉ nhận token cấp cho chính nó (kiểm audience), dùng token riêng cho API phía sau
Phạm vi token quá rộngLộ một token là lộ nhiều quyềnScope tối thiểu, nâng dần khi cần
SSRFClient bị dẫn tới gọi địa chỉ nội bộChặn dải địa chỉ nội bộ, kiểm URL
Secret trong prompt hoặc codeKey lộ qua log, transcriptSecrets manager, biến môi trường, vault của Managed Agents

Đặc tả authorization của MCP cho server từ xa dựa trên OAuth 2.1: client bắt buộc dùng PKCE và resource indicator (RFC 8707) để nói rõ token xin cho server nào; server kiểm tra token được cấp cho chính nó; token sai hoặc hết hạn trả 401.

Bẫy. "Cho agent một API key admin để tránh lỗi quyền" là tạo lỗ hổng. "Model lớn hơn tuân lệnh tốt hơn nên an toàn hơn" không liên quan phạm vi quyền.

Ví dụ chạy từng bước: agent tra cứu nhân sự. Bản đầu dùng một tài khoản dịch vụ đọc được mọi hồ sơ, trả lời bất kỳ ai hỏi.

  1. Nhận ra lỗ hổng: agent đọc hồ sơ thay cho người hỏi mà không kiểm người hỏi có quyền không.
  2. Đưa danh tính người dùng vào: đăng nhập SSO, agent gọi API nhân sự bằng token mang quyền của chính người hỏi.
  3. MCP server nhân sự kiểm token được cấp cho chính nó (audience), không chuyển tiếp token cho hệ thống khác; gọi hệ thống phía sau bằng token riêng.
  4. Scope tối thiểu: quyền đọc hồ sơ của phòng mình; quyền rộng hơn phải xin riêng.
  5. Log truy cập theo người dùng để kiểm toán.
Sai
Một tài khoản dịch vụ quyền rộng cho mọi người dùng, kèm dặn trong prompt "chỉ trả lời người có quyền".
Đúng
Agent hành động theo danh tính và quyền của từng người dùng; quyền được kiểm ở API, không ở prompt.
Cốt lõi. Agent không được có nhiều quyền hơn người nó phục vụ. Xác thực từng người dùng, token đúng audience và scope hẹp, không chuyển tiếp token, kiểm quyền ở hệ thống chứ không ở prompt.
Thuật ngữ
Confused deputy
Một bên có quyền (proxy, server) bị lừa dùng quyền đó thay cho kẻ không có quyền.
Audience
Trường trong token cho biết token được cấp cho dịch vụ nào; dịch vụ phải từ chối token không dành cho mình.
PKCE
Cơ chế của OAuth chống bị đánh cắp mã cấp quyền trên đường trả về.

3. Chọn cơ chế tích hợp: MCP, API, CLI, A2A

CCAR-P D3

Hình dung đời thường
Cắm thiết bị vào nhà có nhiều cách. Ổ cắm chuẩn thì mọi thiết bị dùng chung (MCP). Nối dây riêng cho một máy đặc biệt thì chỉ máy đó dùng được (API riêng). Dụng cụ có sẵn trong hộp đồ nghề thì cứ thế mà dùng (CLI). Còn khi cần công ty khác làm giúp một việc, bạn không nối dây vào máy móc của họ mà ký hợp đồng giao việc (A2A).
Cơ chếNối gì với gìHợp khi
MCPAgent với tool, dữ liệu, promptMột hệ thống cần dùng lại ở nhiều ứng dụng, nhiều client (Claude Code, claude.ai, API); có hệ sinh thái server sẵn
Gọi API trực tiếp (custom tool)Một ứng dụng với một dịch vụTích hợp riêng một app, cần kiểm soát chặt, ít client
CLIAgent với công cụ dòng lệnh có sẵn (git, gh, aws)Môi trường developer (Claude Code), công cụ đã có CLI tốt
A2A (agent-to-agent)Agent với agent khác, mỗi bên là hộp đenAgent của tổ chức, nhà cung cấp khác nhau cần giao việc cho nhau; mỗi agent công bố khả năng (agent card)
Cốt lõi. Agent cần dùng một hệ thống: MCP (dùng lại) hoặc API (riêng một app). Agent cần giao việc cho một agent khác mà nó không nhìn được bên trong: A2A.

Câu hỏi giúp chọn nhanh:

  1. Thứ cần nối là tool hay dữ liệu, hay là một agent khác? Agent khác mà bạn không thấy bên trong: A2A. Tool, dữ liệu: MCP, API hoặc CLI.
  2. Bao nhiêu ứng dụng, client cần dùng? Nhiều (Claude Code, claude.ai, vài app API): MCP để viết một lần dùng nhiều nơi. Một app: custom tool gọi API là đủ.
  3. Đã có CLI tốt và người dùng là developer? Cho agent dùng CLI với quyền hẹp thường đơn giản nhất, không cần viết server mới.

Ví dụ chạy từng bước. Công ty có dịch vụ tồn kho, bốn nơi cần dùng: Claude Code của đội kỹ thuật, claude.ai của đội kinh doanh, hai app nội bộ gọi Claude API. Ngoài ra agent mua hàng cần giao việc đàm phán cho agent của nhà cung cấp.

  1. Tồn kho: viết một MCP server remote có OAuth, mỗi người dùng chỉ thấy kho mình được phép; cả bốn nơi kết nối cùng server.
  2. Đội kỹ thuật thao tác hạ tầng: dùng CLI aws sẵn có với role chỉ đọc, không viết MCP riêng.
  3. Đàm phán với nhà cung cấp: A2A, vì agent của họ là hộp đen; trao đổi qua agent card và tác vụ, không chia sẻ prompt hay tool nội bộ.
Sai
Mỗi app tự viết tích hợp riêng tới dịch vụ tồn kho; bốn bản code, bốn cách phân quyền.
Đúng
Một MCP server dùng chung, phân quyền tập trung; app nào cần cũng kết nối được.
Thuật ngữ
Agent card
Mô tả công khai của một agent trong A2A: nó làm được gì, nhận yêu cầu thế nào, xác thực ra sao.
MCP server remote
MCP server chạy trên mạng (HTTP), nhiều client kết nối được, thường có OAuth.

4. Thiết kế pipeline RAG

CCAR-P D3 CCDV-F D2

Hình dung đời thường
Thủ thư giỏi không đọc cả thư viện cho bạn. Họ có mục lục tốt (index), biết sách nào nói về gì (metadata), tra cả theo từ khoá lẫn theo chủ đề, rồi đưa bạn đúng vài trang.

Trước khi dựng RAG: nếu kho tri thức nhỏ hơn khoảng 200.000 token, cách đơn giản nhất là đưa toàn bộ vào prompt kèm prompt caching. RAG dành cho kho lớn hơn hoặc thay đổi thường xuyên.

Theo Anthropic, contextual embeddings cộng contextual BM25 giảm số lần truy xuất thất bại khoảng 49%, thêm rerank thì khoảng 67%. Anthropic không cung cấp model embedding; tài liệu dùng Voyage AI hoặc nhà cung cấp khác.

Quyết địnhLựa chọn
ChunkingTheo cấu trúc cho Markdown, HTML, văn bản pháp lý; theo kích thước có overlap làm mặc định; theo câu cho văn bản thuần
MetadataNguồn, ngày, phòng ban, quyền truy cập: dùng để lọc và để chặn người dùng thấy tài liệu họ không có quyền
Làm mới indexRe-index khi tài liệu đổi; kiểm tra sau mỗi lần refresh (lỗi index là nguyên nhân hay gặp khi câu trả lời đột ngột sai)
Bẫy. RAG trả lời tự tin nhưng sai ngay sau một lần cập nhật tài liệu, model và độ trễ không đổi: nghi bước truy xuất và index trước (index hỏng, embedding lệch phiên bản), không nghi model "tự đổi trọng số".

Ví dụ chạy từng bước: trợ lý tri thức nội bộ cho cả công ty.

  1. Đo kho: 15.000 trang (vượt xa 200.000 token), đổi hằng tuần, nên cần RAG.
  2. Chunking theo cấu trúc (mục, tiêu đề) cho tài liệu Markdown và HTML; theo kích thước có overlap cho PDF.
  3. Thêm ngữ cảnh cho từng chunk trước khi đánh index (tên tài liệu, mục, kỳ báo cáo), để "doanh thu tăng 3%" biết là của công ty nào, quý nào.
  4. Index lai embedding và BM25, rerank lấy 5–10 chunk.
  5. Gắn metadata quyền truy cập; lọc theo quyền của người hỏi ngay khi truy xuất.
  6. Eval riêng tầng truy xuất (chunk đúng có nằm trong top k không) và tầng trả lời; kiểm lại sau mỗi lần làm mới index.
Sai
Index toàn bộ tài liệu không kèm quyền, rồi dặn model "không trích tài liệu mật".
Đúng
Metadata quyền trên từng chunk, lọc theo người hỏi ngay ở bước truy xuất; model không bao giờ thấy tài liệu người hỏi không được xem.
Cốt lõi. Kho nhỏ thì đừng dựng RAG. Kho lớn: chunk theo cấu trúc, thêm ngữ cảnh cho chunk, tìm lai và rerank, lọc quyền khi truy xuất, eval riêng tầng truy xuất.
Thuật ngữ
Chunk
Một đoạn tài liệu được cắt ra để đánh index và truy xuất.
Contextual retrieval
Kỹ thuật thêm một đoạn ngữ cảnh ngắn vào mỗi chunk trước khi đánh index, giúp truy xuất đúng hơn.

5. Chiến lược truy xuất theo dạng dữ liệu

CCAR-P D3

Hình dung đời thường
Trong thư viện, muốn tìm sách theo mã ISBN thì tra danh mục chính xác. Muốn "sách nào nói về nuôi dạy trẻ tuổi teen" thì hỏi thủ thư hiểu nội dung. Muốn biết "năm ngoái mượn bao nhiêu sách thiếu nhi" thì xem bảng thống kê, không đi đọc từng cuốn. Ba câu hỏi, ba cách tìm.

RAG thường được nghĩ là "embedding và vector database", nhưng embedding chỉ hợp với một kiểu câu hỏi. Nhiệm vụ 3.6 kiểm tra bạn có khớp cách tìm với dạng dữ liệu và kiểu câu hỏi hay không.

Dạng dữ liệu, kiểu câu hỏiChiến lược hợp
Bảng số liệu, câu hỏi tổng hợp ("doanh thu quý theo vùng")Tool truy vấn SQL hoặc API có cấu trúc, không dùng embedding
Mã sản phẩm, số hợp đồng, tên riêngTìm kiếm từ khoá (BM25) hoặc tra cứu chính xác
Câu hỏi theo nghĩa, diễn đạt đa dạngEmbedding, thường kết hợp BM25
Quan hệ ("ai gọi hàm này", "phòng nào phụ thuộc hệ thống X")Đồ thị, chỉ mục cấu trúc, công cụ tìm theo quan hệ
Thông tin mới theo thời gianLọc theo ngày, ưu tiên nguồn mới, ghi ngày nguồn
Codebase, thư mục tài liệu agent tự khám pháAgentic search just-in-time (Grep, Glob, đọc file theo nhu cầu)

Vì sao embedding không hợp mọi thứ:

  • Mã và số chính xác (E-4471, HĐ-2026-118): embedding coi "E-4471" và "E-4417" gần nhau vì trông giống nhau, nhưng đó là hai lỗi khác hẳn. Tìm từ khoá khớp đúng chuỗi.
  • Câu hỏi tổng hợp: "tổng doanh thu" cần cộng hàng nghìn dòng. Truy xuất vài đoạn văn rồi để model cộng sẽ sai; để cơ sở dữ liệu tính, model chỉ viết truy vấn và diễn giải kết quả.
  • Quan hệ nhiều bước: "dịch vụ nào hỏng nếu đổi API thanh toán" cần đi theo chuỗi phụ thuộc, không phải tìm đoạn văn giống câu hỏi nhất.

Tìm kiếm lai (hybrid) chạy cả embedding và BM25 rồi gộp kết quả, sau đó rerank để giữ đoạn tốt nhất. Đây là cấu hình mặc định hợp lý cho kho văn bản hỗn hợp, vì người dùng vừa hỏi theo nghĩa vừa gõ mã chính xác.

Ví dụ chạy từng bước: trợ lý cho đội hỗ trợ kỹ thuật. Câu hỏi đến từ ba kiểu người dùng.

  1. "Lỗi E-4471 là gì?": tìm từ khoá trên kho bài viết, khớp đúng mã.
  2. "Máy in kêu lạch cạch khi khởi động": tìm lai embedding cộng BM25, rerank, lấy 5 đoạn.
  3. "Tháng trước có bao nhiêu ticket về lỗi này theo khu vực?": tool chạy truy vấn có tham số trên kho ticket, model diễn giải bảng kết quả.
  4. Cho agent cả ba tool, mô tả rõ khi nào dùng tool nào; eval có ca cho từng kiểu câu hỏi để đo agent chọn đúng tool.
Sai
Đưa cả bảng doanh thu vào vector database, rồi hỏi "tổng doanh thu theo vùng" và để model cộng các đoạn truy xuất được.
Đúng
Cho model một tool truy vấn SQL chỉ đọc, có giới hạn; cơ sở dữ liệu tính tổng, model diễn giải.
Bẫy. Cho model tự viết SQL tuỳ ý trên cơ sở dữ liệu production là rủi ro. Dùng tài khoản chỉ đọc, view giới hạn cột, truy vấn có tham số hoặc API có cấu trúc, và giới hạn số dòng trả về.
Cốt lõi. Không có chiến lược truy xuất chung cho mọi thứ. Khớp cách tìm với hình dạng dữ liệu và kiểu câu hỏi; nhiều hệ thật dùng kết hợp.
Thuật ngữ
BM25
Thuật toán tìm kiếm theo từ khoá, chấm điểm theo tần suất từ; giỏi khớp chính xác mã và tên.
Hybrid search
Kết hợp tìm theo nghĩa (embedding) và tìm theo từ khoá, rồi gộp kết quả.

6. Đánh đổi độ chính xác và độ trễ

CCAR-P D3

Hình dung đời thường
Quán phở có thể ninh nước dùng thêm hai tiếng cho ngon hơn, nhưng khách đang đứng chờ thì không đợi được hai tiếng. Chủ quán khéo không chọn "ngon nhất" hay "nhanh nhất". Họ hỏi: khách chịu chờ tối đa bao lâu, và trong thời gian đó làm sao cho ngon nhất? Ninh sẵn từ sáng (làm trước), trụng bánh song song với múc nước (làm cùng lúc), bưng rau ra trước cho khách đỡ sốt ruột (cho thấy kết quả sớm).

Kiến trúc sư không tối ưu riêng độ chính xác hay riêng độ trễ. Bạn nhận hai ngưỡng từ yêu cầu (ví dụ độ chính xác từ 92%, p95 dưới 3 giây), rồi tìm cấu hình rẻ nhất đạt cả hai. Muốn làm vậy phải biết thời gian đang tiêu vào đâu. Cách làm là lập ngân sách độ trễ: chia SLA cho từng khâu (truy xuất, rerank, thời gian tới token đầu, sinh output) rồi đo từng khâu bằng trace.

Núm chỉnhTăng chính xácGiá phải trả
Model lớn hơn, effort cao hơnSuy luận tốt hơnChậm hơn, đắt hơn
Thêm chunk, thêm rerankÍt bỏ sót hơnThêm độ trễ, thêm token
Vòng kiểm tra (evaluator, validate)Ít lỗi lọt raThêm một hoặc nhiều lượt gọi
Song song hoá các bước độc lậpKhông đổiGiảm độ trễ, tăng chi phí đồng thời
Prompt caching, streamingKhông đổiGiảm độ trễ (cảm nhận và thật) mà không giảm chất lượng

Hai loại độ trễ cần tách riêng:

  • Độ trễ cảm nhận: người dùng chờ bao lâu mới thấy chữ đầu tiên (time to first token, TTFT). Streaming và cache phần tĩnh cải thiện chỉ số này.
  • Tổng độ trễ: lâu bao nhiêu thì xong cả câu trả lời hoặc cả tác vụ. Chỉ số này quan trọng khi hệ thống khác đang chờ kết quả (API phía sau, pipeline), vì máy không "đỡ sốt ruột" nhờ streaming.

Ví dụ chạy từng bước. Trợ lý tra cứu chính sách đạt độ chính xác 92,5% nhưng p95 là 4,2 giây, trong khi SLA là 3 giây.

  1. Đo trace theo khâu, không đoán: rerank 1,1 giây, chờ token đầu 1,6 giây vì input có 20 chunk.
  2. Thử từng núm một và chạy lại eval sau mỗi lần: 20 chunk xuống 8 chunk, độ chính xác 92,5% xuống 92,1%; vẫn đạt.
  3. Rerank chỉ 30 ứng viên đầu thay vì 100: rerank còn 0,5 giây, độ chính xác không đổi.
  4. Đặt system prompt và chính sách chung lên đầu, bật prompt caching: chờ token đầu còn 0,7 giây.
  5. Bật streaming cho giao diện chat để người dùng thấy chữ sớm hơn nữa.
  6. Ghi quyết định: "Cấu hình B đạt 92,1% và p95 2,6 giây, rẻ hơn cấu hình A vì ít token input". Kèm số liệu eval để người sau hiểu vì sao.
Sai
Thấy chậm thì đổi ngay sang model nhỏ nhất, không đo khâu nào chậm, không chạy lại eval.
Đúng
Đo theo khâu, cắt khâu chiếm nhiều thời gian nhất, đổi một núm mỗi lần và chạy lại eval, chọn cấu hình rẻ nhất đạt cả hai ngưỡng.
Bẫy. Song song hoá các bước phụ thuộc nhau (bước sau cần kết quả bước trước) không giảm được độ trễ mà còn sai kết quả. Chỉ song song hoá bước độc lập, ví dụ ba lần tra cứu không liên quan nhau.
Cốt lõi. Biện minh cấu hình bằng SLA và số liệu eval: "p95 dưới 3 giây, độ chính xác từ 92%; cấu hình B đạt cả hai với chi phí thấp nhất". Với tác vụ có người đang chờ, streaming và trả lời từng phần cải thiện trải nghiệm ngay cả khi tổng thời gian không đổi.
Thuật ngữ
p95
Mức độ trễ mà 95% request nhanh hơn. Dùng thay trung bình vì người dùng nhớ những lần chậm.
TTFT
Time to first token: thời gian từ lúc gửi request tới lúc nhận token đầu tiên.
Ngân sách độ trễ
Chia tổng thời gian cho phép thành phần cho từng khâu, để biết khâu nào đang vượt.
Reranker
Model chấm lại mức liên quan của các đoạn đã truy xuất, giữ lại những đoạn tốt nhất.

8. Khám phá dần hay context nguyên khối

CCAR-P D3

Hình dung đời thường
Một luật sư chuẩn bị phiên toà. Vụ nhỏ thì bê cả tập hồ sơ lên bàn, lật đâu có đó. Vụ lớn có hàng nghìn trang thì không bê hết được: họ giữ mục lục và danh sách tài liệu, cần chứng cứ nào thì nhờ trợ lý lấy đúng tập đó lên. Bàn chỉ có hạn, nên càng nhiều giấy tờ không liên quan thì càng khó tìm thứ cần.

Nhiệm vụ 3.8 của CCAR-P hỏi khi nào nạp mọi thứ vào context ngay từ đầu (nguyên khối, monolithic), và khi nào để agent tự tìm và nạp phần cần lúc cần (khám phá dần, progressive discovery). Context không phải chỉ là giới hạn token: nhồi nhiều thứ không liên quan làm model kém chú ý vào thứ quan trọng, kể cả khi còn chỗ.

Nguyên khối (nạp hết từ đầu)
  • Mọi tài liệu, mọi định nghĩa tool trong system prompt
  • Đơn giản, dự đoán được, cache tốt khi phần tĩnh lớn
  • Hợp: kho nhỏ, ít tool, câu hỏi luôn cần cùng bối cảnh
  • Rủi ro: tốn token, loãng chú ý khi kho lớn
Khám phá dần (progressive discovery)
  • Skills nạp khi khớp việc; tool search; đọc file just-in-time
  • Tiết kiệm context, mở rộng tới kho rất lớn
  • Hợp: nhiều tool, nhiều quy trình, kho thay đổi
  • Rủi ro: thêm bước tìm, cần mô tả tốt để tìm đúng

Nguồn: anthropic.com/engineering (advanced tool use, code execution with MCP, contextual retrieval).

Bốn câu hỏi giúp chọn:

  1. Kho lớn cỡ nào so với context? Nhỏ và ổn định thì nạp hết, cache phần tĩnh.
  2. Có bao nhiêu tool, bao nhiêu quy trình? Vài tool thì nạp thẳng; hàng chục tới hàng trăm tool thì dùng tool search hoặc Skills.
  3. Thay đổi thường xuyên không? Kho đổi hằng ngày thì khám phá dần đọc bản mới nhất, không phải dựng lại prompt.
  4. Độ trễ có gắt không? Mỗi bước tìm là thêm lượt gọi. Nếu mọi câu hỏi đều cần cùng một bối cảnh, nạp sẵn nhanh hơn.

Ví dụ chạy từng bước. Trợ lý nội bộ phải theo 40 quy trình và dùng 150 tool từ 8 MCP server. Bản đầu nạp hết, câu trả lời kém dần và mỗi request tốn nhiều token.

  1. Đo context: định nghĩa tool chiếm khoảng 60.000 token, 40 quy trình thêm 30.000 token, trước khi người dùng hỏi gì.
  2. Chuyển mỗi quy trình thành một Skill có description nói rõ khi nào dùng; chỉ tên và description nằm sẵn trong context.
  3. Bật tool search; giữ nạp sẵn 5 tool dùng trong hầu hết hội thoại.
  4. Giữ nguyên khối phần dùng chung cho mọi câu hỏi (chính sách công ty, khoảng 5.000 token) và cache nó.
  5. Chạy lại eval: kiểm tra tỷ lệ chọn đúng skill và đúng tool, không chỉ độ chính xác câu trả lời.
Bẫy. Khám phá dần chỉ tốt khi agent tìm được. Skill có description mơ hồ ("hỗ trợ công việc") thì không bao giờ được nạp đúng lúc; tool có tên trùng nghĩa thì tool search chọn nhầm. Khi chuyển sang khám phá dần, đo tỷ lệ chọn đúng chứ không chỉ đo token.
Cốt lõi. Kho nhỏ và ổn định: nạp hết kèm cache. Kho lớn, nhiều tool, nhiều quy trình: khám phá dần, và đầu tư vào mô tả (tên, description) để agent tìm đúng. Hệ thống thật thường kết hợp cả hai: phần chung nguyên khối, phần chuyên biệt nạp khi cần.
Thuật ngữ
Progressive disclosure
Cách Skills hoạt động: chỉ lộ thông tin tóm tắt trước, chi tiết được nạp dần khi cần.
Just-in-time
Nạp dữ liệu đúng lúc cần dùng, thay vì nạp sẵn từ đầu.
Tool search
Cơ chế để Claude tìm và nạp định nghĩa tool khi cần, thay vì nhận mọi định nghĩa ngay từ đầu.
