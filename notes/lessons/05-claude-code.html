1. Thứ bậc CLAUDE.md

CCAR-F D3 CCDV-F D3 CCDV-F D2 CCAR-P D7

Hình dung đời thường
Một nhân viên mới vào công ty gặp ba loại “nội quy”. Nội quy công ty dán ở sảnh, ai cũng đọc. Quy định riêng của phòng ban chỉ có hiệu lực khi bạn vào phòng đó. Sổ tay cá nhân của chính bạn thì chỉ bạn đọc. Nếu sếp ghi quy tắc quan trọng vào sổ tay của mình, nhân viên mới sẽ không bao giờ thấy nó. CLAUDE.md hoạt động y như vậy.

CLAUDE.md là một file markdown chứa chỉ dẫn cố định (lệnh build, quy ước code, “luôn làm X”). Claude Code đọc nó ở đầu mỗi phiên và đưa vào context (vùng nhớ làm việc của Claude trong phiên đó). Có ba cấp, mỗi cấp nằm ở một chỗ khác nhau nên người được thấy cũng khác nhau.

CấpVị tríChia sẻ với đội?
User~/.claude/CLAUDE.mdKhông (không nằm trong git)
ProjectCLAUDE.md ở gốc repo hoặc .claude/CLAUDE.mdCó
Thư mụcCLAUDE.md trong thư mục conCó
  • /init quét repo và tạo CLAUDE.md ban đầu.
  • @import tham chiếu file ngoài để CLAUDE.md gọn; mỗi package chỉ import chuẩn liên quan.
  • /memory xem file memory nào đang được nạp: dùng khi hành vi không nhất quán giữa các phiên.
  • Định kỳ rà CLAUDE.md cho gọn và hết mâu thuẫn.

Ví dụ: package billing chỉ import chuẩn nó cần

# packages/billing/CLAUDE.md
Dự án thanh toán. Chạy test: npm test -- billing

@docs/standards/money.md        # import: nội dung file này được nạp cùng
@docs/standards/testing.md      # chỉ import chuẩn liên quan tới billing

Cách làm này giữ file gọn. Package web không cần đọc chuẩn tiền tệ, nên CLAUDE.md của nó không import money.md.

Sai
  • Ghi quy ước của cả đội vào ~/.claude/CLAUDE.md của mình
  • Thành viên mới clone repo nhưng Claude không biết quy ước
  • Một CLAUDE.md dài, nhiều mâu thuẫn
Đúng
  • Đặt quy ước chung ở CLAUDE.md của project rồi commit
  • Chỉ giữ sở thích cá nhân (ngôn ngữ trả lời, editor) ở cấp user
  • Tách chuẩn theo chủ đề, dùng @import, định kỳ rà lại
Tình huống hay ra. Thành viên mới không nhận được chỉ dẫn vì chỉ dẫn nằm ở cấp user của người khác.
Thực tế 11/2026 Theo tài liệu memory hiện hành:
  • Claude Code nạp CLAUDE.md ở thư mục đang chạy và mọi thư mục cha của nó. File ở thư mục gốc đứng trước, file gần nhất đứng sau. Các file được nối lại, không ghi đè nhau.
  • CLAUDE.md trong thư mục con chỉ nạp khi Claude đọc, ghi hoặc sửa file ở thư mục đó, đúng như Hình 1.
  • Ngoài ba cấp của đề thi còn có CLAUDE.local.md (riêng bạn trong một project, nên gitignore) và CLAUDE.md managed policy do admin triển khai cho cả tổ chức.
  • Mỗi file nên dưới khoảng 200 dòng. @import cho phép lồng tối đa 4 bước, và đường dẫn tương đối tính từ file chứa dòng import.
  • Claude cũng đọc được AGENTS.md nếu repo dùng file này thay cho CLAUDE.md.
  • Kiểm tra file nào đã nạp: docs hướng dẫn chạy /context all rồi xem danh sách dưới mục Memory files. /memory dùng để duyệt và mở các file memory (CLAUDE.md, CLAUDE.local.md, auto memory) ra sửa, và để bật tắt auto memory. Exam guide v1.0 vẫn nói dùng /memory để xác minh file đã nạp: khi thi chọn theo exam guide.
Đề thi chỉ hỏi ba cấp user, project, thư mục.
Thuật ngữ
Context
Toàn bộ chữ Claude đang “nhìn thấy” trong phiên: chỉ dẫn, hội thoại, file đã đọc. Càng đầy, Claude càng khó theo dõi và càng tốn token.
Phiên (session)
Một lần làm việc liên tục với Claude Code, từ lúc mở đến lúc đóng.

Dòng bắt đầu bằng @ kèm đường dẫn, để kéo nội dung file khác vào CLAUDE.md.
Version control (git)
Nơi cả đội cùng lưu code. File nằm trong git thì đồng đội nhận được, file nằm trong thư mục home của bạn thì không.

2. Slash command và skill

CCAR-F D3 CCDV-F D3

Hình dung đời thường
Trong thư viện, trên kệ chỉ dán nhãn tên sách và một dòng mô tả. Bạn chỉ rút sách xuống khi cần. Skill hoạt động như vậy: Claude chỉ thấy tên và mô tả, và chỉ đọc cả “cuốn sách” khi việc đang làm khớp mô tả. Còn CLAUDE.md giống nội quy dán tường: ai vào cũng thấy, lúc nào cũng thấy.

Slash command là lệnh bạn gõ bắt đầu bằng / (ví dụ /review) để chạy một prompt đã soạn sẵn. Skill là một thư mục có file SKILL.md mô tả một quy trình làm việc; Claude tự nạp khi thấy việc phù hợp, hoặc bạn gọi bằng /tên-skill.

Project (chia sẻ qua git)User (cá nhân)
Command.claude/commands/~/.claude/commands/
Skill.claude/skills/<tên>/SKILL.md~/.claude/skills/

Ví dụ command đơn giản nhất: file .claude/commands/review.md chứa một prompt, và cả đội gõ /review là dùng được vì file nằm trong git.

---
name: analyze-deps
description: Phân tích phụ thuộc của repo. Dùng khi người dùng hỏi về thư viện lỗi thời,
  xung đột phiên bản hoặc nói "kiểm tra dependency".
context: fork             # chạy trong context subagent riêng, output dài không làm bẩn phiên chính
allowed-tools: Read, Grep, Bash
argument-hint: [thư mục]  # gợi ý tham số khi gọi mà không truyền đối số
---
## Các bước
1. …, vì …
  • description là phần quan trọng nhất: lúc khởi động Claude chỉ thấy tên và mô tả của mọi skill để quyết định có nạp không. Nêu rõ skill làm gì, khi nào dùng, và cách người dùng hay diễn đạt.
  • Thân skill chỉ nạp khi được kích hoạt (progressive disclosure); giữ SKILL.md gọn, tách chi tiết sang file phụ.
  • Skill nạp khi cần, cho workflow theo việc; CLAUDE.md luôn được nạp, cho chuẩn chung.
  • Muốn biến thể riêng: tạo skill cá nhân tên khác trong ~/.claude/skills/.
Trường frontmatterLàm gì (theo exam guide)
context: forkChạy skill trong context subagent cô lập. Dùng cho output dài (phân tích codebase) hoặc việc thăm dò (brainstorm phương án).
allowed-toolsHạn chế tool trong lúc chạy skill, ví dụ chỉ cho ghi file để tránh hành động phá hoại. (Đề v1.0 chấm theo guide; docs hiện hành: chỉ cấp sẵn quyền, không chặn tool khác, muốn chặn dùng disallowed-tools. Xem ghi chú bên dưới.)
argument-hintNhắc người dùng nhập tham số khi gọi skill mà không kèm đối số.
Mô tả mơ hồ
  • description: Phân tích dependency.
  • Claude không biết khi nào nên nạp, nên bỏ qua dù bạn nói “kiểm tra thư viện cũ”
Mô tả rõ
  • Nêu việc làm, thời điểm dùng, và các cách nói của người dùng (“thư viện lỗi thời”, “kiểm tra dependency”)
  • Claude khớp được và nạp đúng lúc
Bẫy. Nhét quy trình riêng của từng việc vào CLAUDE.md khiến nó nạp ở mọi phiên và tốn context. Quy trình theo việc thì làm skill. Chuẩn chung luôn đúng thì để ở CLAUDE.md. Muốn tuỳ biến skill của đội cho riêng mình, tạo bản tên khác ở ~/.claude/skills/ thay vì sửa bản chung.

Khung đầy đủ của một skill: ghi chú Cấu trúc của một Claude Skill.

Thực tế 11/2026 Theo tài liệu skills hiện hành:
  • Command trong .claude/commands/ đã gộp vào skill; file cũ vẫn chạy, trùng tên thì skill thắng.
  • allowed-tools cấp quyền dùng không cần hỏi trong lượt gọi skill, không chặn tool khác. Muốn loại tool thì dùng disallowed-tools. Exam guide v1.0 mô tả allowed-tools là “giới hạn tool”: khi thi, chọn theo exam guide.
  • Quyền của allowed-tools chỉ có hiệu lực trong lượt gọi skill và hết khi bạn gửi tin nhắn kế tiếp.
  • argument-hint theo docs chỉ là gợi ý hiện khi autocomplete (ví dụ [issue-number]), không tự hỏi người dùng. Exam guide mô tả nó như cách “nhắc nhập tham số”: khi thi chọn theo exam guide. Skill tải lên claude.ai hoặc Skills API chỉ nhận name, description, license, compatibility, metadata, allowed-tools; trường lạ như argument-hint gây lỗi khi đóng gói, trong khi Claude Code lặng lẽ bỏ qua trường nó không biết.
  • description là trường nên có nhất: Claude đọc nó để quyết định có áp dụng skill hay không. Bỏ trống thì Claude Code lấy dòng không rỗng đầu tiên của thân skill. description cộng when_to_use bị cắt ở 1.536 ký tự trong danh sách skill, nên đặt ý chính lên đầu.
  • disable-model-invocation: true: chỉ người dùng gọi được (hợp với /deploy có tác dụng phụ). user-invocable: false: ẩn khỏi menu /, chỉ Claude gọi.
  • Skill cũng có trường paths để chỉ tự nạp khi làm việc với file khớp glob. Exam guide vẫn dùng .claude/rules/ cho tình huống này.
  • context: fork kèm agent (Explore, Plan, general-purpose…); subagent không thấy lịch sử hội thoại nên nội dung skill phải tự đủ.

3. Rule theo đường dẫn

CCAR-F D3

Hình dung đời thường
Trong xưởng, biển “đeo kính bảo hộ” chỉ treo ở khu máy cắt, không treo ở văn phòng. Ai bước vào khu máy cắt mới cần biết quy tắc đó. Rule theo đường dẫn cũng vậy: chỉ khi Claude làm việc với loại file đó, quy tắc mới được nạp.

Rule là một file markdown trong .claude/rules/, mỗi file một chủ đề. Dòng paths ở đầu file là một danh sách glob (mẫu khớp tên file, ví dụ *.test.tsx khớp mọi file test). Rule có paths chỉ nạp khi Claude làm việc với file khớp mẫu.

---
paths: ["**/*.test.tsx"]
---
Quy ước viết test: …
  • File trong .claude/rules/ tách chuẩn theo chủ đề (testing.md, api-conventions.md).
  • Rule có paths chỉ nạp khi Claude làm việc với file khớp glob (exam guide viết “khi sửa”; xem ghi chú bên dưới), tiết kiệm context.
  • Rule theo glob thắng CLAUDE.md thư mục con khi quy ước áp cho file rải khắp codebase (test nằm cạnh code).
Quy ước nằm ở…ChọnLý do
Một thư mục (terraform/)CLAUDE.md trong thư mục đó, hoặc rule với paths: ["terraform/**/*"]File cùng chỗ
File rải nhiều thư mục (mọi *.test.tsx)Rule với glob **/*.test.tsxCLAUDE.md từng thư mục sẽ phải chép lặp
Thực tế 11/2026 Theo tài liệu memory: rule có paths nạp khi Claude dùng tool Read, Write hoặc Edit trên file khớp, và cả khi Claude xem file bằng lệnh Bash được tính là đọc (ví dụ cat hoặc head trên một file). Vậy Claude không cần sửa file thì rule vẫn nạp; đáp án đề nói “khi sửa file khớp” vẫn đúng. Rule không có paths thì nạp ngay lúc khởi động, cùng mức ưu tiên với .claude/CLAUDE.md. Mẫu trong paths tính từ thư mục chứa thư mục .claude của rule dự án.
Bẫy. Đặt một CLAUDE.md trong mỗi thư mục có file test để áp quy ước test. Quy ước bị chép nhiều chỗ, dễ lệch, và sót thư mục mới. Rule theo glob giải quyết gọn một lần.
Thuật ngữ
Glob
Mẫu khớp đường dẫn: * thay cho một đoạn tên, ** thay cho mọi thư mục lồng nhau.
Token
Đơn vị tính chữ của model. Context càng nhiều chữ càng tốn token.

4. Plan mode hay làm trực tiếp

CCAR-F D3

Hình dung đời thường
Sửa bóng đèn hỏng thì bạn thay luôn, không cần bản vẽ. Xây thêm một tầng nhà thì phải có bản vẽ, khảo sát móng và chủ nhà duyệt trước khi đổ bê tông. Làm sai ở bản vẽ chỉ tốn một tờ giấy, làm sai khi xây thì tốn cả tầng. Plan mode là bước “vẽ bản vẽ” cho Claude.

Plan mode là chế độ Claude chỉ đọc code và lập kế hoạch, chưa sửa file nào. Bạn xem kế hoạch, đồng ý rồi mới chuyển sang làm trực tiếp (direct execution: để Claude sửa file ngay).

Plan mode
  • Thay đổi lớn, nhiều file (migration 45+ file)
  • Quyết định kiến trúc, nhiều hướng hợp lệ
  • Tách monolith thành microservice
Làm trực tiếp
  • Phạm vi rõ: bug một file có stack trace
  • Thêm một điều kiện kiểm tra
  • Kết hợp: plan để điều tra và thiết kế, rồi làm trực tiếp theo kế hoạch.
  • Explore subagent cô lập phần dò tìm dài dòng, chỉ trả tóm tắt, tránh cạn context.

Ví dụ: đội muốn đổi thư viện HTTP ở 45 file. Dùng plan mode để Claude tìm mọi chỗ dùng, đề xuất thứ tự đổi và rủi ro. Sau khi bạn duyệt, làm trực tiếp từng nhóm file. Ngược lại, “thêm kiểm tra ngày hợp lệ vào hàm parseDate” là việc một file, rõ phạm vi, nên làm trực tiếp.

Bẫy. “Bắt đầu làm trực tiếp, gặp khó mới chuyển plan” khi đề đã nói rõ việc phức tạp.
Thuật ngữ
Migration
Việc chuyển cả code sang thư viện hoặc phiên bản mới, thường chạm nhiều file.
Monolith / microservice
Một ứng dụng nguyên khối, và các dịch vụ nhỏ tách riêng. Tách cái trước thành cái sau là quyết định kiến trúc lớn.
Explore subagent
Subagent có sẵn chuyên đọc và tìm trong code, trả về bản tóm tắt.

5. Tinh chỉnh lặp

CCAR-F D3

Hình dung đời thường
Bạn nhờ thợ may “may áo vừa vặn” thì mỗi người hiểu một kiểu. Đưa chiếc áo mẫu và số đo cụ thể thì thợ làm đúng ngay. Sau đó thử áo, chỉ chỗ chật, thợ sửa, thử lại, cho đến khi vừa. Làm việc với Claude cũng là vòng lặp “thử, chỉ chỗ sai, sửa”.

Tinh chỉnh lặp (iterative refinement) là cải thiện kết quả qua nhiều vòng nhỏ thay vì mong một lần đúng ngay. Có bốn kỹ thuật chính.

  • Mô tả bằng lời bị hiểu không nhất quán → đưa 2–3 ví dụ vào/ra cụ thể.
  • TDD: viết test trước (hành vi, biên, hiệu năng), lặp bằng cách đưa lỗi test cho Claude.
  • Interview pattern: để Claude hỏi lại nhằm lộ ra điều chưa nghĩ tới trước khi làm ở lĩnh vực lạ.
  • Lỗi tương tác nhau gửi chung một tin nhắn; lỗi độc lập sửa lần lượt.

Ví dụ vào/ra thay cho lời mô tả

Câu “chuẩn hoá ngày tháng” có thể hiểu nhiều cách. Ba ví dụ cụ thể giúp Claude hiểu đúng, kể cả trường hợp biên như null:

"12/03/2024" -> "2024-03-12"
"1/2/2024"   -> "2024-02-01"
null         -> null            # biên: không được báo lỗi

Interview pattern hợp khi bạn làm trong lĩnh vực chưa quen, ví dụ cache. Bạn nhờ: “Trước khi viết code, hãy hỏi tôi về cách làm mất hiệu lực cache và các kiểu lỗi có thể xảy ra.” Câu hỏi của Claude giúp bạn nghĩ ra điều mình chưa nghĩ tới.

Sai
  • Viết “xử lý ngày tháng cho tốt” rồi sửa mỗi lần Claude hiểu khác
  • Hai lỗi liên quan nhau mà báo từng cái, Claude vá cái này làm hỏng cái kia
Đúng
  • Đưa 2–3 ví dụ vào/ra cụ thể, gồm cả trường hợp biên
  • Lỗi tương tác nhau thì gửi chung một tin nhắn. Lỗi độc lập thì sửa lần lượt
Cốt lõi. Ví dụ cụ thể thắng mô tả bằng lời. Test cho Claude một thước đo khách quan. Interview pattern lộ ra yêu cầu ẩn trước khi code. Lỗi liên quan nhau thì xử lý cùng lúc.
Thuật ngữ
TDD (test-driven development)
Viết test trước, rồi viết code cho đến khi test qua.
Trường hợp biên (edge case)
Đầu vào lạ như rỗng, null, số rất lớn, nơi code hay hỏng.

6. Claude Code trong CI/CD

CCAR-F D3 CCDV-F D3 CCAR-P D7

Hình dung đời thường
Nhà máy có một dây chuyền kiểm tra chạy tự động lúc nửa đêm. Không ai đứng đó để bấm nút “đồng ý”. Nếu một máy dừng lại chờ người xác nhận, cả dây chuyền treo. Vì vậy mọi thứ máy được phép làm phải khai báo sẵn, và kết quả phải ghi theo mẫu để máy khác đọc được. Claude Code trong CI cũng thế.

CI/CD là hệ thống tự chạy build, test, review mỗi khi có code mới. Headless mode là chạy claude không có người ngồi tương tác. Cờ -p bật chế độ này.

claude -p "Review the diff for security issues" \
  --output-format json --json-schema review.schema.json \
  --allowedTools "Read,Grep,Glob"
  • -p / --print: chạy không tương tác, không treo chờ input. --output-format json hoặc stream-json.
  • Trong CI không ai bấm duyệt: quyền phải khai báo sẵn, ở mức tối thiểu.
  • CLAUDE.md cung cấp chuẩn test, fixture, tiêu chí review cho Claude chạy trong CI.
  • Phiên đã sinh code review kém hơn một phiên độc lập.
  • Review lại sau commit mới: đưa kết quả review cũ vào, chỉ báo lỗi mới hoặc chưa sửa.
  • Sinh test: đưa file test hiện có vào context để tránh trùng kịch bản.
  • Phiên: --continue tiếp phiên gần nhất, --resume chọn phiên theo tên.
Sai
  • CI chạy claude không có -p, job treo chờ input
  • Nhờ phiên vừa viết code tự review code đó
  • Mỗi lần review lại đăng cả lỗi cũ, comment lặp
Đúng
  • -p kèm --output-format json và --json-schema
  • Phiên review độc lập, đã có CLAUDE.md về tiêu chí
  • Đưa kết quả review cũ vào, chỉ báo lỗi mới hoặc chưa sửa
Bẫy. CLAUDE_HEADLESS, cờ --batch, < /dev/null đều không phải cách đúng.
Thực tế 11/2026 Theo tài liệu chạy Claude Code theo chương trình:
  • Chế độ này nay nằm trong Agent SDK; -p vẫn là cách chạy không tương tác bằng CLI.
  • Khi dùng --json-schema, kết quả có cấu trúc nằm trong trường structured_output của JSON trả về, cùng metadata như session ID và usage.
  • Cờ --bare bỏ qua việc tự tìm hook, skill, plugin, MCP server, auto memory và CLAUDE.md, để cùng một kết quả trên mọi máy. Tài liệu khuyến nghị cho lời gọi theo script; nếu dùng thì phải đưa chỉ dẫn qua cờ, vì CLAUDE.md không được nạp.
  • Không có --bare, phiên -p vẫn chạy hook trong .claude/settings.json và kết nối MCP trong .mcp.json của project, không hiện hộp thoại tin cậy.
Đề thi chỉ cần biết -p, --output-format, --json-schema và vai trò CLAUDE.md.
Thuật ngữ
Pull request (PR)
Đề nghị gộp code mới vào nhánh chính, nơi đồng đội xem và nhận xét.
Diff
Phần khác biệt giữa code cũ và mới.
Fixture
Dữ liệu hoặc môi trường mẫu dựng sẵn cho test.
Inline comment
Bình luận gắn đúng vào một dòng code trong PR.

7. Settings và quyền

CCDV-F D2 CCDV-F D3 CCAR-P D7

Hình dung đời thường
Trong tòa nhà, có luật của chính quyền, nội quy của ban quản lý, và quy định riêng của từng căn hộ. Luật của chính quyền thắng tất cả. Còn thẻ ra vào thì có ba loại quyền: “cấm vào”, “phải hỏi bảo vệ”, “cho vào”. Bảo vệ kiểm tra theo thứ tự cấm trước, rồi hỏi, rồi mới cho, nên đã bị cấm thì không giấy cho phép nào cứu được.

Settings là file JSON cấu hình Claude Code. Permissions (quyền) là phần quyết định tool nào Claude được chạy mà không hỏi, phải hỏi, hoặc bị chặn. Có bốn nơi đặt settings.

FilePhạm viCommit?
~/.claude/settings.jsonUser, mọi dự ánKhông
.claude/settings.jsonProject, cả độiCó
.claude/settings.local.jsonProject, riêng từng ngườiKhông (tự gitignore)
Managed settingsTổ chức, do admin đặtKhông ghi đè được
  • Ưu tiên từ cao xuống thấp: managed → tham số dòng lệnh → local → project → user.
  • permissions có allow, ask, deny, đánh giá theo thứ tự deny → ask → allow; luật khớp đầu tiên theo thứ tự đó quyết định, độ cụ thể của luật không đổi được thứ tự. Deny luôn thắng: deny ở bất kỳ cấp nào chặn allow ở cấp khác; allow không “khoét” ngoại lệ trong deny. Tương tự, một luật ask vẫn hỏi dù có allow cụ thể hơn.
  • Danh sách như permissions.allow gộp giữa các cấp, không thay thế nhau. Khoá đơn (như model) thì cấp cao hơn thắng.
  • Allow trong .claude/settings.json của project chỉ có hiệu lực sau khi từng người tin cậy thư mục (workspace trust); deny và ask áp dụng ngay.
  • Quyết định của hook PreToolUse không vượt qua được luật deny, ask.
Chế độ quyềnHành vi
default (Manual)Hỏi khi dùng mỗi tool lần đầu
acceptEditsTự chấp nhận sửa file và lệnh file thông dụng trong thư mục làm việc
planChỉ đọc và chạy lệnh chỉ đọc để khám phá, không sửa mã nguồn
autoKhông hỏi thường lệ; một classifier kiểm tra hành động trước khi chạy
dontAskTự từ chối mọi lời gọi lẽ ra phải hỏi; chỉ chạy những gì đã được allow sẵn (hợp với CI)
bypassPermissionsBỏ qua hỏi quyền (trừ vài hành động không chế độ nào tự duyệt)

defaultMode là auto hoặc bypassPermissions không có hiệu lực khi đặt trong settings của project hay local; phải đặt ở user, managed, hoặc cờ --permission-mode. Nguồn: settings, permissions.

// .claude/settings.json
{ "permissions": {
    "allow": ["Bash(npm test:*)", "Read"],
    "deny":  ["Bash(rm -rf:*)", "Bash(terraform destroy:*)", "Read(./.env)"] } }

Trong ví dụ trên, cả đội chạy được npm test và đọc file mà không bị hỏi. Lệnh xoá hàng loạt, phá hạ tầng và đọc file .env (chứa bí mật) bị chặn hẳn, dù cá nhân nào đó có allow ở file local của họ.

Sai
  • Deny ở project, rồi allow cụ thể hơn ở local và tin rằng allow sẽ “mở” ngoại lệ
  • Cho rằng luật cụ thể hơn thì thắng
Đúng
  • Deny ở bất kỳ cấp nào vẫn chặn. Muốn mở lại thì gỡ luật deny
  • Thứ tự cố định deny → ask → allow, độ cụ thể không đổi thứ tự
Cốt lõi. Danh sách quyền gộp giữa các cấp, khoá đơn thì cấp cao hơn thắng. Trong quyền, deny luôn thắng.
Thuật ngữ
Hook PreToolUse
Đoạn lệnh tự chạy ngay trước khi một tool được dùng, có thể kiểm tra hoặc từ chối.
Workspace trust
Bước bạn xác nhận “tôi tin thư mục này” trước khi cấu hình trong đó có hiệu lực.
Classifier
Một bộ phân loại tự động đánh giá hành động có an toàn không (dùng ở chế độ auto).
Gitignore
File liệt kê thứ không đưa vào git, như settings.local.json.

8. Plugin

CCDV-F D2 CCDV-F D8 CCAR-P D7

Hình dung đời thường
Một bộ dụng cụ đóng hộp: thay vì mỗi thợ tự mua từng món, công ty đóng sẵn một hộp đầy đủ rồi phát cho mọi chi nhánh. Cập nhật hộp thì mọi nơi nhận bản mới. Plugin là cái hộp đó cho Claude Code.

Plugin gói command, skill, agent, hook, MCP server để cài một lần cho nhiều dự án, phân phối qua marketplace. Hợp khi một đội nền tảng muốn nhiều repo dùng chung một bộ công cụ.

Nhu cầuChọn
Chuẩn chung luôn áp dụng cho một repoCLAUDE.md của project
Quy trình theo việc, dùng trong một repoSkill hoặc command trong .claude/
Cùng một bộ command, skill, hook, MCP cho nhiều repoPlugin qua marketplace
Cốt lõi. Một repo thì để cấu hình trong .claude/. Nhiều repo cần cùng một bộ công cụ thì gói thành plugin để cài một lần và cập nhật tại một nơi.
Thuật ngữ
Marketplace
Danh mục nơi plugin được đăng và cài.
MCP server
Chương trình cho Claude kết nối công cụ hoặc dữ liệu bên ngoài (xem bài 04).
Hook
Lệnh tự chạy ở một thời điểm cố định trong vòng làm việc của Claude Code.
