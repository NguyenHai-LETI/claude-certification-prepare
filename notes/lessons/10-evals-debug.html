1. Eval là gì và dựng eval đầu tiên

CCDV-F D2 CCDV-F D4 CCAR-P D4

Mục này theo khoá Introduction to Evals của Academy (4 bài): vì sao cần eval, dựng bộ eval đầu tiên, các loại grader và chạy eval trong CI. Mục 2 dùng eval và trace để debug hệ agent; mục 3 là phần eval prompt trong khoá Building with the Claude API.

Hình dung đời thường
Giáo viên ra một bộ đề kiểm tra có đáp án chuẩn. Mỗi lần đổi cách dạy (prompt), thầy cho học sinh làm lại cùng bộ đề rồi chấm điểm. Nếu điểm tăng thì cách dạy mới tốt hơn. Nếu không có bộ đề cố định, thầy chỉ “cảm thấy” lớp giỏi lên, và có thể sai.

1.1 Why Evals Matter

Eval = cơ chế đo lường chất lượng response của Claude một cách có hệ thống. Không có evals, bạn không biết liệu prompt thay đổi có cải thiện hay làm xấu đi kết quả. Quy tắc: iterate prompt trước, upgrade model sau — thường cải thiện prompt hiệu quả hơn và rẻ hơn nhiều so với chuyển sang model mạnh hơn.

Quy trình 5 bước chọn model và tối ưu:

  1. Xác định tiêu chí chất lượng (accuracy floor)
  2. Viết các ca thử vào golden dataset
  3. Chọn grader phù hợp (code, LLM hay người)
  4. Sửa prompt cho tới khi vượt ngưỡng chính xác tối thiểu
  5. Chỉ khi đó mới xem xét upgrade model
Thuật ngữ
Golden dataset
Bộ test case chuẩn: mỗi dòng có input, đáp án mong đợi và rubric.
Accuracy floor
Ngưỡng accuracy thấp nhất chấp nhận được.
Grader
Thứ chấm điểm một câu trả lời: code, LLM hoặc người.
Rubric
Tiêu chí chấm viết thành lời, ví dụ “câu trả lời phải nêu mã đơn”.
Sai
  • Thấy kết quả chưa ổn thì đổi ngay sang model mạnh nhất
  • Sửa prompt rồi “thấy tốt hơn” mà không đo
Đúng
  • Đặt ngưỡng, đo bằng golden dataset, sửa prompt đến khi vượt ngưỡng
  • Chỉ nâng model khi prompt đã tối ưu mà vẫn không đạt

1.2 Dựng eval đầu tiên

Một eval đơn giản gồm ba phần: golden dataset, grader và vòng chạy.

import anthropic
import json

client = anthropic.Anthropic()

# Golden dataset — input + expected output + rubric
with open("golden.json") as f:
    test_cases = json.load(f)
# Format: [{"input": "...", "expected": "...", "rubric": "..."}]

def run_eval(test_cases: list, grader_model="claude-haiku-4-5") -> dict:
    results = []
    for case in test_cases:
        # Chạy model cần test
        response = client.messages.create(
            model="claude-sonnet-5",
            max_tokens=1024,
            system=SYSTEM_PROMPT,
            messages=[{"role": "user", "content": case["input"]}]
        )
        actual = response.content[0].text

        # LLM grader với rubric
        grade = client.messages.create(
            model=grader_model,
            max_tokens=100,
            system="You are an evaluator. Answer only PASS or FAIL.",
            messages=[{"role": "user", "content": f"""
Rubric: {case['rubric']}
Expected: {case['expected']}
Actual: {actual}
Does the actual response satisfy the rubric? Answer PASS or FAIL."""}]
        )
        passed = "PASS" in grade.content[0].text.upper()
        results.append({"input": case["input"], "passed": passed, "actual": actual})

    total = len(results)
    passing = sum(1 for r in results if r["passed"])
    return {"accuracy": passing / total, "results": results}

report = run_eval(test_cases)
print(f"Accuracy: {report['accuracy']:.1%}")  # target: > 80%

Đọc code theo thứ tự: nạp golden.json; với mỗi case, gọi model cần test, rồi gọi grader (grader_model, mặc định claude-haiku-4-5) với rubric; "PASS" in …upper() đổi chữ trả về thành true hoặc false; cuối cùng chia số case đạt cho tổng số.

Bẫy. Để grader nói tự do. Hãy ép grader chỉ trả PASS hoặc FAIL (system prompt và max_tokens nhỏ như trong ví dụ), vì câu trả lời dài khó chuyển thành số.

1.3 Các loại grader và eval trong CI

Hình dung đời thường

CI smoke eval — chạy trong GitHub Actions, chỉ dùng 10–20 test cases đại diện. Smoke test là phép thử nhanh để báo sớm có gì hỏng, không cần chạy hết bộ dữ liệu:

# .github/workflows/eval.yml
name: Smoke Eval
on: [push, pull_request]
jobs:
  eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run smoke eval
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: python scripts/smoke_eval.py --threshold 0.80

Chú giải: on: [push, pull_request] chạy mỗi khi có commit hoặc PR. Khóa API lấy từ secrets của GitHub, không ghi vào file. --threshold 0.80 là accuracy floor: dưới 80% thì script thoát lỗi và job đỏ.

Batch API cho nightly eval đầy đủ — rẻ hơn 50% so với gọi thẳng:

batch = client.messages.batches.create(requests=[
    {"custom_id": f"case-{i}", "params": {
        "model": "claude-sonnet-5", "max_tokens": 1024,
        "messages": [{"role": "user", "content": case["input"]}]
    }}
    for i, case in enumerate(full_test_cases)
])
# Poll cho đến khi xong, rồi đọc kết quả
while batch.processing_status != "ended":
    batch = client.messages.batches.retrieve(batch.id)

for result in client.messages.batches.results(batch.id):
    if result.result.type == "succeeded":
        process(result.custom_id, result.result.message)
    else:
        log_error(result.custom_id, result.result.error)

Mỗi request trong batch có một custom_id riêng (ở đây case-0, case-1…) để ghép kết quả về đúng case, vì kết quả có thể trả về không theo thứ tự.

Thực tế 11/2026 Trang Batch hiện hành ghi bốn loại kết quả cho mỗi request: succeeded, errored, canceled, expired (batch hết hạn sau 24 giờ), và request_counts đếm số request đang xử lý cùng từng loại kết quả. Chỉ errored có thông tin lỗi, nên nhánh else trong ví dụ chỉ đúng khi bạn kiểm tra thêm loại. Vòng while ở trên nên có sleep giữa hai lần hỏi. Nguồn: Batch processing.
Lấy mẫu hằng đêm để bắt độ trôi. Mỗi đêm chạy 100 request thật chọn ngẫu nhiên qua batch eval, để phát hiện khi bản cập nhật model làm đổi hành vi dù prompt không đổi.

1.4 Thiết kế golden dataset và tiêu chí thành công

Tài liệu Define success criteria and build evaluations nêu ba nguyên tắc thiết kế eval:

  1. Bám đúng việc thật: ca thử phản ánh phân bố input thật, kể cả ca biên.
  2. Tự động hoá khi có thể: đặt câu hỏi sao cho chấm được bằng code hoặc LLM (trắc nghiệm, khớp chuỗi, code grader, LLM grader).
  3. Ưu tiên số lượng hơn độ tinh: nhiều ca chấm tự động với tín hiệu hơi yếu tốt hơn ít ca do người chấm tay thật kỹ.

Ca biên (edge case) thường gặp: input rỗng hoặc không liên quan; input quá dài; gõ sai chính tả; ca mơ hồ mà người cũng không đồng ý với nhau; câu mỉa mai hoặc cảm xúc lẫn lộn. Ví dụ ba dòng của golden dataset cho bài toán phân loại cảm xúc:

[ { "input": "Great, another delay. Thanks a lot.",
    "expected": "negative", "rubric": "Sarcasm: the label must be negative." },
  { "input": "",
    "expected": "unknown", "rubric": "Empty input: must not invent a sentiment." },
  { "input": "The food was great but the service was slow.",
    "expected": "mixed", "rubric": "Both a positive and a negative aspect: label mixed." } ]

Tiêu chí thành công (success criteria) phải đo được. So sánh hai cách viết:

Sai
“Model nên phân loại cảm xúc tốt.” Không có con số, không biết khi nào là xong.
Đúng
“F1 ít nhất 0,85 trên tập kiểm tra riêng gồm 10.000 bài đăng đa dạng, cao hơn mức hiện tại 5%.” Có con số, có tập đo, có mốc so sánh.

1.5 Chọn cách chấm theo kiểu output

Nguyên tắc của tài liệu: chọn cách chấm nhanh nhất, đáng tin nhất, mở rộng được nhất. Thứ tự ưu tiên là code, rồi LLM, và người là cuối cùng.

Ba mẹo viết LLM grader, cũng từ tài liệu trên:

  • Rubric chi tiết và rõ. Một tiêu chí có thể cần nhiều rubric.
  • Đầu ra cụ thể: chỉ “correct” hoặc “incorrect”, hoặc điểm từ 1 đến 5, vì đánh giá toàn lời văn khó đo hàng loạt.
  • Khuyến khích lập luận: cho grader suy nghĩ trước khi chấm sẽ tăng độ chính xác với phán đoán phức tạp.
Sai
Rubric: “Câu trả lời nên tốt và chuyên nghiệp.” Mỗi lần grader hiểu một kiểu.
Đúng
Rubric: “Câu đầu tiên phải nhắc tên công ty. Nếu không, chấm là incorrect.” Có thể kiểm bằng mắt hoặc bằng code.

Ví dụ có số về ngưỡng CI. Smoke eval 15 ca với --threshold 0.80 cần ít nhất 12 ca đạt, vì 0,80 × 15 = 12. Chạy ra 11 ca đạt thì accuracy là 11/15 = 73,3%, thấp hơn ngưỡng, script thoát lỗi và job đỏ. Chạy ra 12 ca đạt thì đúng bằng 80%, job xanh nếu script coi “bằng hoặc hơn ngưỡng” là đạt.

2. Eval, test và debug

CCDV-F D4 CCAR-P D4

Hình dung đời thường
Đơn hàng giao nhầm địa chỉ. Bạn không đoán “chắc kho lười”. Bạn mở nhật ký từng chặng: nhận đơn, soạn hàng, giao cho shipper, giao tới nơi. Chặng nào ghi sai, sửa ngay chặng đó. Debug hệ Claude cũng vậy: đọc trace (nhật ký từng bước) rồi mới quyết định sửa gì.

Trace là bản ghi từng bước agent làm: request gửi đi, tool nào được gọi, tool trả gì, câu trả lời cuối. Eval (đánh giá) là bộ ca có đáp án mong đợi, chạy lại mỗi lần bạn đổi gì đó.

Lỗi tầng tích hợp → sửa bằng code
  • HTTP 4xx/5xx, timeout
  • Parse JSON lỗi
  • tool_result thiếu tool_use_id
Lỗi đầu ra model → sửa bằng prompt
  • Chọn sai tool
  • Bịa, sai định dạng
  • Sửa bằng mô tả tool, schema, few-shot
  • Đọc trace từng bước (request, tool call, tool result) để biết lỗi bắt đầu ở đâu; đừng bắt Claude “sửa mò”.
  • Bộ eval: tập ca có kết quả mong đợi, chạy lại mỗi khi đổi prompt, model hay tool; đo chất lượng, độ trễ, chi phí.
  • Kết quả khác nhau giữa các lần chạy là đặc tính LLM: vẫn test, review; có bug thì đọc log trước.
Sai
  • Bảo Claude “thử sửa lại cho đúng” mà không xem trace
  • Đổi prompt rồi tự cảm thấy “có vẻ tốt hơn”
  • Bỏ test vì kết quả mỗi lần chạy hơi khác
Đúng
  • Đọc trace, xác định chặng lỗi đầu tiên
  • Chạy lại bộ eval sau mỗi thay đổi prompt, model hoặc tool
  • Vẫn test và review dù kết quả có biến động
Bẫy. Đừng nhầm lỗi tích hợp với lỗi đầu ra model. Timeout chữa bằng code (thử lại, giới hạn). Chọn sai tool chữa bằng mô tả tool. Dùng nhầm cách sẽ tốn công mà lỗi vẫn còn.

2.2 Từ một lỗi thành một ca eval

Sửa xong một lỗi mà không để lại dấu vết thì lỗi dễ quay lại. Quy trình:

  1. Đọc trace, tìm chặng lỗi đầu tiên.
  2. Thêm input gây lỗi vào golden dataset cùng đáp án mong đợi.
  3. Chạy eval: ca mới phải đỏ, các ca cũ giữ nguyên điểm.
  4. Sửa mô tả tool, schema hoặc prompt, chạy lại cả bộ.
  5. Ca mới xanh và các ca cũ không tụt thì mới giữ thay đổi.

Kết quả mỗi lần chạy có thể hơi khác nhau, nên xem tỷ lệ đạt của cả bộ ca thay vì một lần chạy của một ca.

Trace

Eval

Lỗi tích hợp

Thứ chấm điểm output: một model khác (model-based) hoặc code (code-based).

3.1 Vì sao cần eval

Có ba cách sau khi viết prompt: (1) thử một lần rồi đưa lên production, rủi ro cao; (2) thử vài lần và vá từng trường hợp lẻ, vẫn sót nhiều trường hợp biên; (3) chạy pipeline eval với dataset, grader và vòng lặp sửa, tốn công hơn nhưng đáng tin nhất. Eval tìm ra điểm yếu trước khi lên production.

3.2 Eval workflow

Năm bước cơ bản: (1) viết nháp prompt; (2) tạo dataset eval (3–100 ca thử); (3) chạy từng ca qua Claude; (4) chấm từng output (thang 1–10); (5) sửa prompt, chạy lại, so điểm trung bình.

def run_prompt(test_case, prompt_template):
    messages = [{"role": "user", "content": prompt_template.format(**test_case)}]
    return chat(messages)

def run_test_case(test_case, prompt_template):
    output = run_prompt(test_case, prompt_template)
    score = grade(test_case, output)   # 1-10
    return {"output": output, "test_case": test_case, "score": score}

def run_eval(dataset, prompt_template):
    results = [run_test_case(tc, prompt_template) for tc in dataset]
    avg = sum(r["score"] for r in results) / len(results)
    return results, avg

# So sánh 2 prompt versions
_, score_v1 = run_eval(dataset, PROMPT_V1)   # e.g. 7.66
_, score_v2 = run_eval(dataset, PROMPT_V2)   # e.g. 8.70 → V2 tốt hơn
Sai
  • Thử prompt một lần, thấy ổn là ship
  • Vá từng corner case khi gặp, không đo lại
  • Đổi nhiều thứ cùng lúc rồi không biết cái nào có tác dụng
Đúng
  • Chạy cả dataset, có điểm số trước và sau
  • Thay đổi một thứ mỗi lần, đo lại
  • Giữ phiên bản prompt có điểm trung bình cao hơn
Cốt lõi. Eval biến “có vẻ tốt hơn” thành một con số so sánh được. Dùng Haiku làm grader (rẻ), Sonnet làm producer.

3.3 Model-based grading

Grader là một lần gọi Claude để chấm output. Yêu cầu grader nêu điểm mạnh, điểm yếu, lập luận rồi mới cho điểm; thiếu phần lập luận thì điểm hay dồn quanh 6. Dùng Haiku làm grader (rẻ hơn), Sonnet làm producer:

def model_grader(task, output):
    response = chat([{"role": "user", "content": f"""
Evaluate this output for the task: {task}

Output: {output}

Provide:
1. Strengths
2. Weaknesses
3. Reasoning
4. Score (1-10): SCORE: X"""}], system="You are a strict quality evaluator.")
    # Parse score từ "SCORE: X"
    return int(response.split("SCORE:")[-1].strip().split()[0])

3.4 Code-based grading

Kiểm tra cú pháp và định dạng bằng code: nhanh và cho kết quả cố định:

def grade_syntax(output, format_type):
    """Returns 10 (valid) or 0 (invalid)"""
    try:
        if format_type == "json": json.loads(output); return 10
        elif format_type == "python": ast.parse(output); return 10
        elif format_type == "regex": re.compile(output); return 10
    except: return 0

def combined_score(task, output, format_type):
    syntax = grade_syntax(output, format_type)
    quality = model_grader(task, output)
    return (syntax + quality) / 2  # điều chỉnh weights theo use case

3.5 Đọc điểm: trung bình che gì

Với combined_score ở trên, điểm là trung bình của điểm cú pháp (0 hoặc 10) và điểm chất lượng (1 đến 10). Ba output minh hoạ:

OutputCú phápChất lượngĐiểm chung
JSON hợp lệ, nội dung tốt1099,5
JSON hợp lệ, nội dung tạm1078,5
JSON hỏng, nội dung tốt084
  • Output JSON hỏng vẫn được 4 điểm dù không dùng được. Nếu cú pháp là điều kiện bắt buộc, đặt điểm chung bằng 0 khi cú pháp sai thay vì lấy trung bình. Trọng số trong combined_score điều chỉnh theo từng trường hợp.
  • Điểm trung bình tăng có thể do một vài ca tăng mạnh trong khi vài ca tụt. Xem các ca thấp điểm nhất của bản prompt mới trước khi kết luận.
  • Đổi một thứ mỗi lần rồi đo lại, để biết thứ nào có tác dụng.
