1. Lab Ex1: agent hỗ trợ khách hàng có escalation

CCAR-F D1 CCAR-F D2 CCAR-F D5

Hình dung đời thường
Một nhân viên quầy được giao bốn việc: tra khách, tra đơn, hoàn tiền, chuyển cấp trên. Quầy có một quy định cứng: hoàn tiền trên $500 phải có quản lý ký. Quy định đó không nằm trong lời dặn miệng, mà nằm ở máy tính tiền: máy không cho in phiếu hoàn trên $500.

Mục tiêu: tự dựng một vòng lặp agent có tool, lỗi có cấu trúc, cổng chặn bằng code và escalation. Không cần gọi API thật; viết code và tự kiểm theo tiêu chí ở cuối mục. Domain: D1, D2, D5. Lý thuyết ở bài 03, bài 04, bài 07.

Bước 1: bốn tool, hai tool dễ nhầm

tools = [
  {"name": "get_customer",
   "description": "Look up a customer by email or phone and return a verified customer_id. "
                  "Use FIRST, before any order or refund action. Does not return orders.",
   "input_schema": {"type": "object", "properties": {
       "email": {"type": "string"}, "phone": {"type": "string"}}}},
  {"name": "lookup_order",
   "description": "Return one order's status and amount. Requires a verified customer_id "
                  "from get_customer and an order_id. Use for 'where is my order' questions.",
   "input_schema": {"type": "object", "properties": {
       "customer_id": {"type": "string"}, "order_id": {"type": "string"}},
       "required": ["customer_id", "order_id"]}},
  {"name": "process_refund", "description": "...", "input_schema": {...}},
  {"name": "escalate_to_human", "description": "...", "input_schema": {...}}
]

get_customer và lookup_order là cặp dễ nhầm. Mô tả nói rõ mỗi tool trả gì, dùng khi nào, cần gì đầu vào, và ranh giới "không trả đơn hàng".

Bước 2: vòng lặp dựa trên stop_reason

messages = [{"role": "user", "content": user_text}]
while True:
    resp = client.messages.create(model=MODEL, max_tokens=4096,
                                  system=SYSTEM, tools=tools, messages=messages)
    messages.append({"role": "assistant", "content": resp.content})
    if resp.stop_reason != "tool_use":          # end_turn: trả lời xong
        break
    results = [run_tool_with_gate(b) for b in resp.content if b.type == "tool_use"]
    messages.append({"role": "user", "content": results})   # mọi tool_result trong MỘT message

Bước 3: lỗi có cấu trúc

{"type": "tool_result", "tool_use_id": block.id, "is_error": true,
 "content": json.dumps({"errorCategory": "business",        # transient | validation | business | permission
                        "isRetryable": false,
                        "message": "Refunds above $500 need manager approval."})}

Bước 4: cổng chặn bằng code

def run_tool_with_gate(block):
    if block.name in ("lookup_order", "process_refund") and not session.verified_customer_id:
        return error(block, "validation", False, "Call get_customer first to verify the customer.")
    if block.name == "process_refund" and block.input["amount"] > 500:
        ticket = escalate_to_human(summary_for_human(block))       # chuyển luồng
        return error(block, "business", False, f"Escalated to a manager: ticket {ticket}.")
    return execute(block)

Trong Agent SDK, cùng logic này đặt ở hook PreToolUse (chặn hoặc chuyển hướng trước khi tool chạy). Hook là cơ chế tất định; dặn trong system prompt chỉ là xác suất.

Bước 5: tin nhắn nhiều vấn đề

Thử: "Đơn #123 chưa tới, đơn #456 bị trừ tiền hai lần, và tôi muốn đổi email." Agent nên tách ba việc, xử lý từng việc (tra đơn, kiểm tra trùng tiền, đổi thông tin), rồi trả một câu trả lời tổng hợp.

Tiêu chí tự kiểmĐạt khi
Chọn toolCâu "đơn của tôi đâu" luôn đi get_customer rồi lookup_order
Dừng vòng lặpDừng theo stop_reason, không theo chữ "xong" trong câu trả lời
LỗiTimeout thì thử lại; lỗi nghiệp vụ thì giải thích cho khách, không thử lại
CổngKhông có đường nào để hoàn tiền trên $500 hoặc khi chưa xác minh khách
Bàn giaoNgười nhận ca thấy customer_id, nguyên nhân, số tiền, đề xuất, không cần đọc transcript
Cốt lõi. Mô tả tool tốt cho việc chọn tool; stop_reason cho việc dừng; lỗi có cấu trúc cho việc phục hồi; code cho quy tắc bắt buộc.

2. Lab Ex2: cấu hình Claude Code cho cả đội

CCAR-F D3 CCAR-F D2

Hình dung đời thường
Một văn phòng có nội quy chung dán ở sảnh, quy định riêng dán ở cửa từng phòng, sổ tay quy trình để trên kệ, và tủ khoá cá nhân của từng người. Ai mới vào cũng thấy nội quy sảnh; tủ khoá cá nhân thì không ai khác thấy.

Mục tiêu: dựng cấu hình Claude Code mà mọi người clone repo đều nhận được đúng chuẩn. Domain: D3, D2. Lý thuyết ở bài 05.

# .claude/rules/testing.md
---
paths: ["**/*.test.*"]
---
Use the shared fixtures in tests/fixtures. One behavior per test.

# .claude/skills/deps/SKILL.md
---
name: analyze-deps
description: Analyze dependency graph and report outdated or risky packages.
context: fork
allowed-tools: Read, Grep, Glob
argument-hint: "[package-dir]"
---

// .mcp.json
{ "mcpServers": { "github": { "command": "github-mcp",
    "env": { "GITHUB_TOKEN": "${GITHUB_TOKEN}" } } } }
ThửKết quả mong đợi
Thành viên mới clone repoCó chuẩn code, lệnh /review, MCP GitHub (với token của chính họ)
Sửa src/api/users.tsChỉ rule API được nạp; sửa file test thì rule test được nạp
Chạy /analyze-depsKết quả dài nằm trong context riêng, hội thoại chính chỉ nhận tóm tắt
MCP cá nhân trong ~/.claude.jsonDùng được cùng lúc với server của project
Sửa một bug một file có stack traceLàm trực tiếp
Migration thư viện qua nhiều file, nhiều cách làm hợp lệPlan mode trước
Cốt lõi. "Cả đội", "khi clone repo" thì đặt ở project và commit. "Cá nhân", "thử nghiệm" thì đặt ở thư mục nhà. Quy ước theo loại file rải khắp repo thì dùng rule có paths.

3. Lab Ex3: pipeline trích xuất có cấu trúc

CCAR-F D4 CCAR-F D5

Hình dung đời thường
Nhập hoá đơn vào phần mềm kế toán: ô nào hoá đơn không có thì để trống, không tự bịa. Nhập sai định dạng ngày thì phần mềm báo lỗi và bạn sửa đúng ô đó. Hoá đơn nào mờ thì để riêng cho kế toán trưởng xem.

Mục tiêu: trích xuất bằng tool_use với JSON schema, validate và retry, xử lý theo lô, chuyển ca khó cho người. Domain: D4, D5. Lý thuyết ở bài 06, bài 07 §5.

{"name": "extract_invoice", "input_schema": {"type": "object",
  "properties": {
    "invoice_number": {"type": "string"},
    "due_date":       {"type": ["string", "null"]},       # có thể không có: nullable
    "category":       {"enum": ["goods", "services", "other", "unclear"]},
    "category_detail":{"type": ["string", "null"]},       # mô tả khi category = other
    "stated_total":   {"type": "number"},
    "calculated_total": {"type": "number"},
    "conflict_detected": {"type": "boolean"},
    "field_confidence": {"type": "object"}},
  "required": ["invoice_number", "category", "stated_total"]}}

Theo lô và SLA

100 tài liệu qua Message Batches, mỗi request có custom_id. Kết quả về không theo thứ tự: ghép bằng custom_id. Mục lỗi: chỉ gửi lại mục đó, có điều chỉnh (chia nhỏ tài liệu quá dài). Tính thời gian: chờ tới lần gửi lô + tối đa 24 giờ xử lý phải nằm trong SLA. Ví dụ SLA 30 giờ thì gửi lô ít nhất mỗi 6 giờ.

Tiêu chí tự kiểmĐạt khi
Trường không có trong tài liệuTrả null, không bịa
Loại ngoài danh sáchother kèm category_detail
RetryGhi lại lỗi nào sửa được qua retry, lỗi nào không
Few-shot2–4 ví dụ cho tài liệu cấu trúc khác nhau (trích dẫn nội dòng và thư mục, bảng và văn xuôi)
Người duyệtĐộ chính xác đo theo loại tài liệu và theo trường, lấy mẫu phân tầng, trước khi giảm duyệt tay
Cốt lõi. Schema loại lỗi cú pháp, không loại lỗi ngữ nghĩa. Nullable chống bịa. Retry chỉ có ích khi thông tin có trong tài liệu.

4. Lab Ex4: hệ nghiên cứu nhiều agent

CCAR-F D1 CCAR-F D5

Hình dung đời thường
Trưởng nhóm nghiên cứu giao hai trợ lý cùng lúc: một người tìm tài liệu trên mạng, một người đọc báo cáo nội bộ. Mỗi người nộp phiếu ghi chép có cột "nhận định, trích đoạn, nguồn, ngày". Ai không truy cập được nguồn thì ghi rõ đã thử gì và còn thiếu gì.

Mục tiêu: coordinator giao việc song song, truyền context rõ, giữ nguồn gốc, lan truyền lỗi có cấu trúc. Domain: D1, D2, D5. Lý thuyết ở bài 03, bài 07 §6.

# Coordinator: allowedTools phải có "Task" để tạo subagent (theo exam guide v1.0;
# docs Agent SDK hiện hành: allowedTools chỉ tự duyệt, tool Agent chạy dù không liệt kê)
options = ClaudeAgentOptions(allowed_tools=["Task"], agents={
    "web-search": AgentDefinition(description="Search the web for sources...",
                                  prompt="...", tools=["WebSearch", "WebFetch"]),
    "doc-analysis": AgentDefinition(description="Analyze internal reports...",
                                    prompt="...", tools=["Read", "Grep"])})
# Song song: coordinator phát HAI lời gọi Task trong CÙNG một response.
# Prompt cho subagent ghi rõ mọi thứ nó cần: câu hỏi, phạm vi, định dạng kết quả.
# Mỗi phát hiện của subagent
{"claim": "...", "evidence": "trích đoạn nguyên văn", "source": "URL hoặc tên tài liệu",
 "published": "2026-09-14"}
# Khi lỗi
{"status": "partial", "errorType": "timeout", "attemptedQuery": "...",
 "partialResults": [...], "alternatives": ["thử nguồn X"]}
Tiêu chí tự kiểmĐạt khi
Song songHai Task trong một response; thời gian giảm so với gọi lần lượt
ContextSubagent nhận đủ thông tin trong prompt, không dựa vào việc "thừa hưởng" hội thoại
Nguồn gốcBáo cáo cuối giữ cặp nhận định và nguồn
LỗiCoordinator nhận lỗi có cấu trúc, đi tiếp với kết quả một phần, ghi rõ phần thiếu
Mâu thuẫnHai nguồn uy tín khác số liệu: giữ cả hai kèm nguồn, tách phần đã xác lập và phần còn tranh cãi
Thực tế 11/2026 Trong Agent SDK hiện hành, tool tạo subagent có thể mang tên Agent; exam guide v1.0 dùng Task. Làm bài thi theo Task.

5. Phạm vi đề CCAR-F

CCAR-F D5 CCAR-F

Exam guide liệt kê rõ chủ đề có ra và không ra. Dùng danh sách "không ra" để không học thừa và để loại nhanh phương án nói về các chủ đề đó.

Có ra
  • Vòng lặp agent theo stop_reason; điều kiện dừng
  • Coordinator, subagent, phân rã, chạy song song, lặp tinh chỉnh
  • Truyền context cho subagent, lưu trạng thái, khôi phục bằng manifest
  • Thiết kế tool, tách hay gộp, đặt tên; resource và tool của MCP
  • Cấu hình MCP project và user, biến môi trường
  • Lỗi có cấu trúc, phục hồi tại chỗ trước khi đẩy lên
  • Escalation theo tiêu chí, tôn trọng yêu cầu khách, chính sách có khoảng trống
  • CLAUDE.md, @import, rules có glob, command, skill
  • Plan mode hay làm trực tiếp; tinh chỉnh lặp
  • Output qua tool_use, nullable, tool_choice; few-shot
  • Batches; tối ưu context; human review; nguồn gốc thông tin
Không ra
  • Fine-tuning, huấn luyện model riêng
  • Xác thực API, billing, quản lý tài khoản
  • Chi tiết ngôn ngữ lập trình, framework
  • Triển khai, host MCP server
  • Kiến trúc nội bộ, quá trình huấn luyện, Constitutional AI, RLHF
  • Embedding, vector database
  • Computer use, vision
  • Streaming, SSE
  • Rate limit, quota, tính giá
  • OAuth, xoay vòng key
  • Cấu hình AWS, GCP, Azure; benchmark
  • Chi tiết prompt caching (chỉ cần biết có); thuật toán tokenization
Bẫy. Phương án "dùng vector database", "chuyển sang streaming", "tăng rate limit" trong một câu CCAR-F hiếm khi là đáp án, vì chủ đề nằm ngoài phạm vi. Nhiều mục trong cột phải lại có trong CCDV-F (streaming, caching, rate limit): đừng mang suy luận CCAR-F sang CCDV-F.
