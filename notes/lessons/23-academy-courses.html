Delegation và Diligence là hai quyết định rộng (khi nào và cách dùng AI). Description và Discernment là hai việc làm lặp lại trong từng cuộc trao đổi: bạn mô tả, AI trả lời, bạn đánh giá, rồi mô tả lại tốt hơn. Phần giải thích đầy đủ nằm ở bài 15 §3.

Ví dụ chạy từng bước. Một nhân viên nhờ Claude tóm tắt hợp đồng nhà cung cấp.

  1. Delegation: tóm tắt giao cho AI; quyết định có ký hay không giữ lại cho người.
  2. Description: nêu sản phẩm (tóm tắt một trang), cách làm (liệt kê điều khoản phạt trước), tiêu chuẩn (cho người không chuyên luật).
  3. Discernment: đọc bản trả về, đối chiếu với hợp đồng, thấy thiếu điều khoản phạt, góp ý đúng chỗ thiếu, lặp lại tới khi đạt.
  4. Diligence: đọc lại toàn bộ trước khi chuyển cho sếp; thêm ghi chú có dùng AI nếu công ty yêu cầu.
Bẫy. Nhầm ý nghĩa của hai chữ D đầu. Description là nói với AI việc cần làm; Delegation là quyết định có giao việc đó cho AI hay không. Đề hay cho tình huống và hỏi bước nào đang bị bỏ qua.

  2. Grader bằng code so nhãn Claude trả về với nhãn đúng; phần cần đánh giá sắc thái thì thêm model chấm theo rubric.
  3. Đặt ngưỡng, ví dụ 90%. CI chạy eval mỗi khi prompt đổi và chặn merge nếu điểm thấp hơn ngưỡng.

15. Lưu ý ôn thi: Evals, Claude Code in Action, SDLC

Hình dung đời thường
Trước giờ thi, bạn ghi ra một tờ nhớ nhanh những chỗ dễ nhầm nhất. Ở bài này, chỗ nhầm nổi tiếng nhất là cái “bảo vệ” (exit code): chỉ một mã duy nhất thật sự chặn cổng.
CCAR-F D3 (20%), hook: nhớ mã 2 chặn, mã 1 không chặn. PreToolUse dùng để cưỡng chế. permissionDecision: allow/deny/ask. Phân biệt các permission mode. Thứ bậc CLAUDE.md (4 vị trí theo khoá học). Quy tắc two-strikes.
CCDV-F D4 (2,6%), eval: 5 bước chọn model, 3 loại grader, Batch API (custom_id, request_counts), lấy mẫu hằng đêm để bắt độ trôi. Sửa prompt trước khi nâng model.
Mẫu chính của SDLC: viết intent.md trước việc phức tạp, worktree song song cho việc song song, subagent kiểm tra để review độc lập, hook làm cổng duyệt.
Sai
  • “Hook thoát exit 1 sẽ chặn lệnh”
  • “Kết quả chưa tốt thì nâng model trước”
  • “Verifier nên dùng lại context của implementation cho nhanh”
Đúng
  • Chỉ exit 2 chặn
  • Iterate prompt trước, upgrade model sau
  • Subagent kiểm tra có context mới để review độc lập

15.1 Hook và quyền: nhớ bằng bảng

Hook là code chạy tất định, nên dùng cho quy tắc phải đúng 100%. Lời dặn trong CLAUDE.md chỉ là hướng dẫn, và Claude có thể bỏ sót. Chi tiết ở bài 13 §11.

Bẫy. Viết hook thoát exit 1 khi kiểm tra thất bại rồi tin rằng lệnh bị chặn. Chỉ exit 2 chặn.

17. Lưu ý ôn thi: Building with the Claude API

Hình dung đời thường
Trước giờ thi, bạn không đọc lại cả giáo trình mà xem bản đồ ôn tập: domain nào nặng điểm, ý nào hay bị hỏi. Các khối dưới đây là bản đồ đó, theo thứ tự trọng số.
CCDV-F D2 (33,1%), Applications and Integration: domain nặng nhất. Nắm chắc: tham số của messages.create (model, max_tokens, messages); cấu trúc response (content block, stop_reason, usage); các loại event của streaming; quản lý lịch sử hội thoại nhiều lượt; prompt caching (cache_control, breakpoint, số token tối thiểu, thứ tự xử lý tools → system → messages); Batch API (custom_id, hỏi trạng thái, giảm 50%); Files API (tải lên → file_id → dùng lại); code execution tool (Docker, không có mạng); web search tool (chuỗi type, max_uses, allowed_domains).
CCDV-F D5 (16,8%), chọn model: các bậc model (Fable, Opus, Sonnet, Haiku); khoảng temperature và việc hợp với từng khoảng; extended thinking (budget_tokens, tối thiểu 1024, ràng buộc với max_tokens); usage.input_tokens và output_tokens. Mẫu định tuyến theo chi phí: Haiku phân loại → Sonnet viết nháp → Opus chỉ cho việc phức tạp.
CCDV-F D6 (11%), prompt engineering: rõ ràng và trực tiếp (động từ hành động), cụ thể (tiêu chí chất lượng output và các bước xử lý), thẻ XML (khi nào cần), few-shot (trường hợp biên, ví dụ định dạng, lấy từ kết quả eval). Vòng eval lặp lại.
CCDV-F D8 (10,6%), tool và MCP: cấu trúc schema của tool (name, description, input_schema); tool_use block (id, name, input); tool_result block (tool_use_id, content, is_error); vòng tool nhiều lượt; fine-grained tool calling (eager_input_streaming); kiến trúc MCP (3 capability: tool, resource, prompt; 2 transport: stdio, HTTP).
CCAR-F D1 (27%), kiến trúc agent: workflow là các bước định sẵn (bạn điều khiển); agent là mục tiêu cộng tool (Claude điều khiển). Song song (async gather, gộp kết quả), nối chuỗi (mỗi bước một trọng tâm), định tuyến (phân loại → chuyên biệt), evaluator-optimizer (producer, grader, vòng lặp). Tự kiểm tra môi trường là vòng phản hồi cho agent.
CCAR-F D4 (20%), prompt và output có cấu trúc: output có cấu trúc qua tool_use với tool_choice={"type": "tool", "name": "..."}, model_json_schema() của Pydantic. Sửa prompt theo kết quả eval. Nối chuỗi để xử lý prompt có nhiều ràng buộc.

18. Tổng quan khoá Tool Use với Messages API

Hình dung đời thường
Bạn ngồi ở quán ăn. Bồi bàn (Claude) không tự nấu. Anh ta ghi phiếu gọi món rồi đưa vào bếp (code của bạn). Bếp nấu xong, đưa đĩa ra, bồi bàn mang đến bàn. Bài này là về cách viết phiếu gọi món đúng mẫu, cho bếp nấu nhiều món cùng lúc, và đỡ tốn tiền khi cứ đưa lại cùng một thực đơn dài mỗi lần.

Khóa Tool Use with the Messages API (9 bài) là khóa chuyên sâu nhất về tool design trên Claude Academy. Nội dung trực tiếp cho CCAR-F D2 (18%) và CCDV-F D8 (10,6%).

Bài 05 đã dạy phần nền: tool definition, tool_choice, client tool và server tool, lỗi có cấu trúc. Bài này đi tiếp: strict mode, gọi nhiều tool song song, và hai cách giảm chi phí (programmatic tool calling, prompt caching cho tool definitions).

Thuật ngữ
Tool use
Claude yêu cầu code của bạn chạy một hàm, rồi dùng kết quả để trả lời.
Messages API
API chính của Claude: bạn gửi danh sách tin nhắn, nhận câu trả lời.
stop_reason
Lý do Claude dừng: tool_use (đang chờ bạn chạy tool) hoặc end_turn (đã trả lời xong).
tool_use_id
Mã gắn một yêu cầu gọi tool với kết quả của nó, để khớp đúng cặp.
Cốt lõi. Claude chỉ đề nghị gọi tool. Code của bạn mới là bên chạy tool và gửi lại kết quả.

19. Lưu ý ôn thi: Tool Use với Messages API

CCAR-F D2 (18%): cấu trúc tool definition (name, description, input_schema, input_examples). Viết description 3–4 câu, nói khi nào dùng và khi nào không. Gộp tool trùng. Yêu cầu của strict mode (additionalProperties: false). Luồng gọi tool song song (gom hết → chạy song song → một user message).
CCDV-F D8 (10,6%): cách dùng tool_choice, server tool so với client tool, ép output có cấu trúc bằng tool_choice, Batch API, prompt caching cho tool definition. Biết dùng is_error: true khi tool lỗi.
Bẫy hay ra đề: khi Claude gọi nhiều tool song song, phải gửi TẤT CẢ kết quả trong MỘT user message (mảng các tool_result block), không phải mỗi kết quả một message. Và phải thêm assistant message (chứa response.content) vào messages trước user message chứa kết quả tool.
Bẫy hay gặp: thiếu additionalProperties: false khi dùng strict; throw exception thay vì is_error: true; tách mỗi tool_result một tin nhắn; quên thêm assistant message trước tin nhắn user; đặt cache_control ở tool đầu thay vì tool cuối.

19.1 Hình dạng đúng của message khi gọi tool song song

Claude trả hai khối tool_use trong cùng một response. Message tiếp theo phải theo đúng hình dạng sau: message assistant giữ nguyên response.content, rồi một message user duy nhất chứa mọi tool_result.

messages = [
    {"role": "user", "content": "Weather in Hanoi and Hue?"},
    {"role": "assistant", "content": response.content},
    {"role": "user", "content": [
        {"type": "tool_result", "tool_use_id": "toolu_01", "content": "31C"},
        {"type": "tool_result", "tool_use_id": "toolu_02", "content": "29C"},
    ]},
]
