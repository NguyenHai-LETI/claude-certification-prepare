1. Thứ bậc CLAUDE.md

CCAR-F D3 CCDV-F D3 CCDV-F D2 CCAR-P D7

Hình dung đời thường
Một nhân viên mới vào công ty gặp ba loại “nội quy”. Nội quy công ty dán ở sảnh, ai cũng đọc. Quy định riêng của phòng ban chỉ có hiệu lực khi bạn vào phòng đó. Sổ tay cá nhân của chính bạn thì chỉ bạn đọc. Nếu sếp ghi quy tắc quan trọng vào sổ tay của mình, nhân viên mới sẽ không bao giờ thấy nó. CLAUDE.md hoạt động y như vậy.

CLAUDE.md là một file markdown chứa chỉ dẫn cố định (lệnh build, quy ước code, “luôn làm X”). Claude Code đọc nó ở đầu mỗi phiên và đưa vào context (vùng nhớ làm việc của Claude trong phiên đó). Có ba cấp, mỗi cấp nằm ở một chỗ khác nhau nên người được thấy cũng khác nhau.

Thư mụcCLAUDE.md trong thư mục conCó

  • @import tham chiếu file ngoài để CLAUDE.md gọn; mỗi package chỉ import chuẩn liên quan.
  • /memory xem file memory nào đang được nạp: dùng khi hành vi không nhất quán giữa các phiên.
  • Định kỳ rà CLAUDE.md cho gọn và hết mâu thuẫn.

Sai
  • Ghi quy ước của cả đội vào ~/.claude/CLAUDE.md của mình
  • Thành viên mới clone repo nhưng Claude không biết quy ước
  • Một CLAUDE.md dài, nhiều mâu thuẫn
Đúng
  • Đặt quy ước chung ở CLAUDE.md của project rồi commit
  • Chỉ giữ sở thích cá nhân (ngôn ngữ trả lời, editor) ở cấp user
  • Tách chuẩn theo chủ đề, dùng @import, định kỳ rà lại
Tình huống hay ra. Thành viên mới không nhận được chỉ dẫn vì chỉ dẫn nằm ở cấp user của người khác.

  • Ngoài ba cấp của đề thi còn có CLAUDE.local.md (riêng bạn trong một project, nên gitignore) và CLAUDE.md managed policy do admin triển khai cho cả tổ chức.

  • Claude cũng đọc được AGENTS.md nếu repo dùng file này thay cho CLAUDE.md.

Exam guide v1.0 vẫn nói dùng /memory để xác minh file đã nạp: khi thi chọn theo exam guide.

2. Slash command và skill

CCAR-F D3 CCDV-F D3

Hình dung đời thường
Trong thư viện, trên kệ chỉ dán nhãn tên sách và một dòng mô tả. Bạn chỉ rút sách xuống khi cần. Skill hoạt động như vậy: Claude chỉ thấy tên và mô tả, và chỉ đọc cả “cuốn sách” khi việc đang làm khớp mô tả. Còn CLAUDE.md giống nội quy dán tường: ai vào cũng thấy, lúc nào cũng thấy.

Slash command là lệnh bạn gõ bắt đầu bằng / (ví dụ /review) để chạy một prompt đã soạn sẵn. Skill là một thư mục có file SKILL.md mô tả một quy trình làm việc; Claude tự nạp khi thấy việc phù hợp, hoặc bạn gọi bằng /tên-skill.

Project (chia sẻ qua git)User (cá nhân)
Command.claude/commands/~/.claude/commands/
Skill.claude/skills/<tên>/SKILL.md~/.claude/skills/

Ví dụ command đơn giản nhất: file .claude/commands/review.md chứa một prompt, và cả đội gõ /review là dùng được vì file nằm trong git.

---
name: analyze-deps
description: Phân tích phụ thuộc của repo. Dùng khi người dùng hỏi về thư viện lỗi thời,
  xung đột phiên bản hoặc nói "kiểm tra dependency".
context: fork             # chạy trong context subagent riêng, output dài không làm bẩn phiên chính
allowed-tools: Read, Grep, Bash
argument-hint: [thư mục]  # gợi ý tham số khi gọi mà không truyền đối số
---

  • Thân skill chỉ nạp khi được kích hoạt (progressive disclosure); giữ SKILL.md gọn, tách chi tiết sang file phụ.

3. Rule theo đường dẫn

CCAR-F D3

Hình dung đời thường
Trong xưởng, biển “đeo kính bảo hộ” chỉ treo ở khu máy cắt, không treo ở văn phòng. Ai bước vào khu máy cắt mới cần biết quy tắc đó. Rule theo đường dẫn cũng vậy: chỉ khi Claude làm việc với loại file đó, quy tắc mới được nạp.

Rule là một file markdown trong .claude/rules/, mỗi file một chủ đề. Dòng paths ở đầu file là một danh sách glob (mẫu khớp tên file, ví dụ *.test.tsx khớp mọi file test). Rule có paths chỉ nạp khi Claude làm việc với file khớp mẫu.

---
paths: ["**/*.test.tsx"]
---
Quy ước viết test: …
  • File trong .claude/rules/ tách chuẩn theo chủ đề (testing.md, api-conventions.md).
  • Rule có paths chỉ nạp khi Claude làm việc với file khớp glob (exam guide viết “khi sửa”; xem ghi chú bên dưới), tiết kiệm context.
  • Rule theo glob thắng CLAUDE.md thư mục con khi quy ước áp cho file rải khắp codebase (test nằm cạnh code).
Quy ước nằm ở…ChọnLý do
Một thư mục (terraform/)CLAUDE.md trong thư mục đó, hoặc rule với paths: ["terraform/**/*"]File cùng chỗ
File rải nhiều thư mục (mọi *.test.tsx)Rule với glob **/*.test.tsxCLAUDE.md từng thư mục sẽ phải chép lặp
Thực tế 11/2026 Theo tài liệu memory: rule có paths nạp khi Claude dùng tool Read, Write hoặc Edit trên file khớp, và cả khi Claude xem file bằng lệnh Bash được tính là đọc (ví dụ cat hoặc head trên một file). Vậy Claude không cần sửa file thì rule vẫn nạp; đáp án đề nói “khi sửa file khớp” vẫn đúng. Rule không có paths thì nạp ngay lúc khởi động, cùng mức ưu tiên với .claude/CLAUDE.md. Mẫu trong paths tính từ thư mục chứa thư mục .claude của rule dự án.
Bẫy. Đặt một CLAUDE.md trong mỗi thư mục có file test để áp quy ước test. Quy ước bị chép nhiều chỗ, dễ lệch, và sót thư mục mới. Rule theo glob giải quyết gọn một lần.

4. Plan mode hay làm trực tiếp

CCAR-F D3

Hình dung đời thường
Sửa bóng đèn hỏng thì bạn thay luôn, không cần bản vẽ. Xây thêm một tầng nhà thì phải có bản vẽ, khảo sát móng và chủ nhà duyệt trước khi đổ bê tông. Làm sai ở bản vẽ chỉ tốn một tờ giấy, làm sai khi xây thì tốn cả tầng. Plan mode là bước “vẽ bản vẽ” cho Claude.

Plan mode là chế độ Claude chỉ đọc code và lập kế hoạch, chưa sửa file nào. Bạn xem kế hoạch, đồng ý rồi mới chuyển sang làm trực tiếp (direct execution: để Claude sửa file ngay).

Plan mode
  • Thay đổi lớn, nhiều file (migration 45+ file)
  • Quyết định kiến trúc, nhiều hướng hợp lệ
  • Tách monolith thành microservice
Làm trực tiếp
  • Phạm vi rõ: bug một file có stack trace
  • Thêm một điều kiện kiểm tra
  • Kết hợp: plan để điều tra và thiết kế, rồi làm trực tiếp theo kế hoạch.
  • Explore subagent cô lập phần dò tìm dài dòng, chỉ trả tóm tắt, tránh cạn context.

Ví dụ: đội muốn đổi thư viện HTTP ở 45 file. Dùng plan mode để Claude tìm mọi chỗ dùng, đề xuất thứ tự đổi và rủi ro. Sau khi bạn duyệt, làm trực tiếp từng nhóm file. Ngược lại, “thêm kiểm tra ngày hợp lệ vào hàm parseDate” là việc một file, rõ phạm vi, nên làm trực tiếp.

Bẫy. “Bắt đầu làm trực tiếp, gặp khó mới chuyển plan” khi đề đã nói rõ việc phức tạp.
Thuật ngữ
Migration
Việc chuyển cả code sang thư viện hoặc phiên bản mới, thường chạm nhiều file.
Monolith / microservice
Một ứng dụng nguyên khối, và các dịch vụ nhỏ tách riêng. Tách cái trước thành cái sau là quyết định kiến trúc lớn.
Explore subagent
Subagent có sẵn chuyên đọc và tìm trong code, trả về bản tóm tắt.

5. Tinh chỉnh lặp

CCAR-F D3

Hình dung đời thường
Bạn nhờ thợ may “may áo vừa vặn” thì mỗi người hiểu một kiểu. Đưa chiếc áo mẫu và số đo cụ thể thì thợ làm đúng ngay. Sau đó thử áo, chỉ chỗ chật, thợ sửa, thử lại, cho đến khi vừa. Làm việc với Claude cũng là vòng lặp “thử, chỉ chỗ sai, sửa”.

Tinh chỉnh lặp (iterative refinement) là cải thiện kết quả qua nhiều vòng nhỏ thay vì mong một lần đúng ngay. Có bốn kỹ thuật chính.

  • Mô tả bằng lời bị hiểu không nhất quán → đưa 2–3 ví dụ vào/ra cụ thể.
  • TDD: viết test trước (hành vi, biên, hiệu năng), lặp bằng cách đưa lỗi test cho Claude.
  • Interview pattern: để Claude hỏi lại nhằm lộ ra điều chưa nghĩ tới trước khi làm ở lĩnh vực lạ.
  • Lỗi tương tác nhau gửi chung một tin nhắn; lỗi độc lập sửa lần lượt.

5.1 Ví dụ vào/ra thay cho lời mô tả

Câu “chuẩn hoá ngày tháng” có thể hiểu nhiều cách. Ba ví dụ cụ thể giúp Claude hiểu đúng, kể cả trường hợp biên như null:

"12/03/2024" -> "2024-03-12"
"1/2/2024"   -> "2024-02-01"
null         -> null            # biên: không được báo lỗi

Interview pattern hợp khi bạn làm trong lĩnh vực chưa quen, ví dụ cache. Bạn nhờ: “Trước khi viết code, hãy hỏi tôi về cách làm mất hiệu lực cache và các kiểu lỗi có thể xảy ra.” Câu hỏi của Claude giúp bạn nghĩ ra điều mình chưa nghĩ tới.

Sai
  • Viết “xử lý ngày tháng cho tốt” rồi sửa mỗi lần Claude hiểu khác
  • Hai lỗi liên quan nhau mà báo từng cái, Claude vá cái này làm hỏng cái kia
Đúng
  • Đưa 2–3 ví dụ vào/ra cụ thể, gồm cả trường hợp biên

Cốt lõi. Ví dụ cụ thể thắng mô tả bằng lời. Test cho Claude một thước đo khách quan. Interview pattern lộ ra yêu cầu ẩn trước khi code. Lỗi liên quan nhau thì xử lý cùng lúc.
Thuật ngữ
TDD (test-driven development)
Viết test trước, rồi viết code cho đến khi test qua.
Trường hợp biên (edge case)

7. Claude Code trong CI/CD

Hình dung đời thường
Nhà máy có một dây chuyền kiểm tra chạy tự động lúc nửa đêm. Không ai đứng đó để bấm nút “đồng ý”. Nếu một máy dừng lại chờ người xác nhận, cả dây chuyền treo. Vì vậy mọi thứ máy được phép làm phải khai báo sẵn, và kết quả phải ghi theo mẫu để máy khác đọc được. Claude Code trong CI cũng thế.

CI/CD là hệ thống tự chạy build, test, review mỗi khi có code mới. Headless mode là chạy claude không có người ngồi tương tác. Cờ -p bật chế độ này.

claude -p "Review the diff for security issues" \
  --output-format json --json-schema review.schema.json \
  --allowedTools "Read,Grep,Glob"
  • -p / --print: chạy không tương tác, không treo chờ input. --output-format json hoặc stream-json.
  • Trong CI không ai bấm duyệt: quyền phải khai báo sẵn, ở mức tối thiểu.
  • CLAUDE.md cung cấp chuẩn test, fixture, tiêu chí review cho Claude chạy trong CI.
  • Phiên đã sinh code review kém hơn một phiên độc lập.
  • Review lại sau commit mới: đưa kết quả review cũ vào, chỉ báo lỗi mới hoặc chưa sửa.
  • Sinh test: đưa file test hiện có vào context để tránh trùng kịch bản.
  • Phiên: --continue tiếp phiên gần nhất, --resume chọn phiên theo tên.
Sai
  • CI chạy claude không có -p, job treo chờ input
  • Nhờ phiên vừa viết code tự review code đó
  • Mỗi lần review lại đăng cả lỗi cũ, comment lặp
Đúng

  • Phiên review độc lập, đã có CLAUDE.md về tiêu chí
  • Đưa kết quả review cũ vào, chỉ báo lỗi mới hoặc chưa sửa

8. Settings và quyền

CCDV-F D2 CCDV-F D3 CCAR-P D7

Hình dung đời thường
Trong tòa nhà, có luật của chính quyền, nội quy của ban quản lý, và quy định riêng của từng căn hộ. Luật của chính quyền thắng tất cả. Còn thẻ ra vào thì có ba loại quyền: “cấm vào”, “phải hỏi bảo vệ”, “cho vào”. Bảo vệ kiểm tra theo thứ tự cấm trước, rồi hỏi, rồi mới cho, nên đã bị cấm thì không giấy cho phép nào cứu được.

Settings là file JSON cấu hình Claude Code. Permissions (quyền) là phần quyết định tool nào Claude được chạy mà không hỏi, phải hỏi, hoặc bị chặn. Có bốn nơi đặt settings.

FilePhạm viCommit?

  • Ưu tiên từ cao xuống thấp: managed → tham số dòng lệnh → local → project → user.
  • permissions có allow, ask, deny, đánh giá theo thứ tự deny → ask → allow; luật khớp đầu tiên theo thứ tự đó quyết định, độ cụ thể của luật không đổi được thứ tự. Deny luôn thắng: deny ở bất kỳ cấp nào chặn allow ở cấp khác; allow không “khoét” ngoại lệ trong deny. Tương tự, một luật ask vẫn hỏi dù có allow cụ thể hơn.
  • Danh sách như permissions.allow gộp giữa các cấp, không thay thế nhau. Khoá đơn (như model) thì cấp cao hơn thắng.
  • Allow trong .claude/settings.json của project chỉ có hiệu lực sau khi từng người tin cậy thư mục (workspace trust); deny và ask áp dụng ngay.
  • Quyết định của hook PreToolUse không vượt qua được luật deny, ask.

// .claude/settings.json
{ "permissions": {
    "allow": ["Bash(npm test:*)", "Read"],
    "deny":  ["Bash(rm -rf:*)", "Bash(terraform destroy:*)", "Read(./.env)"] } }

Trong ví dụ trên, cả đội chạy được npm test và đọc file mà không bị hỏi. Lệnh xoá hàng loạt, phá hạ tầng và đọc file .env (chứa bí mật) bị chặn hẳn, dù cá nhân nào đó có allow ở file local của họ.

8.1 Cú pháp một luật quyền

Mỗi phần tử trong allow, ask, deny là một luật nêu tên tool và, trong ngoặc, phạm vi của nó. File settings là JSON chặt: một dòng chú thích // hay dấu phẩy thừa làm Claude Code báo lỗi file ở lần khởi động sau. Dòng // .claude/settings.json trong ví dụ phía trên chỉ là nhãn tên file cho người đọc.

LuậtKhớp với
Bash(npm run lint)Đúng lệnh npm run lint
Bash(npm run test *)Lệnh bắt đầu bằng npm run test, kèm tham số bất kỳ
Read(./.env)Việc đọc file .env ở thư mục làm việc
Read(./.env.*)Các file như .env.local, .env.production

Ví dụ để cho phép lint, test mà không hỏi và chặn đọc file chứa bí mật: allow hai luật Bash ở trên, deny hai luật Read. Vì deny luôn thắng, không luật allow nào ở cấp khác mở lại được việc đọc .env.

Sai
  • Deny ở project, rồi allow cụ thể hơn ở local và tin rằng allow sẽ “mở” ngoại lệ
  • Cho rằng luật cụ thể hơn thì thắng
Đúng
  • Deny ở bất kỳ cấp nào vẫn chặn. Muốn mở lại thì gỡ luật deny
  • Thứ tự cố định deny → ask → allow, độ cụ thể không đổi thứ tự
Cốt lõi. Danh sách quyền gộp giữa các cấp, khoá đơn thì cấp cao hơn thắng. Trong quyền, deny luôn thắng.

9. Chế độ quyền và auto mode

CCDV-F D3

Hình dung đời thường
Nhân viên mới làm gì cũng hỏi sếp. Nhân viên lâu năm được tự làm việc thường ngày, chỉ hỏi khi có việc bất thường. Có công ty còn thuê kiểm soát viên đứng cạnh: nhân viên tự làm, nhưng việc nào vượt quá yêu cầu thì kiểm soát viên chặn lại.

Bài 13 §8 đã có luật allow, ask, deny. Chế độ quyền (permission mode) đặt mức nền, còn luật thì chồng lên trên mức nền đó.

Chế độChạy không cần hỏiHợp với
default (Manual)Chỉ đọcViệc nhạy cảm, muốn duyệt từng bước
acceptEditsĐọc, sửa file, lệnh file thông dụng (mkdir, mv, cp)Đang lặp trên code bạn tự review
planĐọc (và lệnh được classifier duyệt nếu có auto mode)Khám phá codebase trước khi sửa

Auto mode hoạt động như sau:

  • Một model classifier riêng xem từng hành động trước khi chạy. Nó chặn việc vượt quá yêu cầu của bạn, việc nhắm vào hạ tầng lạ, và việc có vẻ bị nội dung độc hại Claude vừa đọc điều khiển (prompt injection).
  • Luật ask vẫn bắt hỏi; luật deny chặn ở mọi chế độ, kể cả bypassPermissions.
  • Hành động bị chặn hiện trong /permissions ở mục Recently blocked. Bạn duyệt ở đó thì Claude được thử lại.
  • Bị chặn 3 lần liên tiếp hoặc 20 lần tổng cộng thì auto mode tạm dừng và Claude Code quay lại hỏi bạn.
  • Admin Team, Enterprise tắt được cho cả tổ chức bằng permissions.disableAutoMode trong managed settings.

Sai
Bật auto mode cho việc xoá dữ liệu production vì "đã có classifier lo".
Đúng

Cốt lõi. Chế độ là mức nền, luật là ngoại lệ chồng lên. Deny thắng mọi chế độ. Auto mode thay việc bấm duyệt bằng một classifier, không thay việc review thao tác nguy hiểm.
Thực tế 11/2026 Agent SDK xét một lời gọi tool qua sáu bước theo thứ tự: hook, luật deny, luật ask, permission mode, luật allow, rồi callback canUseTool. Hook trả allow không bỏ qua được luật deny và ask. Tool đã được duyệt ở bước trước (bởi acceptEdits, bypassPermissions hay luật allow) không bao giờ tới canUseTool, nên kiểm tra đặt trong callback bị bỏ qua lặng lẽ với tool đó; cần kiểm mọi lời gọi thì dùng hook PreToolUse. Muốn gỡ hẳn một tool thì dùng deny theo tên trần (disallowed_tools=["Bash"] xoá định nghĩa tool khỏi request); deny có phạm vi như Bash(rm *) thì giữ tool và chặn lệnh khớp ở mọi chế độ. Plugin gói command, skill, agent, hook, MCP server để cài một lần cho nhiều dự án, phân phối qua marketplace. Hợp khi một đội nền tảng muốn nhiều repo dùng chung một bộ công cụ.

Nói chính xác hơn, một plugin là một thư mục chứa skill, agent, hook, MCP server hoặc thành phần khác, và Claude Code cài rồi nạp cả thư mục như một khối. Plugin thường có manifest: file JSON ở .claude-plugin/plugin.json, đặt tên cho plugin (dạng kebab-case) và có thể thêm version, mô tả. Manifest là tuỳ chọn. Thiếu nó thì Claude Code nạp các thành phần theo bố cục chuẩn, và lấy tên từ marketplace hoặc từ tên thư mục.

10.3 Bật plugin tốn gì và cần cân nhắc gì

Plugin đã bật là một phần của mọi phiên, không chỉ phiên bạn dùng đến nó. Có ba hệ quả.

  • Context: với mỗi skill, agent, command mà Claude có thể tự gọi, tên và mô tả luôn nằm trong context ở mọi lượt. Cài nhiều plugin thì context bớt chỗ và tốn usage.
  • Tiến trình: MCP server của plugin chạy cạnh mỗi phiên bật nó, và hook của nó chạy ở các sự kiện.
  • Quyền: plugin chạy với quyền của chính bạn. Hãy đọc kỹ plugin của bên thứ ba trước khi cài, vì nó chạy được code với quyền user của bạn.

Muốn ngưng một plugin mà chưa gỡ, tắt bằng /plugin hoặc claude plugin disable.

11.1 Plan mode, compact, rewind

Plan mode: Nhấn Shift+Tab (hoặc gõ /plan) để bật — Claude đọc/phân tích nhưng không viết code. Dùng để review kế hoạch trước khi thực thi. Nhấn lại để tắt.

Thu gọn hội thoại: dùng /compact khi context đầy; Claude tóm tắt lịch sử hội thoại để giải phóng context window. Có thể kèm lời dặn trọng tâm cho bản tóm tắt: /compact Focus on the database schema changes.

Rewind: Nếu Claude đi sai hướng, nhấn Escape để dừng, sau đó dùng /rewind để quay về checkpoint trước. Checkpoint tạo tự động trước mỗi bước quan trọng.

Thực tế 11/2026 Tài liệu hiện hành mô tả Shift+Tab là phím xoay vòng các permission mode (default, acceptEdits, plan, rồi auto nếu có), và khởi động thẳng vào plan bằng claude --permission-mode plan. Checkpoint được tạo trước mỗi prompt bắt đầu một lượt; /rewind (bí danh /undo) hoặc nhấn Esc hai lần mở menu gồm: khôi phục code và hội thoại, chỉ hội thoại, chỉ code, hoặc “Summarize”. File chỉ bị đổi bởi lệnh Bash không được theo dõi, vì vậy checkpoint không thay thế git. Chưa tìm thấy lệnh /plan trong trang tài liệu đã tra; vẫn giữ theo bài giảng. 11.2 Thứ bậc CLAUDE.md theo khoá học

Mục 1 trình bày ba cấp theo exam guide. Khoá học liệt kê bốn vị trí, theo thứ tự ưu tiên dưới đây; chỗ khoá học khác tài liệu hiện hành xem khối Thực tế ngay sau hình.

  1. ~/.claude/CLAUDE.md — global, áp dụng mọi project

11.3 Hook và quyền

Hình dung đời thường
Cổng kiểm soát ở kho hàng. Bảo vệ nhận phiếu lấy hàng, xem xét, rồi làm một trong ba việc: vẫy tay cho qua (exit 0), nhắc nhở nhưng vẫn cho qua (exit 1), hoặc chặn lại và nói lý do (exit 2). Chỉ có “chặn lại” mới thật sự giữ hàng ở trong kho.

Hooks = shell script chạy trước/sau khi Claude dùng tool. Cấu hình trong .claude/settings.json:

{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{
        "type": "command",
        "command": "node scripts/safety-check.js"
      }]
    }]
  }
}

Hook nhận input của tool qua stdin (JSON) và có thể:

  • Cho qua: thoát với mã 0, không in gì
  • Chặn: thoát với mã 2 và in lý do. Mã 1 KHÔNG chặn, chỉ mã 2 mới chặn.
  • Ask: output JSON {"permissionDecision": "ask", "message": "..."}
#!/bin/bash
# hooks/redact-secrets.sh — hook PreToolUse để redact PII trước khi log
INPUT=$(cat)
TOOL=$(echo "$INPUT" | jq -r '.name')
if [ "$TOOL" = "Bash" ]; then
    COMMAND=$(echo "$INPUT" | jq -r '.input.command')
    # Check for secret patterns
    if echo "$COMMAND" | grep -qE "(password|secret|token|key)="; then
        echo '{"permissionDecision":"ask","message":"Command contains potential secrets. Review before proceeding."}'
        exit 0
    fi
fi
exit 0

Script này đọc JSON từ stdin, lấy tên tool và lệnh. Nếu lệnh Bash chứa mẫu như password= hoặc token=, nó in JSON “ask” rồi exit 0: Claude Code sẽ hỏi bạn trước khi chạy. Ngược lại nó thoát 0 và không in gì, tức cho qua.

Permission mode (theo khoá học): default (hỏi mọi thứ), auto-approve (tự duyệt mọi thứ), bypassPermissions (không hỏi gì, chỉ dùng trong CI có sandbox).

Bẫy. Viết hook chặn nhưng dùng exit 1. Hook báo lỗi, nhưng lệnh vẫn chạy. Muốn chặn phải exit 2.
Thực tế 11/2026 Tài liệu hooks hiện hành xác nhận: exit 2 là cách chặn; mọi mã khác (kể cả 1) là “non-blocking error”, hành động vẫn đi tiếp. Muốn trả quyết định bằng JSON thì phải thoát exit 0; nếu thoát 2 thì JSON allow cũng không mở được cổng. JSON đầu vào của hook dùng khóa tool_name và tool_input (ví dụ tool_input.command), khác với .name và .input.command trong ví dụ trên. Về permission mode, tài liệu liệt kê: default, acceptEdits, plan, auto, dontAsk, bypassPermissions; bypassPermissions chỉ nên dùng trong container hoặc VM cô lập. Đề thi theo ba mode như bài. Nguồn: Hooks reference, Permission modes.

11.4 Tác vụ định kỳ và chế độ headless

Hình dung đời thường
Máy giặt hẹn giờ: bạn bỏ đồ vào, bấm nút, máy tự chạy lúc 6 giờ sáng mà không cần bạn đứng cạnh. Headless mode là Claude Code chạy “không màn hình”, không hỏi gì giữa chừng. Scheduled task là hẹn giờ cho nó.

Chế độ headless: chạy Claude Code không cần tương tác, dùng trong script, CI, cron job.

# -p: prompt text
# --bare: output chỉ content (không có markdown formatting)
# --output-format json: machine-readable output
claude -p "Review these test failures and suggest fixes" \
       --input-file test-results.txt \
       --bare \
       --output-format json > review.json

# Chạy từ Agent SDK (Python)
result = subprocess.run(
    ["claude", "-p", task_description, "--bare"],
    capture_output=True, text=True, cwd=project_dir
)

Tác vụ định kỳ: dùng lệnh /schedule trong Claude Code (hoặc claude schedule create) để tạo cron job chạy trên cloud. Cũng có thể dùng GitHub Actions với trigger schedule.

Cron là cách viết lịch lặp bằng năm trường: phút, giờ, ngày trong tháng, tháng, thứ. Ví dụ 0 9 * * 1-5 là 9 giờ sáng các ngày trong tuần.

Thực tế 11/2026 Trang tài liệu hiện hành mô tả --bare theo nghĩa khác bài: nó bỏ qua việc tự nạp hook, skill, subagent, plugin, MCP server, auto memory và CLAUDE.md để chạy giống nhau trên mọi máy; không phải “chỉ in nội dung”. Dạng gọi là claude --bare -p "…", và bare mode không dùng đăng nhập subscription nên cần ANTHROPIC_API_KEY. Đưa dữ liệu vào bằng pipe stdin (cat file | claude -p "…"), tôi chưa thấy cờ --input-file trong trang đã tra. Về lịch chạy, tài liệu liệt kê cloud scheduled tasks (routines), Desktop scheduled tasks, /loop trong phiên, và GitHub Actions; tôi chưa kiểm chứng được lệnh /schedule hay claude schedule create. Nguồn: Headless, Scheduled tasks.

11.5 Tích hợp GitHub Actions

Hình dung đời thường
Mỗi khi ai đó nộp bài (mở pull request), một người chấm tự động được gọi tới, đọc bài, rồi ghi nhận xét lên chính tờ bài. Bạn không phải nhắc. GitHub Actions là chuông báo, Claude là người chấm. 
# .github/workflows/claude-review.yml
name: Claude Code Review
on:
  pull_request:
    types: [opened, synchronize]

jobs:
  review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Claude Code Review
        uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          github_token: ${{ secrets.GITHUB_TOKEN }}
          review_type: "security,performance,correctness"
          post_as_comment: true

Dịch vụ Claude Code Review: Anthropic chạy hộ, kích hoạt qua GitHub App, bạn không phải tự host. Cấu hình bằng CLAUDE.md trong repo hoặc cài đặt riêng cho review.

Thực tế 11/2026 Trang GitHub Actions hiện hành dùng các input anthropic_api_key (hoặc claude_code_oauth_token), prompt và claude_args; chưa thấy review_type và post_as_comment trong tài liệu đã tra. Workflow mẫu hiện dùng actions/checkout@v6 và id-token: write cho xác thực GitHub App mặc định. Khi workflow có prompt, Claude chạy ở chế độ automation; không có prompt thì chờ nhắc @claude. Trang này cũng tách “Code Review” (review tự động, không viết workflow) thành sản phẩm riêng. Ví dụ ở trên vẫn giữ theo bài giảng. Nguồn: Claude Code GitHub Actions.
Bẫy. Dán API key thẳng vào file workflow. Luôn dùng ${{ secrets.… }}, và cấp permissions vừa đủ.
