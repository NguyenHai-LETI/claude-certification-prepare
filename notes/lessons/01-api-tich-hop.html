1. Bức tranh chung

Hình dung đời thường
Claude giống một đầu bếp giỏi. Bạn có thể gặp đầu bếp ở nhà hàng (gọi món có sẵn, không cần biết bếp chạy thế nào), hoặc thuê đầu bếp về bếp nhà mình (cho dụng cụ, nguyên liệu, quy tắc riêng), hoặc đặt nguyên liệu và công thức qua cửa sổ giao hàng để tự dựng món trong quán của mình. Cùng một đầu bếp, ba cách làm việc khác nhau. Ba cách đó là ba bề mặt của Claude.

Claude không chỉ là một chatbot mà là một hệ sinh thái: mô hình là bộ não, công cụ tìm kiếm và trình duyệt là đôi mắt, khả năng tạo code, tài liệu là đôi tay, MCP là hệ thần kinh nối ra hệ thống ngoài, Skills lưu quy trình, Memory và Projects giữ bối cảnh. Một bề mặt (surface) là nơi bạn gặp Claude. Có ba bề mặt chính:

Bề mặtDùng choSystem prompt
claude.ai, Desktop, di độngNgười dùng cuối, nghiệp vụ (CCAO-F)Có system prompt riêng của Anthropic
Claude Code, Agent SDKAgent lập trình trong terminal, IDE, CINạp thêm CLAUDE.md, skill, rule
Claude API (Messages API)Nhà phát triển tích hợp vào ứng dụngChỉ những gì bạn gửi

Mọi thứ qua API đều đi qua một endpoint POST /v1/messages. Một endpoint là một địa chỉ URL mà chương trình của bạn gửi yêu cầu tới. Tool, output có cấu trúc, thinking là tính năng của endpoint này; Batches, Files, đếm token là endpoint hỗ trợ.

Cốt lõi. Trên claude.ai, Anthropic đã viết sẵn system prompt cho bạn. Trên API thì không có gì ngoài những gì bạn gửi. Vì vậy cùng một câu hỏi có thể cho kết quả khác nhau giữa claude.ai và API.
Thuật ngữ
Model
“Bộ não” đã được huấn luyện, nhận chữ vào và sinh chữ ra.
API
Cửa để chương trình của bạn nói chuyện với một dịch vụ khác. Ở đây là dịch vụ của Anthropic.

Lời dặn nền cho model: vai trò, quy tắc lâu dài. Người dùng thường không thấy.
Agent SDK
Bộ thư viện để bạn tự dựng một agent chạy giống Claude Code.

2. Cấu trúc request

CCDV-F D2

Hình dung đời thường
Bạn nhắn tin cho một người bạn mắc chứng quên tức thì. Mỗi lần nhắn, người đó trả lời rất hay, nhưng ngay sau đó quên sạch. Muốn tiếp tục câu chuyện, bạn phải dán lại toàn bộ đoạn chat từ đầu rồi viết thêm câu mới. API của Claude hoạt động đúng như vậy.

Một request là gói dữ liệu JSON bạn gửi tới API. JSON là định dạng chữ có cặp khoá và giá trị. Gói này có các phần sau:

{
  "model": "claude-…",            // ghim ID cụ thể ở production
  "max_tokens": 1024,             // bắt buộc
  "system": "Bạn là trợ lý …",    // tham số riêng, không phải một message
  "messages": [                   // xen kẽ user / assistant
    {"role": "user", "content": "…"}
  ],
  "tools": [ … ], "tool_choice": {"type": "auto"},
  "stop_sequences": ["###"]
}
  • model: chọn model nào xử lý. max_tokens: trần số token model được viết; bắt buộc.
  • system: lời dặn nền. Nó là tham số riêng ở cấp cao nhất, không nằm trong messages.
  • messages: lịch sử hội thoại. Phần tử xen kẽ user và assistant.
  • tools, tool_choice: danh sách hàm Claude được phép xin gọi, và cách chọn (xem bài 04).
  • stop_sequences: chuỗi chữ mà khi model viết ra thì dừng ngay.

Ví dụ chạy hai lượt để thấy API không nhớ gì:

Cốt lõi. API không lưu trạng thái: mỗi request phải gửi lại toàn bộ lịch sử cần thiết. system là tham số cấp cao nhất cho vai trò và quy tắc lâu dài; messages chứa việc cụ thể và dữ liệu.
Sai
  • Truyền conversation_id để API nhớ hội thoại
  • Bật prompt caching để API nhớ hội thoại
  • Nhét system thành một message role system trong messages
Đúng
  • Tự lưu lịch sử và gửi lại mỗi request
  • Cache chỉ giảm chi phí cho tiền tố lặp lại, không tạo trí nhớ
  • system là tham số riêng ở cấp cao nhất
Bẫy. “Truyền conversation_id để API nhớ”, “bật prompt caching để API nhớ hội thoại”: đều sai. Cache chỉ giảm chi phí cho tiền tố lặp lại.
Thuật ngữ
Token
Mẩu chữ nhỏ (một từ ngắn hoặc một phần từ) mà model đọc và viết. Tiền và giới hạn tính theo token.
role
Người nói trong một message: user (bạn) hoặc assistant (Claude).
Stateless
Không lưu trạng thái: server không nhớ request trước.

3. stop_reason

CCDV-F D2

Hình dung đời thường
Một nhân viên trả lời bạn rồi dừng. Có nhiều lý do dừng: nói xong; cần bạn giúp tra một thứ rồi mới nói tiếp; hết giờ nên bị ngắt giữa câu; từ chối vì việc không được phép. Bạn cần biết lý do mới biết phải làm gì tiếp. stop_reason chính là lý do đó.

Mỗi response có trường stop_reason: lý do model ngừng viết. Response còn có content (danh sách khối nội dung) và usage (số token đã dùng).

Giá trịÝ nghĩaXử lý
end_turnModel trả lời xongTrả kết quả
tool_useModel muốn gọi toolChạy tool, gửi tool_result, gọi tiếp
max_tokensChạm max_tokens, câu trả lời bị cắtTăng max_tokens hoặc yêu cầu viết tiếp
stop_sequenceGặp chuỗi dừng đã khai báoXử lý theo logic của mình
pause_turnServer tool chạy lâu, lượt bị tạm dừngGửi lại để model tiếp tục
refusalModel từ chối vì lý do an toànKhông retry y hệt; xem lại yêu cầu hoặc chuyển luồng dự phòng

Luôn kiểm tra stop_reason trước khi đọc content. Ví dụ: câu trả lời kết thúc giữa chừng “Bước 1 là cài đặt, bước 2 là…” với stop_reason = max_tokens nghĩa là bị cắt, không phải model chủ ý dừng. Nếu bạn không kiểm tra, người dùng sẽ thấy một câu cụt.

Bẫy. Đừng coi mọi response là “xong”. max_tokens là câu bị cắt, tool_use là chưa xong (model đang chờ bạn chạy tool), refusal thì retry y hệt chỉ bị từ chối lại.
Thuật ngữ
Server tool
Tool chạy phía Anthropic (ví dụ tìm kiếm web), không phải code của bạn chạy.
Chuỗi dừng (stop sequence)
Đoạn chữ bạn khai trước, như ###. Model viết tới đó là dừng.

4. Lỗi HTTP và retry

CCDV-F D2

Hình dung đời thường
Bạn gọi điện đặt bàn. Nếu máy bận, bạn đợi một lúc rồi gọi lại, và lần sau đợi lâu hơn một chút để khỏi chen chúc cùng mọi người. Nhưng nếu bạn quay nhầm số hay đọc sai tên nhà hàng, gọi lại một trăm lần vẫn sai. Phải sửa số trước. Lỗi tạm thời thì retry, lỗi do bạn thì sửa.

Mã HTTP là con số server trả về để báo kết quả. Họ 4xx là lỗi phía bạn gửi. Họ 5xx là lỗi phía server. Retry là gửi lại cùng request. Exponential backoff là chờ lâu dần giữa các lần gửi lại (ví dụ 1 giây, 2 giây, 4 giây), thường cộng thêm một chút ngẫu nhiên (jitter) để nhiều client không cùng thử lại một lúc.

MãLoạiRetry?
400invalid_request_error: sai định dạng, sai tham sốKhông: sửa request
401authentication_error: key saiKhông: sửa key
403permission_errorKhông
404not_found_errorKhông
413request_too_largeKhông: chia nhỏ
429rate_limit_errorCó: backoff theo header retry-after
500api_errorCó: exponential backoff
529overloaded_errorCó: exponential backoff
  • SDK chính thức có sẵn retry (mặc định 2 lần) với exponential backoff cho lỗi kết nối, 408, 409, 429 và 5xx.
  • Bắt lỗi theo chuỗi cụ thể → chung (ví dụ RateLimitError trước APIStatusError) để phân biệt lỗi retry được với lỗi không retry được.
Sai
  • Retry ngay lập tức, không chờ, trong vòng lặp chặt
  • Retry 400 hoặc 401 “cho chắc”
  • Bắt mọi lỗi bằng một except Exception rồi nuốt đi
Đúng
  • Chờ lâu dần, tôn trọng retry-after của 429
  • Sửa request hoặc key trước, không retry
  • Bắt lớp lỗi cụ thể trước, lớp chung sau
Bẫy. 429 và 529 trông giống nhau nhưng khác nguồn. 429 là bạn vượt giới hạn (giảm tốc độ gửi). 529 là server quá tải (chờ rồi thử lại). Cả hai đều retry được. 400 và 413 thì không.
Thực tế 11/2026 Docs hiện hành thêm vài mã mà bảng thi chưa có: 402 billing_error (vấn đề thanh toán), 409 conflict_error (xung đột trạng thái tài nguyên, SDK có retry), 504 timeout_error (request quá giờ; request dài nên dùng streaming). Một số trường hợp 429 do chạm trần chi tiêu thì không có retry-after và retry không giúp được. Vượt giới hạn chi tiêu tự đặt trả về 400. Lỗi xảy ra giữa dòng streaming đến sau khi đã có HTTP 200. Giới hạn kích thước: Messages API 128 MB, Batch 256 MB, Files 500 MB. Nguồn: platform.claude.com/docs/en/api/errors.
Thuật ngữ
Rate limit
Mức tối đa request hoặc token bạn được gửi trong một khoảng thời gian.
Header retry-after
Dòng thông tin kèm response, cho biết nên chờ bao lâu trước khi thử lại.
SDK
Thư viện do Anthropic cung cấp để gọi API từ Python, TypeScript… mà khỏi tự viết HTTP.

5. Streaming

CCDV-F D2 CCDV-F D5 Streaming và SSE ngoài phạm vi CCAR-F.

Hình dung đời thường
Một nhà hàng có thể chờ nấu xong cả mâm rồi bưng ra một lần, hoặc bưng từng món ngay khi có để khách bắt đầu ăn. Cách thứ hai làm khách đỡ sốt ruột dù tổng thời gian nấu như nhau. Streaming là bưng từng món.

Streaming là nhận câu trả lời từng mẩu nhỏ ngay khi model sinh ra, thay vì đợi viết xong. Bạn bật bằng stream: true. API gửi về các server-sent events (SSE): một kết nối giữ mở, server đẩy các sự kiện chữ về dần. Thứ tự:

message_startmở message
→
content_block_start / delta / stoptừng khối nội dung
→
message_deltastop_reason, usage
→
message_stopkết thúc

Kèm ping (giữ kết nối) và error. Dùng streaming để hiện chữ dần cho người dùng và tránh timeout khi output dài hoặc max_tokens lớn.

Cốt lõi. stop_reason và usage nằm ở message_delta, gần cuối dòng. Muốn biết tổng token hay lý do dừng thì phải đọc hết dòng.
Thuật ngữ
Delta
Phần thay đổi nhỏ thêm vào, ở đây là một mẩu chữ mới.
Timeout
Hết thời gian chờ nên kết nối bị cắt. Request rất dài không có streaming dễ gặp.

6. Message Batches API

CCAR-F D4 CCDV-F D2 CCAR-P D4

Hình dung đời thường
Gửi một thùng quần áo cho tiệm giặt giặt thường: rẻ hơn giặt lấy ngay, nhưng bạn không biết chính xác lúc nào xong, chỉ hứa trong ngày hôm sau. Mỗi món đồ có một cái nhãn để bạn nhận đúng đồ. Batch API là tiệm giặt thường. Cái nhãn là custom_id.

Message Batches API nhận nhiều request cùng lúc, xử lý bất đồng bộ (không chờ kết quả ngay), và tính giá thấp hơn.

~50%

rẻ hơn gọi đồng bộ

≤ 24 giờ

thời gian xử lý tối đa, không cam kết độ trễ

custom_id

ghép request với kết quả; kết quả về theo thứ tự bất kỳ

Hợp
  • Báo cáo qua đêm, audit hằng tuần, sinh test hằng đêm
  • Khối lượng lớn, không ai đang chờ
Không hợp
  • Việc chặn: kiểm tra trước merge
  • Người dùng đang chờ
  • Gọi tool nhiều lượt trong một request
  • Lỗi thì chỉ gửi lại các mục lỗi theo custom_id, có điều chỉnh (chia nhỏ tài liệu quá dài).
  • Tính chu kỳ gửi: khoảng cách giữa hai lần gửi + 24 giờ xử lý ≤ SLA. Ví dụ SLA 36 giờ thì gửi tối đa mỗi 12 giờ, nên chọn thưa hơn một chút để có dư.
  • Thử prompt trên mẫu nhỏ trước khi chạy khối lớn.
Cốt lõi. Batch hợp với việc không ai chờ. Việc chặn hoặc có người đang chờ phải gọi đồng bộ. Ví dụ SLA 36 giờ: 12 giờ chờ gom + 24 giờ xử lý = 36 giờ, vừa đủ không dư, nên thực tế chọn chu kỳ thưa hơn chút.
Thực tế 11/2026 Docs hiện hành nói hầu hết batch xong trong khoảng 1 giờ, nhưng vẫn không cam kết và hết hạn sau 24 giờ. Một batch tối đa 100.000 request hoặc 256 MB. Kết quả giữ 29 ngày. custom_id dài 1 đến 64 ký tự. Batch không hỗ trợ stream: true và fast mode. Nguồn: platform.claude.com/docs/en/build-with-claude/batch-processing. Đề thi vẫn theo mốc “≤ 24 giờ”.
Thuật ngữ
Bất đồng bộ (asynchronous)
Gửi việc đi rồi làm việc khác, lúc sau mới quay lại lấy kết quả.
Poll
Hỏi định kỳ “xong chưa?”.
SLA
Mốc thời gian cam kết với người dùng hoặc đối tác (ví dụ báo cáo phải có trong 36 giờ).

7. Ảnh, PDF, file

CCDV-F D2 Vision ngoài phạm vi CCAR-F.

Hình dung đời thường
Bạn nhờ trợ lý đọc một bản hợp đồng. Bạn có thể đưa tận tay mỗi lần hỏi, hoặc gửi hồ sơ lên kho một lần, nhận một mã số, lần sau chỉ cần nói “xem hồ sơ số 42”. Cách hai đỡ phải khuân lại cả tập giấy mỗi lần. Đó là Files API.

Một message có thể chứa nhiều content block (khối nội dung) khác loại: chữ, ảnh, tài liệu.

  • Ảnh: content block image (base64, URL hoặc file_id). PDF: block document.
  • Files API: tải lên một lần, tham chiếu nhiều lần bằng file_id.
  • Đặt tài liệu trước phần câu hỏi trong cùng message.
Cốt lõi. Tài liệu dài đặt trước câu hỏi trong cùng message. Cần dùng một file nhiều lần thì tải lên một lần bằng Files API.
Thuật ngữ
base64
Cách mã hoá dữ liệu nhị phân (ảnh, PDF) thành chuỗi chữ để nhét vào JSON.
file_id
Mã Files API trả về sau khi tải file lên; dùng để tham chiếu lại.

8. Nền tảng bên thứ ba

CCDV-F D2 CCAR-P D1

Hình dung đời thường
Bạn có thể mua cùng một thương hiệu cà phê ở cửa hàng chính hãng hoặc trong siêu thị bạn vẫn có thẻ thành viên. Siêu thị tiện vì tích điểm và thanh toán chung, nhưng mặt hàng mới đôi khi đến muộn hơn. Bedrock, Vertex AI và Foundry là các “siêu thị” đó.

Claude có trên Amazon Bedrock, Google Vertex AI, Microsoft Foundry. Chọn khi cần tính phí, IAM, quản trị theo tài khoản cloud sẵn có. Model ID và cách xác thực khác nhau; tính năng mới có thể đến chậm hơn API của Anthropic. Trọng số model không được phát hành để tự host.

9. Thiết kế ứng dụng Claude

CCDV-F D2

Hình dung đời thường
Khi giao việc cho nhân viên, bạn để lời dặn trong một tờ giấy, tài liệu cần xử lý trong một phong bì khác. Nhân viên không nhầm nội dung phong bì với chỉ thị của bạn. Nếu bạn dán lẫn lộn, một dòng “hãy bỏ qua mọi chỉ thị trước” nằm trong tài liệu có thể bị hiểu là lệnh.
  • Ranh giới nội dung: tách chỉ dẫn với dữ liệu, bọc tài liệu trong thẻ XML (<document>…</document>).
  • Vệ sinh phiên: mỗi việc một phiên; phiên dài thì compact hoặc mở phiên mới kèm tóm tắt.
  • Structured output: tool kèm JSON schema, hoặc tính năng structured outputs / strict: true trên tool để output khớp schema.
  • Đi từ yêu cầu nghiệp vụ tới yêu cầu chức năng và hạ tầng; tính cả vận hành, bảo trì trong vòng đời.

Ví dụ ranh giới nội dung: thay vì dán thẳng email của khách vào prompt, bạn viết:

Tóm tắt email trong thẻ <email> thành 3 gạch đầu dòng.
<email>
…nội dung email của khách, có thể chứa chữ bất kỳ…
</email>

Thẻ cho Claude biết đoạn nào là dữ liệu cần xử lý, đoạn nào là yêu cầu của bạn.

Cốt lõi. Tách chỉ dẫn khỏi dữ liệu bằng thẻ XML; mỗi việc một phiên; muốn output đúng khuôn thì dùng schema, đừng chỉ xin bằng lời.
Thuật ngữ
JSON schema
Bản mô tả khuôn mẫu của JSON: có trường nào, kiểu gì.
Compact
Tóm gọn hội thoại dài để giải phóng chỗ trong context.

10. Quản lý cấu hình

CCDV-F D2

Hình dung đời thường
Một công thức bánh đang bán chạy. Nếu nhà cung cấp bột âm thầm đổi loại bột mà bạn không biết, bánh đổi vị bất ngờ. Bạn muốn ghi rõ “bột loại X, lô Y” và chỉ đổi khi đã thử mẻ nhỏ. Với model là ghim model ID; với prompt là lưu phiên bản trong git.
  • Ghim model: production dùng model ID cụ thể, không dùng alias trỏ tới bản mới nhất. Nâng cấp có chủ đích: đọc migration guide, chạy lại eval.
  • Version prompt: lưu prompt trong git như code, gắn phiên bản, chạy eval khi đổi.
  • Cấu hình Claude Code (CLAUDE.md, settings.json, plugin) xem bài 05 §7.
Sai
  • Production dùng alias “mới nhất” và để nó tự đổi
  • Sửa prompt trực tiếp trên server, không ghi lại
Đúng
  • Ghim model ID cụ thể, nâng cấp có chủ đích sau khi chạy eval
  • Prompt nằm trong git, có phiên bản, đổi thì chạy lại eval
Thuật ngữ
Alias
Tên chung trỏ tới “bản mới nhất” của một dòng model. Nội dung sau tên có thể đổi.
Eval
Bộ ca thử có đáp án mong muốn, để đo prompt hoặc model có đạt không.

11. Gọi song song

CCDV-F D2

Hình dung đời thường
Một nhà hàng có tám bàn phục vụ. Gọi từng khách một thì chậm. Cho cả trăm khách vào cùng lúc thì bếp sập. Cách hợp lý: tám bàn chạy cùng lúc, bàn nào xong thì mời khách kế tiếp vào. Con số tám là một semaphore.

Khi có nhiều request độc lập, chạy chúng đồng thời sẽ nhanh hơn chạy tuần tự. Nhưng gửi quá nhiều cùng lúc thì dính 429. Một semaphore là bộ đếm giới hạn số việc chạy đồng thời.

sem = asyncio.Semaphore(8)            # giới hạn đồng thời để tránh 429
async def one(doc):
    async with sem:
        return await client.messages.create(…)
results = await asyncio.gather(*(one(d) for d in docs))
  • Semaphore(8): tối đa 8 request đang chạy. Việc thứ 9 chờ có chỗ trống.
  • gather: chờ mọi việc xong và gom kết quả theo đúng thứ tự đầu vào.

Tuần tự quá chậm; bắn hết không giới hạn thì dính 429; không gấp thì dùng Batch.
