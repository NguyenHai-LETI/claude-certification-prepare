1. Tổng quan

Hình dung đời thường
Bạn ngồi ở quán ăn. Bồi bàn (Claude) không tự nấu. Anh ta ghi phiếu gọi món rồi đưa vào bếp (code của bạn). Bếp nấu xong, đưa đĩa ra, bồi bàn mang đến bàn. Bài này là về cách viết phiếu gọi món đúng mẫu, cho bếp nấu nhiều món cùng lúc, và đỡ tốn tiền khi cứ đưa lại cùng một thực đơn dài mỗi lần.

2. Tool Definition Anatomy (Bài 1–2)

CCDV-F D8 CCAR-F D2

Hình dung đời thường
Một tờ hướng dẫn dán trên máy photocopy: tên máy, máy làm gì, bấm nút nào cần nhập gì, và ví dụ mẫu. Claude đọc tờ hướng dẫn này để quyết định có dùng máy hay không. Tờ hướng dẫn càng rõ thì Claude càng ít dùng nhầm.

Mỗi tool gồm bốn thành phần (bài 04 đã giới thiệu ba thành phần đầu):

2.1 Merge Overlapping Tools

Nếu nhiều tools có chức năng tương tự, merge chúng thành một:

# BAD — Claude không biết khi nào dùng cái nào
tools_bad = [
    {"name": "search_by_name", ...},
    {"name": "search_by_category", ...},
    {"name": "search_by_price", ...}
]

# GOOD — một tool với optional parameters
tools_good = [{
    "name": "search_products",
    "description": "Search products by any combination of name, category, or price range.",
    "input_schema": {
        "type": "object",
        "properties": {
            "name": {"type": "string"},
            "category": {"type": "string"},
            "min_price": {"type": "number"},
            "max_price": {"type": "number"}
        }
        # required: [] — tất cả optional
    }
}]
  • tools_bad: ba tool với ba tên gần giống, ... là phần còn lại bị lược. Câu hỏi “tìm tai nghe rẻ hơn 100 đô” cần cả tên lẫn giá, nhưng Claude chỉ được chọn một tool.
  • tools_good: một tool với bốn trường, không có trường nào bắt buộc (required bỏ trống). Claude điền trường nào cần dùng và bỏ qua trường còn lại.
Sai
  • Ba tool search_by_* mô tả mơ hồ như nhau
  • Thêm few-shot để “dạy” Claude chọn giữa ba tool đó
Đúng
  • Một tool search_products với tham số tùy chọn
  • Hoặc giữ tool riêng nhưng viết description khác biệt rõ
Thực tế 11/2026 Nếu các tool trùng chức năng nhưng khác hợp đồng vào/ra, bài 04 gợi ý cách ngược lại: tách tool chung thành tool hẹp có hợp đồng rõ. Hai lời khuyên không mâu thuẫn: mục tiêu chung là mỗi tool có ranh giới dễ phân biệt. Gộp khi chỉ khác nhau ở bộ lọc, tách khi khác nhau ở mục đích.

3. Strict Tool Use (Bài 3–4)

CCDV-F D8 CCAR-F D4

Hình dung đời thường
Một biểu mẫu giấy chỉ có ô tick sẵn thì không ai điền sai được. Một biểu mẫu để trống thì có người viết “rẻ thôi” vào ô “giá tối đa”. Strict mode biến tool input thành biểu mẫu có ô tick sẵn: Claude chỉ có thể điền thứ hợp lệ với schema.

Strict mode dùng grammar-constrained sampling — Claude được đảm bảo chỉ generate JSON hợp lệ theo schema. Hiệu quả hơn nhiều so với chỉ nhắc "return valid JSON".

Grammar-constrained sampling (lấy mẫu có ràng buộc ngữ pháp) nghĩa là ở mỗi bước chọn token, model chỉ được chọn trong các token còn khớp schema. Token làm hỏng JSON bị loại ngay từ đầu.

from pydantic import BaseModel, Field
from typing import Optional

class SearchInput(BaseModel):
    query: str = Field(description="Search keywords")
    category: Optional[str] = Field(None, description="Product category")
    max_price: Optional[float] = Field(None, ge=0)

# Generate schema từ Pydantic model
schema = SearchInput.model_json_schema()
# Phải thêm additionalProperties: false cho strict mode
schema["additionalProperties"] = False

tools = [{
    "name": "search_products",
    "description": "Search the product catalog.",
    "input_schema": schema
}]

response = client.messages.create(
    model="claude-sonnet-5",
    tools=tools,
    tool_choice={
        "type": "tool",
        "name": "search_products",
        "disable_parallel_tool_use": True  # Chỉ gọi tool này
    },
    messages=[{"role": "user", "content": "Find wireless headphones"}]
)

# Parse với Pydantic — sẽ luôn thành công vì strict mode đảm bảo valid JSON
for block in response.content:
    if block.type == "tool_use":
        search_input = SearchInput(**block.input)  # Type-safe!

Chú giải từng đoạn:

  • class SearchInput(BaseModel): khai báo hình dạng đầu vào bằng một lớp Python. Pydantic là thư viện Python kiểm tra dữ liệu theo kiểu đã khai báo.
  • query: str = Field(description=...): trường bắt buộc kiểu chuỗi. Optional[str] = Field(None, ...): trường tùy chọn, mặc định None. ge=0: giá trị phải lớn hơn hoặc bằng 0.
  • SearchInput.model_json_schema(): Pydantic tự sinh JSON Schema từ lớp trên, đỡ viết tay.
  • schema["additionalProperties"] = False: cấm trường lạ không có trong schema. Strict mode yêu cầu điều này.
  • tool_choice={"type": "tool", "name": "search_products", ...}: ép Claude gọi đúng tool này (bài 04). disable_parallel_tool_use: True: chỉ cho một lời gọi trong lượt này.
  • for block in response.content: phản hồi gồm nhiều khối. Chọn khối tool_use và lấy block.input.
  • SearchInput(**block.input): biến dict thành đối tượng đã kiểm kiểu. ** trải các cặp khóa-giá trị thành tham số.
Strict mode requirements:
  • Tất cả properties phải được khai báo trong properties
  • additionalProperties: false bắt buộc
  • Không dùng $ref hay recursive schemas
  • Chỉ support một số JSON Schema keywords nhất định
Sai
  • Chỉ viết “hãy trả về JSON hợp lệ” trong prompt rồi tin chắc
  • Dùng schema có $ref hoặc đệ quy cho strict mode
  • Quên additionalProperties: false
Đúng
  • Dùng strict mode để model chỉ sinh JSON hợp lệ theo schema
  • Viết schema phẳng, mọi trường khai báo trong properties
  • Luôn đặt additionalProperties: false
Thực tế 11/2026 Tài liệu hiện hành bật strict bằng cờ "strict": true đặt ngang hàng name, description, input_schema trong tool definition, cùng với additionalProperties: false trong schema. Khi đó input trong khối tool_use khớp schema và name luôn hợp lệ. Tool computer use và browser use không nhận strict: true. Ví dụ thi ở trên chỉ nhấn mạnh yêu cầu schema. Nguồn: Strict tool use.
Cốt lõi. Strict mode đảm bảo hình dạng đầu vào đúng. Nó không đảm bảo nghiệp vụ đúng: Claude vẫn có thể điền một mã sản phẩm đúng kiểu chuỗi nhưng không tồn tại.

4. Parallel Tool Calling (Bài 5–6)

CCDV-F D8

Hình dung đời thường
Bạn cần ba việc: hỏi thời tiết, xem giá cổ phiếu, đọc tin công nghệ. Làm lần lượt thì mất 3 lượt chờ. Nhờ ba người cùng làm thì chỉ chờ lâu bằng người chậm nhất. Parallel tool calling là Claude giao ba việc cùng lúc, code của bạn cho ba luồng chạy cùng lúc.

Claude có thể gọi nhiều tools cùng lúc trong một turn — chạy song song để giảm latency:

from concurrent.futures import ThreadPoolExecutor
import anthropic

client = anthropic.Anthropic()

def run_tool(tool_name: str, tool_input: dict) -> str:
    """Execute a tool and return result as string."""
    if tool_name == "get_weather":
        return get_weather(**tool_input)
    elif tool_name == "get_stock_price":
        return get_stock_price(**tool_input)
    elif tool_name == "get_news":
        return get_news(**tool_input)
    else:
        raise ValueError(f"Unknown tool: {tool_name}")

messages = [{"role": "user", "content": "Get weather, AAPL stock price, and tech news."}]

while True:
    response = client.messages.create(
        model="claude-sonnet-5", max_tokens=2048,
        tools=tools, messages=messages
    )

    if response.stop_reason == "end_turn":
        break

    if response.stop_reason == "tool_use":
        # Collect ALL tool_use blocks trước khi chạy
        tool_use_blocks = [b for b in response.content if b.type == "tool_use"]

        # Chạy song song với ThreadPoolExecutor
        with ThreadPoolExecutor(max_workers=len(tool_use_blocks)) as executor:
            futures = {
                executor.submit(run_tool, block.name, block.input): block
                for block in tool_use_blocks
            }

            tool_results = []
            for future, block in futures.items():
                try:
                    result = future.result(timeout=30)
                    tool_results.append({
                        "type": "tool_result",
                        "tool_use_id": block.id,
                        "content": result
                    })
                except Exception as e:
                    tool_results.append({
                        "type": "tool_result",
                        "tool_use_id": block.id,
                        "is_error": True,  # Quan trọng: báo lỗi cho Claude
                        "content": f"Error: {str(e)}"
                    })

        # Thêm cả response của Claude VÀ tất cả tool results vào messages
        messages.append({"role": "assistant", "content": response.content})
        messages.append({"role": "user", "content": tool_results})  # Một user message, nhiều results

Chú giải từng đoạn:

  • ThreadPoolExecutor: công cụ của Python để chạy nhiều hàm cùng lúc trên nhiều luồng (thread). Phù hợp khi tool chủ yếu chờ mạng.
  • run_tool(tool_name, tool_input): một hàm điều phối. Nhận tên tool, gọi đúng hàm; tên lạ thì raise ValueError để lỗi lộ ra thay vì im lặng.
  • while True: vòng lặp chạy đến khi Claude trả end_turn.
  • tool_use_blocks = [b for b in response.content if b.type == "tool_use"]: lọc ra mọi khối tool_use trong câu trả lời. Có thể là 1 hoặc nhiều khối.
  • ThreadPoolExecutor(max_workers=len(tool_use_blocks)): số luồng bằng số tool cần chạy, nên tất cả chạy cùng lúc.
  • executor.submit(run_tool, block.name, block.input): giao một việc cho luồng. Trả về future (hứa hẹn kết quả sẽ có).
  • future.result(timeout=30): chờ kết quả tối đa 30 giây. Quá hạn thì ném lỗi, chuyển xuống except.
  • "tool_use_id": block.id: ghép kết quả với đúng lời gọi.
  • "is_error": True: báo cho Claude biết tool lỗi. Claude đọc nội dung lỗi và quyết định thử lại, hỏi người dùng hay đổi cách. Không ném ngoại lệ làm chết cả vòng lặp.
  • Hai dòng cuối: thêm response.content của Claude vào messages trước, rồi thêm một tin nhắn user chứa danh sách mọi kết quả.
Sai
  • Gửi mỗi tool_result một tin nhắn user riêng
  • Chạy tool_use đầu tiên ngay khi thấy, rồi mới đọc các khối còn lại
  • Ném ngoại lệ khi tool lỗi, làm sập vòng lặp
Đúng
  • Một tin nhắn user chứa mảng mọi tool_result, đứng sau tin nhắn assistant tương ứng
  • Gom tất cả tool_use rồi mới chạy song song
  • Trả is_error: true kèm nội dung lỗi cho Claude
Quy tắc parallel tools: (1) Collect TẤT CẢ tool_use blocks trước khi chạy bất kỳ cái nào. (2) Chạy song song với ThreadPoolExecutor. (3) Dùng is_error: true cho failures — không throw exception. (4) Gửi TẤT CẢ results trong một user message duy nhất.
Thực tế 11/2026 Tài liệu hiện hành xác nhận cùng quy tắc: tách mỗi kết quả thành một tin nhắn user riêng là lỗi định dạng phổ biến nhất, và còn “dạy” Claude gọi song song ít hơn. Trong tin nhắn user đó, các khối tool_result phải đứng trước mọi nội dung văn bản. Claude 4 trở lên mặc định gọi song song khi hợp lý; disable_parallel_tool_use: true trong tool_choice tắt hành vi này. Nguồn: Parallel tool use.

5. Cost Optimization (Bài 7–9)

CCDV-F D5

Hình dung đời thường
Có hai cách tiết kiệm tiền ở quán. Cách một: nhờ bếp tự làm gộp cả quy trình (lọc, cộng, so sánh) rồi chỉ báo kết quả cuối, thay vì gọi bồi bàn chạy ra chạy vào từng bước. Cách hai: thực đơn dài 20 trang đã được quán lưu sẵn, lần sau bạn chỉ cần nói “dùng thực đơn hôm qua” thay vì đọc lại từ đầu.

5.1 Programmatic Tool Calling (allowed_callers)

Programmatic tool calling cho phép tool chỉ được gọi từ code của bạn, không phải qua user request — dùng cho tools không cần user approve từng lần:

tools = [{
    "name": "execute_query",
    "description": "Execute a pre-approved database query",
    "input_schema": {
        "type": "object",
        "properties": {
            "query_id": {"type": "string", "description": "ID of the pre-approved query"}
        },
        "required": ["query_id"]
    },
    # Chỉ allow gọi từ container ID cụ thể
    "allowed_callers": ["container:your-container-id"]
}]

response = client.beta.messages.create(
    model="claude-sonnet-5",
    tools=tools,
    betas=["programmatic-tool-use-2025-01-01"],
    messages=[{"role": "user", "content": "Run the monthly report"}]
)
  • "allowed_callers": [...]: danh sách “ai được phép gọi tool này”. Đây là trường riêng của programmatic tool calling.
  • client.beta.messages.create: dùng endpoint beta, vì tính năng đang thử nghiệm ở thời điểm tài liệu thi viết.
  • betas=[...]: bật tính năng beta bằng tên đã định.
  • query_id thay cho câu SQL tự do: tool chỉ chạy truy vấn đã duyệt sẵn, nên rủi ro thấp hơn.
Thực tế 11/2026 Tài liệu hiện hành mô tả khác ví dụ thi ở hai điểm. (1) Giá trị allowed_callers là phiên bản của code execution tool, ví dụ ["code_execution_20260120"], hoặc ["direct"] (mặc định, Claude gọi trực tiếp); ví dụ dạng "container:..." ở trên không có trong tài liệu hiện hành. (2) Tính năng yêu cầu thêm code execution tool vào tools và ví dụ chính thức không dùng tham số betas. Ngoài ra allowed_callers chỉ hướng dẫn Claude, không phải hàng rào bảo mật cứng; code của bạn vẫn phải xử lý trường hợp bị gọi trực tiếp. Mỗi khối tool_use có trường caller cho biết gọi trực tiếp hay từ code. Đề thi theo tài liệu khóa học; khi làm thật, tra tài liệu mới nhất. Nguồn: Programmatic tool calling.
Thuật ngữ
Container
Môi trường chạy code cô lập (sandbox) do Anthropic cung cấp qua code execution tool.
Beta
Tính năng đang thử nghiệm, có thể đổi trước khi chính thức.
Context window
Lượng văn bản Claude xem được trong một lần xử lý. Kết quả tool dài làm đầy cửa sổ này và tốn token.

5.2 Prompt Caching với Tool Definitions

Tool definitions thường lớn và ổn định — cache chúng để tiết kiệm:

# Cache tool definitions (thường 2K-5K tokens, không đổi)
tools_with_cache = [
    {**tool_def, "cache_control": {"type": "ephemeral"}}  # Cache mỗi tool
    if i == len(tool_definitions) - 1  # Chỉ cache tool CUỐI CÙNG
    else tool_def
    for i, tool_def in enumerate(tool_definitions)
]
# Lý do cache tool cuối: Claude cache theo checkpoint — cache point cuối nhất
# sẽ cover tất cả content trước nó, bao gồm cả các tool trước đó

Chú giải:

  • {**tool_def, "cache_control": {"type": "ephemeral"}}: sao chép tool và thêm trường cache_control. ** trải các trường cũ ra. ephemeral là kiểu cache tạm có thời hạn.
  • if i == len(tool_definitions) - 1: chỉ tool có chỉ số cuối mới được thêm. Các tool trước giữ nguyên (else tool_def).
  • Một điểm đánh dấu ở cuối là đủ, vì nó phủ mọi nội dung đứng trước.

Cost savings với caching:

ScenarioKhông cacheVới cache
100 requests, 5K token tool defs500K input tokens5K write + ~495K read (rẻ hơn 10x)
Nightly eval (1000 requests)Tính theo 1000x full prompt1 write + 999 reads
Sai
  • Đặt cache_control ở tool đầu tiên và hy vọng cache cả danh sách
  • Cache tool definitions hay đổi liên tục
Đúng
  • Đặt ở tool cuối, vì checkpoint phủ mọi nội dung đứng trước nó
  • Cache phần ổn định (tool definitions thường 2K-5K token, ít đổi)
Thực tế 11/2026 Tài liệu hiện hành cho biết đổi nội dung tool definitions làm cache của phần sau nó mất hiệu lực, nên chỉ nên cache bộ tool ổn định. Tài liệu bài 04 cũng nêu đổi tool_choice giữa các lượt làm mất cache của các message. Con số “rẻ hơn 10x” trong bảng là cách nói gọn của khóa học; giá cụ thể xem trang giá chính thức.
Bẫy. Nhầm giữa hai kỹ thuật tiết kiệm: caching giảm giá của token lặp lại (tool definitions giống nhau mỗi lần), còn programmatic tool calling giảm số vòng và lượng dữ liệu vào context. Hai kỹ thuật dùng được cùng nhau.
